Vì sao nén lịch sử nhiều lần liên tiếp dễ làm mất ràng buộc?Why does compaction applied repeatedly tend to lose constraints?

"Photocopy của bản photocopy": mỗi vòng chi tiết mờ đi — "CUDA 12.4" → "CUDA 12.x" → "recent CUDA". Chống bằng cách chép nguyên văn anchor, giữ đuôi gần nhất, giữ đường dẫn về bằng chứng gốc (slide 50). Trong ví dụ TravelPlanner, ngân sách — phương tiện di chuyển — chế độ ăn là loại ràng buộc gì?In the TravelPlanner example, budget — transportation — diet are what kind of constraint?

Chia nhỏ rất sạch (vé máy bay, khách sạn, ăn uống, tham quan) nhưng ghép lại có thể vượt ngân sách hoặc không kịp di chuyển — vì mỗi mảnh tối ưu cho riêng nó. Cách xử lý: xác định trước ràng buộc "không được vỡ ở bất kỳ mảnh nào"; giao manager giữ chứ không đẩy xuống worker; kiểm tra ở bước ghép như tiêu chí nghiệm thu.The decomposition is very clean (flights, hotel, food, attractions) but combining the pieces can exceed the budget or leave no time to travel — because each piece optimizes for itself. The fix: identify up front the constraints that "must not break in any piece"; give them to the manager rather than pushing them down to workers; check them at the merge step as acceptance criteria.

Đâu là lý do sâu xa nhất khiến code là domain mà agent tiến bộ nhanh nhất?What is the deepest reason code is the domain where agents improve fastest?

Mục 1: code là "bài tập có đáp án ở cuối sách" — test và build trả lời đúng/sai ngay, không cần con người phán. Nhờ đó vòng lặp localize → edit → verify có điểm dừng khách quan, và RL bằng phần thưởng thực thi (slide 28) hoạt động đặc biệt tốt trong domain code.Section 1: code is "a problem set with the answers at the back of the book" — tests and builds answer right/wrong immediately, with no human needed to judge. That gives the localize → edit → verify loop an objective stopping point, and RL with execution rewards (slide 28) works especially well in the code domain.

Least-to-Most giải bài toán khó bằng hai giai đoạn như thế nào?How does Least-to-Most solve a hard problem in two stages?

Vì sao hiệu quả: model giỏi trả lời câu hỏi con hơn câu hỏi lớn, và mỗi câu con cần ít ngữ cảnh hơn — lợi ích còn tăng theo độ dài bài toán. Điểm mạnh thứ hai là kiểm được từng chặng; câu con nào vẫn khó thì chia tiếp (tinh thần Recursive Language Models).Why it works: models are better at answering sub-questions than the big question, and each sub-question needs less context — the benefit even grows with problem length. The second strength is that every stage can be checked; any sub-question that is still hard gets split further (the spirit of Recursive Language Models).

Vì sao tổng token cộng dồn tăng nhanh hơn nhiều so với số bước của agent?Why does the cumulative token total grow much faster than the number of agent steps?

Mỗi bước chỉ thêm ~5K nhưng cả phần cũ bị gửi lại: input mỗi lần tăng tuyến tính (6K → 26K sau 5 lần), cộng dồn tăng bậc hai (80K sau 5 lần; ~4,14M sau 40 bước). Slide 3 gọi là "quadratic input from linear history growth".Each step adds only ~5K, but all the old content is resent: per-call input grows linearly (6K → 26K after 5 calls), while the cumulative total grows quadratically (80K after 5 calls; ~4.14M after 40 steps). Slide 3 calls this "quadratic input from linear history growth".
