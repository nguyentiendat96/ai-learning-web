Nhắc lại: ta đang ở đâu

Bài 01 kết thúc với câu thần chú: "An agent is a model in a loop" — agent là một model nằm trong một vòng lặp. Nhưng còn hai câu hỏi bỏ ngỏ:

  • "Model" ở đây chính xác là gì, và nó hoạt động ra sao?
  • Làm sao một model chỉ biết sinh chữ lại hành động được — chạy lệnh, sửa file, gọi API?

Bài này trả lời cả hai. Đây là bài nền tảng nhất của khóa — hiểu chắc nó thì mọi bài sau đều dễ.

LLM — cỗ máy dự đoán token

Điều duy nhất một LLM làm là dự đoán token tiếp theo. Token là mảnh chữ nhỏ — có thể là một từ, một phần từ, hoặc một dấu câu. Quy trình lặp đi lặp lại:

  1. Nhìn vào chuỗi token hiện có (prompt + những gì đã sinh).
  2. Cho xác suất cho mọi token có thể xảy ra tiếp theo.
  3. Chọn một token, nối vào chuỗi.
  4. Lặp lại từ bước 1 — lúc này chuỗi đã dài thêm một token.

Ví dụ: nhìn thấy The capital of France is, model gán xác suất cao nhất cho token Paris — chọn nó, nối vào, và tiếp tục.

Một biến thể quan trọng: chain of thought — trước khi đưa ra câu trả lời, model sinh ra các token suy luận trung gian. Các token này trở thành ngữ cảnh cho những dự đoán sau, giúp câu trả lời chính xác hơn. Ví dụ từ slide 10:

Prompt:     2 × (3 + 4)
Reasoning:  3 + 4 = 7          ← token suy luận trung gian
Answer:     14

Ghi nhớ điểm này: mọi thứ model làm — trả lời, suy luận, và cả "gọi tool" — đều chỉ là sinh token. Không có nút bấm ma thuật nào khác.[1]

Tool — giao diện có kiểu

Nếu model chỉ sinh chữ, thì "chạy lệnh shell" hay "gọi API" là những thứ nằm ngoài nó. Cầu nối giữa hai bên là tool:

"A tool is an interface through which a language model can invoke an external computer program."

— Lecture 02, slide 3 [2]

Mỗi tool được mô tả bằng một định nghĩa gồm: name (tên), description (mô tả để model hiểu khi nào dùng), và JSON schema (kiểu dữ liệu của các tham số). Ví dụ tool đọc file từ slide 11:

{
  "name": "read_file",
  "description": "Read a UTF-8 file.",
  "parameters": {
    "type": "object",
    "properties": { "path": { "type": "string" } },
    "required": ["path"]
  }
}

Và đây là điểm dễ gây bất ngờ nhất: model không có kênh riêng để "thấy" tool. Chat template chỉ đơn giản render định nghĩa tool thành text và nhét vào prompt:

<tools>
{"name":"read_file","description":"Read a UTF-8 file.", ...}
</tools>

Nghĩa là: với model, danh sách tool chỉ là… một đoạn văn bản trong ngữ cảnh. Nó "biết" mình có tool nào vì đọc được mô tả — giống như bạn đọc một tờ hướng dẫn.[3]

Tool call — hành động cũng là token

Khi model quyết định dùng tool, nó sinh ra một chuỗi token mô tả lời gọi — ví dụ từ slide 12:

<tool_call>
{"name":"read_file","arguments":{"path":"test.py"}}
</tool_call>

Chuỗi này trông giống một hành động, nhưng thực chất vẫn chỉ là dự đoán token tiếp theo. Việc biến nó thành hành động thật là của harness — chương trình chạy vòng lặp agent. Harness sẽ:

  1. Parse — đọc chuỗi token, tách ra tên tool + tham số.
  2. Validate — kiểm tra tham số đúng schema không.
  3. Execute — chạy chương trình tương ứng (đọc file, gọi API…).
  4. Return — gửi kết quả về cho model dưới dạng một message mới, kèm tool_call_id để khớp kết quả với lời gọi (quan trọng khi có nhiều lời gọi cùng lúc).

Kết quả quay về trông như thế này (slide 12):

<tool_response>
def add(a, b): …
</tool_response>

"The model proposes; external software decides whether and how to execute."

— Lecture 02, slide 3 [2]

Đây không chỉ là chi tiết kỹ thuật — nó là nền tảng của safety về sau: vì quyền quyết định nằm ở harness, harness có thể chặn, xác nhận, hoặc giới hạn mọi lời gọi tool trước khi nó chạm vào thế giới thật.[4]

Vòng lặp ReAct

Ghép tất cả lại, ta được vòng lặp hoàn chỉnh — lecture gọi là mô hình ReAct (reason + act):

messages = [hướng dẫn hệ thống, task]          # ngữ cảnh ban đầu
while True:
    message = model.query(messages)            # model sinh token từ ngữ cảnh
    messages.append(message)                   # ghi lại vào lịch sử
    if message là câu trả lời cuối:            # model quyết định dừng
        break
    kết_quả = harness.execute(message)         # harness chạy tool call
    messages.append(kết_quả)                   # kết quả thành quan sát mới
                                               # → vòng lặp quay lại đầu

Đây là pseudocode đơn giản hóa từ slide 15. Bản thật nằm trong mini-swe-agent — agent chỉ ~100 dòng Python nhưng đạt hơn 74% trên SWE-bench verified (benchmark sửa lỗi GitHub thật). Bạn sẽ đọc code đó ở bài sau.

Vậy câu thần chú có nghĩa là

Model sinh token dự đoán từ ngữ cảnh. Loop là vòng while: hành động thay đổi môi trường, kết quả quay về thành quan sát mới, ngữ cảnh lớn dần — cho đến khi model quyết định dừng.

Bài 03 đi sâu vào phần "tool" của vòng lặp: thiết kế tool tốt, khi nào nên gọi, gọi song song, và cách đánh giá tool use (theo buổi 1b của khóa).

Kiểm tra hiểu

Làm ngay — sai thì thử lại, đúng thì hiện giải thích.

1. Hoàn thành câu thần chú của khóa học:

"An agent is a model in a ."

2. Khi model "gọi tool", thực chất nó đang làm gì?

Gợi ý: model chỉ có một khả năng duy nhất — dự đoán token tiếp theo.

Chính xác. Model chỉ sinh token. Chuỗi token đó (ví dụ <tool_call>{"name":"read_file",...}</tool_call>) chỉ mô tả lời gọi — nó chưa chạy gì cả. Việc thực thi là bước tiếp theo, do harness làm.

3. Ai là bên thực thi tool call?

Gợi ý: lecture 02 nói "The model proposes; external software decides…" — external software đó tên là gì?

Chính xác. Harness parse → validate → execute → return kết quả. Chính vì quyền thực thi nằm ở harness (không phải model) mà sau này người ta mới gắn được các lớp an toàn: sandbox, giới hạn quyền, xác nhận của người dùng.

4. Một định nghĩa tool (tool definition) gồm những phần nào?

Gợi ý: model cần biết tên tool, khi nào dùng, và tham số có kiểu gì.

Chính xác. Name + description + JSON schema — và chat template render cả ba thành text trong prompt. Model "biết" có tool nào đơn giản vì đọc được mô tả, chứ không có kênh kết nối đặc biệt nào.

5. Chain of thought (chuỗi suy luận) là gì?

Gợi ý: nhớ ví dụ 2 × (3 + 4) ở mục 2.

Chính xác. Các token suy luận trung gian trở thành ngữ cảnh cho những dự đoán sau — nhờ đó model "tính toán" được những việc khó hơn. Và chúng cũng chỉ là token, như mọi thứ khác model sinh ra.

Thực hành — tự làm, tự kiểm

Bài tập 1 — Tự thiết kế một tool

Viết định nghĩa cho một tool mà bạn muốn agent của mình có. Gồm 3 phần: name, description (1 câu, nói rõ khi nào dùng), và JSON schema cho 1–2 tham số. Gợi ý đề bài: get_weather(city), send_email(to, subject), search_products(keyword, max_price)… hoặc tự nghĩ.

Xem đáp án mẫu (get_weather) 
{
  "name": "get_weather",
  "description": "Get the current weather for a city.",
  "parameters": {
    "type": "object",
    "properties": { "city": { "type": "string" } },
    "required": ["city"]
  }
}

Tiêu chí tự kiểm: name ngắn và rõ? description nói được khi nào dùng? schema khai đúng kiểu tham số và tham số nào bắt buộc?

Bài tập 2 — Giải thích bằng lời của bạn

Trong 3–4 câu: vì sao một model chỉ biết "dự đoán token tiếp theo" mà vẫn có thể gọi tool và hành động lên thế giới bên ngoài?

Checklist tự kiểm

Câu trả lời tốt cần đủ 3 ý: (1) model chỉ sinh token — tool call cũng chỉ là một chuỗi token nó viết ra; (2) harness đọc chuỗi đó rồi thực thi thật; (3) kết quả được đưa trở lại ngữ cảnh như một observation mới, để model quyết định bước tiếp.

Tự làm trước, rồi mới mở đáp án để đối chiếu. (Muốn tôi chữa kỹ thì cứ gửi vào chat — nhưng không bắt buộc.)
