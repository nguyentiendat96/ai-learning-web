Cách học bài này

Bạn đã nắm nền tảng agent (9 bài đầu) nhưng mới với Claude platform — nên bài này đi theo đúng thứ tự thực tế khi làm: khai báo tool → chạy vòng lặp → xử lý lỗi → chuyển sang built-in tool → đóng gói bằng MCP.

Mọi tên tham số, tên block, cú pháp trong bài đều lấy nguyên từ docs Anthropic / MCP. Chỗ nào là con số hay phiên bản dễ đổi, tôi ghi rõ (xem docs mới nhất) — bạn đừng học thuộc lòng chuỗi version, hãy nhớ hình dạng của vấn đề.

Tool use trên Claude API — hai loại tool

Tool use (còn gọi là function calling) cho phép Claude gọi những hàm mà bạn định nghĩa, hoặc những hàm do Anthropic cung cấp. Claude quyết định gọi tool nào dựa trên yêu cầu của người dùng và description của tool. Kết quả trả về là một lời gọi có cấu trúc — lời gọi đó do app của bạn chạy, hoặc do hạ tầng Anthropic chạy.

Cách phân loại duy nhất bạn cần nhớ: code chạy ở đâu.

Client toolServer tool
Code chạy ở đâuỨng dụng của bạnHạ tầng của Anthropic
Ví dụget_weather bạn tự viết; các tool Anthropic định nghĩa sẵn schema như bash, text_editorweb_search, web_fetch, code_execution, tool_search
Claude trả về gìstop_reason: "tool_use" + một hoặc nhiều block tool_useClaude nhận kết quả trực tiếp trong cùng response
Bạn phải làm gìChạy hàm thật, gửi lại block tool_resultKhông viết handler — chỉ đọc kết quả
Khác biệt với các API "kiểu cũ"

Nhiều API tách tool thành role riêng (tool, function). Claude API thì không: tool nằm thẳng trong cấu trúc user / assistant.

  • Message assistant chứa tool_use
  • Message user chứa tool_result (cùng với nội dung người dùng)

Nắm được điều này là bạn đọc được mọi ví dụ trong docs mà không bị rối.

Khi nào Claude gọi tool — và khi nào không

Với giá trị mặc định "tool_choice": {"type": "auto"}, Claude tự quyết định mỗi lượt: gọi tool hay trả lời thẳng.

  • Gọi tool khi yêu cầu khớp với khả năng được mô tả của tool, và câu trả lời chưa nằm trong context.
  • Trả lời thẳng với kiến thức ổn định, việc sáng tạo, và các lượt trò chuyện thông thường.

Ranh giới này lái được bằng system prompt — nhẹ thì "Use the tools to investigate before responding.", mạnh hơn thì "Always call a tool first before responding.", còn muốn giữ thận trọng thì "Use your judgment about whether to call a tool or respond directly." Muốn cứng thì dùng tool_choice (mục sau).

Vòng lặp: tools → tool_use → tool_result

Đây là phần xương sống của cả bài. Một lượt gọi client tool gồm đúng năm bước:

  1. Gửi request — messages kèm tham số tools ở cấp cao nhất, mỗi tool là name + description + input_schema.
  2. Claude trả về lời gọi — response có stop_reason: "tool_use" và block tool_use chứa id, name, input.
  3. Bạn chạy tool thật — tra tên tool trong code của bạn, truyền input vào.
  4. Gửi kết quả về — message user mới chứa block tool_result với tool_use_id (chính là id ở bước 2) và content.
  5. Claude trả lời cuối — lần này dùng kết quả tool để hoàn thành câu trả lời cho người dùng.

Đây là hình dạng response ở bước 2 (lấy từ docs):

{
  "id": "msg_01Aq9w938a90dw8q",
  "model": "claude-opus-5-5",
  "stop_reason": "tool_use",
  "role": "assistant",
  "content": [
    { "type": "text", "text": "I'll check the current weather in San Francisco for you." },
    {
      "type": "tool_use",
      "id": "toolu_01A09q90qw90lq917835lq9",
      "name": "get_weather",
      "input": { "location": "San Francisco, CA", "unit": "celsius" }
    }
  ]
}

Và đây là toàn bộ vòng lặp bằng Python (rút gọn từ ví dụ chính thức):

tools = [{
    "name": "get_weather",
    "description": "Get the current weather for a given location.",
    "input_schema": {
        "type": "object",
        "properties": {
            "location": {"type": "string",
                         "description": "City and state, e.g. San Francisco, CA"}
        },
        "required": ["location"]
    }
}]
messages = [{"role": "user", "content": "What's the weather in San Francisco?"}]

# 1) Claude trả về tool_use
response = client.messages.create(
    model="claude-opus-5-5", max_tokens=1024,
    tools=tools, messages=messages,
)
tool_use = next(b for b in response.content if b.type == "tool_use")
# response.stop_reason  == "tool_use"
# tool_use.name         == "get_weather"
# tool_use.input        == {"location": "San Francisco, CA"}

# 2) Bạn chạy tool thật
weather = "15 degrees Celsius, partly cloudy"

# 3) Gửi kết quả về, giữ nguyên assistant message ở giữa
messages += [
    {"role": "assistant", "content": response.content},
    {"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": tool_use.id, "content": weather}
    ]},
]

# 4) Claude trả lời cuối
followup = client.messages.create(
    model="claude-opus-5-5", max_tokens=1024,
    tools=tools, messages=messages,
)
Ba lỗi format khiến request bị 400
  1. Chèn message vào giữa — block tool_result phải nằm ngay sau block tool_use tương ứng, không có message nào xen vào.
  2. Đặt text trước tool_result — trong message user chứa kết quả, các block tool_result phải đứng đầu mảng content; text (nếu có) đứng sau.
  3. Quên tool_use_id — mỗi kết quả phải mang đúng id của lời gọi. Khi Claude gọi song song nhiều tool, đây là thứ giữ cho kết quả không bị gán nhầm.

Gặp lỗi kiểu "tool_use ids were found without tool_result blocks immediately after" thì kiểm tra đúng ba điều trên.

Điều khiển việc gọi tool bằng tool_choice

Giá trịNghĩa
autoClaude tự quyết định gọi hay không. Mặc định khi có tools.
anyBắt buộc dùng một trong các tool đã khai báo, nhưng không ép tool nào cụ thể.
toolÉp dùng đúng một tool: {"type": "tool", "name": "get_weather"}.
noneKhông cho dùng tool. Mặc định khi không có tools.

Trong auto còn có disable_parallel_tool_use: true để giới hạn mỗi lượt chỉ một lời gọi tool.

Ép buộc không phải lúc nào cũng chạy được

Không phải model nào cũng hỗ trợ forced tool use. Trên một số model mới (ví dụ dòng Opus 5.5, Sonnet 5.5 — xem docs mới nhất), any và tool trả về lỗi 400; auto và none vẫn chạy. Cách thay thế được docs khuyến nghị: giữ auto và bật strict: true trên tool definition để đảm bảo input luôn khớp schema. Với extended thinking bật thủ công, any/tool cũng bị chặn.

Đỡ việc tay: Tool Runner

Nếu bạn không muốn tự viết vòng lặp trên, SDK có Tool Runner: nó chạy tool của bạn và tự gửi tool_result về. Dùng khi bạn cần kiểm soát tùy biến thì mới tự viết tay — xem Tool Runner.

Viết một tool đúng chuẩn

Một tool do bạn định nghĩa có bốn field (một field là tùy chọn):

FieldBắt buộc?Nội dung
nameCóTên tool. Phải khớp regex ^[a-zA-Z0-9_-]{1,128}$.
descriptionCóMô tả bằng văn xuôi: tool làm gì, khi nào nên dùng, hành vi ra sao.
input_schemaCóMột object JSON Schema mô tả tham số.
input_examplesKhôngMảng ví dụ input hợp lệ — hữu ích với tool có input phức tạp, object lồng nhau, hay tham số nhạy cảm format.

Ví dụ đầy đủ, đúng chuẩn Anthropic:

{
  "name": "get_weather",
  "description": "Get the current weather in a given location",
  "input_schema": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "The city and state, e.g. San Francisco, CA"
      },
      "unit": {
        "type": "string",
        "enum": ["celsius", "fahrenheit"],
        "description": "The unit of temperature, either 'celsius' or 'fahrenheit'"
      }
    },
    "required": ["location"]
  }
}

Tool này tên get_weather, cần một object có location (bắt buộc) và unit (tùy chọn, chỉ nhận hai giá trị). Để ý: mỗi tham số có description riêng — đó là chỗ dạy model cách điền giá trị đúng.

Description tốt vs description kém

Docs nói thẳng: description chi tiết là yếu tố quan trọng nhất quyết định hiệu năng tool. So sánh hai phiên bản cùng tên tool:

Kém

"Gets the stock price for a ticker."

Một câu ngắn, không nói khi nào dùng, trả về gì, giới hạn ra sao. Claude phải đoán — và đoán sai.

Tốt

"Retrieves the current stock price for a given ticker symbol…"

Nói rõ: ticker phải là mã hợp lệ trên NYSE/NASDAQ; trả về giá giao dịch mới nhất bằng USD; dùng khi người dùng hỏi giá hiện tại/mới nhất của một mã cụ thể; không cung cấp thông tin nào khác về công ty.

Checklist cho description (theo docs):

  • Tool làm gì.
  • Khi nào dùng — và khi nào không.
  • Mỗi tham số nghĩa là gì và ảnh hưởng thế nào tới hành vi tool.
  • Các cảnh báo / giới hạn: tool không trả về cái gì.
  • Độ dài: docs gợi ý ít nhất 3–4 câu cho mỗi tool, dài hơn nếu tool phức tạp.
Chi phí ẩn của tools

Khi bạn truyền tools, API tự dựng thêm một system prompt riêng cho tool use, và mọi thứ trong tools (tên, description, schema) đều tính là input token. Docs có bảng token riêng cho từng model — ví dụ Claude Opus 5.5 tốn 286 token cho phần system prompt này khi tool_choice là auto/none (con số thay đổi theo model — xem docs mới nhất). Client tool không phụ phí gì thêm; server tool thì có thể tính phí theo lượt dùng.

Description & selection — làm sao để model chọn đúng

Claude chọn tool dựa trên yêu cầu + description. Nghĩa là phần lớn lỗi "gọi sai tool" thực ra là lỗi thiết kế description, không phải lỗi model.

Tách hay gộp tool?

Docs khuyến nghị rõ: gộp các thao tác liên quan vào một tool ít hơn. Thay vì ba tool riêng:

create_pr   /   review_pr   /   merge_pr      ❌ ba tool gần giống nhau

hãy dùng một tool với tham số hành động:

github_pr(action: "create" | "review" | "merge", ...)   ✅ ít nhập nhằng hơn

Lý do: ít lựa chọn hơn ⇒ ít nhập nhằng hơn ⇒ bề mặt tool dễ điều hướng hơn. Nhưng đừng gộp tới mức một tool ôm cả chục việc không liên quan — gộp theo cùng một đối tượng nghiệp vụ (cùng là "pull request", cùng là "đơn hàng").

Đặt tên có namespace

Khi tool trải trên nhiều dịch vụ, hãy prefix theo dịch vụ: github_list_prs, slack_send_message. Điều này giữ cho việc chọn tool không nhập nhằng khi thư viện tool lớn dần — và càng quan trọng khi bạn dùng tool search (mục sau).

Trả về thông tin "tín hiệu cao"

Kết quả tool nên trả về định danh ngữ nghĩa, ổn định (slug, UUID) thay vì tham chiếu nội bộ khó hiểu, và chỉ gồm những field Claude cần để nghĩ bước tiếp. Response phình to vừa tốn context, vừa làm model khó rút ra điều quan trọng.

Thiếu tham số: Opus hỏi lại, Sonnet có thể đoán

Nếu prompt không đủ thông tin để điền hết tham số bắt buộc, Claude Opus có xu hướng nhận ra là thiếu và hỏi lại. Sonnet có thể hỏi — nhất là khi được nhắc suy nghĩ trước — nhưng cũng có thể tự suy ra một giá trị hợp lý. Ví dụ với tool cần location mà bạn chỉ hỏi "What's the weather?", model có thể trả về {"location": "New York, NY", "unit": "fahrenheit"}. Hành vi này không được đảm bảo, và càng mơ hồ thì càng dễ xảy ra.

⇒ Cách chống: ghi rõ trong description rằng tham số nào là bắt buộc phải có từ người dùng, đừng đoán.

Đảm bảo hình dạng input: strict: true

Thêm "strict": true vào tool definition để lời gọi của Claude luôn khớp chính xác schema — hết cảnh thiếu tham số hay sai kiểu. Đây là lựa chọn tùy chọn (optional) trên từng tool definition.

Bao nhiêu tool là quá nhiều?

Trực giác "càng nhiều tool càng mạnh" sai ở đây. Docs nêu hai vấn đề khi thư viện tool lớn dần:

Vấn đề 1 — Context

Phình context

Một setup đa server điển hình (GitHub, Slack, Sentry, Grafana, Splunk) có thể ngốn ~55k token chỉ cho định nghĩa tool — trước khi Claude làm được việc gì.

Vấn đề 2 — Accuracy

Chọn sai tăng

Khả năng chọn đúng tool của Claude bắt đầu giảm khi vượt 30–50 tool. Đây là ngưỡng thực nghiệm, không phải giới hạn cứng của API.

Cách xử lý — tool search

Thay vì nạp hết định nghĩa tool vào context, Anthropic có tool search tool: Claude tìm trong catalog tool của bạn rồi chỉ nạp những tool cần dùng.

  1. Bạn khai báo một tool search tool trong tools — hai biến thể: tool_search_tool_regex_20251119 (Claude tự dựng regex) hoặc tool_search_tool_bm25_20251119 (Claude dùng truy vấn ngôn ngữ tự nhiên).
  2. Bạn vẫn gửi toàn bộ định nghĩa tool trong tools, nhưng đặt defer_loading: true trên những tool không cần nạp trước. Ít nhất một tool — thường là chính tool search — phải để không defer.
  3. Ban đầu context chỉ có tool search + các tool không defer.
  4. Khi cần, Claude tìm; API trả về các tool_reference block (mặc định tối đa 5) và tự mở rộng thành định nghĩa đầy đủ.
  5. Claude chọn trong số tool vừa tìm được và gọi.

Docs nêu kết quả điển hình: tool search giảm hơn 85% token định nghĩa, chỉ nạp 3–5 tool cần cho mỗi yêu cầu — và giữ độ chính xác chọn tool cao kể cả với hàng nghìn tool.

Trong Claude Code thì sao?

Claude Code cũng dùng tool search để defer định nghĩa tool: chỉ tên tool và server instructions được nạp lúc bắt đầu session, nên thêm nhiều MCP server ít ảnh hưởng tới context. Claude Code không đặt trần cứng số tool mỗi server — giới hạn thực tế là ngân sách context của bạn.

Ba cách giảm số tool, xếp theo thứ tự nên thử:

  1. Bỏ tool không dùng — đơn giản nhất, hiệu quả nhất.
  2. Gộp tool cùng nghiệp vụ — như mục trước.
  3. Bật tool search — khi bạn thật sự cần cả trăm/nghìn tool.

Khi tool thất bại — is_error

Lỗi tool không phải là chuyện hiếm gặp cần giấu. Nó là một phần của giao thức: bạn báo lỗi cho Claude bằng chính block tool_result, với cờ is_error: true.

{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
      "content": "ConnectionError: the weather service API is not available (HTTP 500)",
      "is_error": true
    }
  ]
}

Claude sẽ đưa lỗi đó vào câu trả lời — kiểu: "I'm sorry, I was unable to retrieve the current weather because the weather service API is not available. Please try again later."

Viết thông điệp lỗi có ích, đừng viết "failed"

Docs khuyến nghị thẳng: thay vì lỗi chung chung, hãy nói cái gì hỏng và Claude nên thử gì tiếp. Ví dụ: "Rate limit exceeded. Retry after 60 seconds." — Claude có đủ ngữ cảnh để tự điều chỉnh thay vì đoán mò.

Tình huốngCách xử lý
Tool chạy nhưng gặp lỗi (API 500, timeout, rate limit)Gửi tool_result với is_error: true + mô tả lỗi và gợi ý bước tiếp.
Lời gọi thiếu tham số / tham số saiGửi is_error: true kèm lỗi cụ thể (ví dụ "Error: Missing required 'location' parameter"). Nếu Claude gọi tool sai, nó thường thử lại 2–3 lần với chỉnh sửa trước khi xin lỗi người dùng.
Lặp lại lỗi nhiều lầnVấn đề nằm ở description. Sửa mô tả chi tiết hơn là cách chữa gốc — hoặc dùng strict: true để lời gọi luôn khớp schema.
Server tool lỗi (web search, code execution)Bạn không phải xử lý. Claude tự xử lý và đưa ra câu trả lời thay thế.
Bảo mật: tool_result là dữ liệu không tin cậy

Kết quả tool thường mang nội dung từ bên ngoài: trang web, email, file người dùng upload, API bên thứ ba. Hãy coi đó là không đáng tin — kẻ tấn công có thể nhúng chỉ thị để lái Claude (indirect prompt injection). Giữ nội dung không tin cậy trong block tool_result, đừng đưa nó vào system prompt hay block text thường của người dùng.

Built-in tools: web search & code execution

Có những việc gần như mọi ứng dụng đều cần, và Anthropic đã làm sẵn dưới dạng server tool — code chạy trên hạ tầng Anthropic, bạn không viết handler, chỉ đọc kết quả.

Web search

Cho Claude truy cập nội dung web theo thời gian thực, trả lời được câu hỏi vượt ngoài knowledge cutoff, kèm citation nguồn.

Cách khai báo tối giản — chỉ hai field:

tools: [{ "type": "web_search_20250305", "name": "web_search" }]

Có ba phiên bản tool, mỗi bản thêm một năng lực (chuỗi version thay đổi theo thời gian — xem docs mới nhất):

VersionThêm gì
web_search_20250305Web search cơ bản.
web_search_20260209Thêm dynamic filtering: Claude tự viết và chạy code để lọc kết quả tìm kiếm trước khi chúng vào context window — giảm token cho các request tìm nhiều.
web_search_20260318Thêm điều khiển response_inclusion cho luồng agentic.

Tham số tùy chọn đáng nhớ:

  • max_uses — chặn trần số lần search mỗi request. Vượt trần thì kết quả là lỗi với mã max_uses_exceeded. Truy vấn đơn giản thường dùng 1–3 lần; nghiên cứu so sánh nhiều đối tượng có thể tới 10+.
  • allowed_domains hoặc blocked_domains — lọc domain (dùng cả hai thì API trả 400). Ghi domain trần, ví dụ example.com hoặc example.com/blog, không kèm scheme.
  • user_location — bản địa hóa kết quả: { "type": "approximate", "city": …, "region": …, "country": "US", "timezone": "America/Los_Angeles" }.

Response trả về theo ba loại block nối tiếp nhau: server_tool_use (Claude quyết định search, kèm query), web_search_tool_result (danh sách kết quả có url, title, page_age, encrypted_content), rồi text trả lời có citations.

Hai điều dễ làm sai với web search
  • Phải gửi lại encrypted_content trong hội thoại nhiều lượt. Gửi lại nguyên xi các content block như bạn nhận được; nếu field này mất hoặc bị sửa, request lỗi 400.
  • Lỗi search không làm request fail. API vẫn trả HTTP 200; lỗi nằm trong content dưới dạng object có error_code: too_many_requests, invalid_tool_input, max_uses_exceeded, query_too_long, request_too_large, unavailable. Tìm không ra kết quả thì content là mảng rỗng — đó không phải lỗi.

Giá: $10 / 1.000 lần search cộng token thông thường. Mỗi lần search tính là một lượt, bất kể trả về bao nhiêu kết quả; search gặp lỗi không bị tính tiền.

Code execution

Cho Claude chạy Bash và thao tác file trong sandbox — hoặc chạy Python để phân tích dữ liệu, tính toán, tạo biểu đồ. Công cụ mạnh nhất trong nhóm built-in khi cần xử lý dữ liệu.

tools: [{ "type": "code_execution_20250825", "name": "code_execution" }]

Hai field này cố định: type chọn phiên bản, name bắt buộc là code_execution. Khi khai báo, Claude tự có hai sub-tool: bash_code_execution (chạy shell) và text_editor_code_execution (xem/tạo/sửa file).

Lỗi của code execution trả về error_code: unavailable, execution_time_exceeded, invalid_tool_input, too_many_requests (mọi tool); thêm output_file_too_large với bash và file_not_found với text editor. Code execution miễn phí khi đi kèm web search / web fetch

Khi trong request có web_search_20260209, web_fetch_20260209 hoặc mới hơn, không có phụ phí cho code execution trong request đó ngoài tiền token (bao gồm cả code chạy sau dynamic filtering). Không có các tool đó thì tính giá code execution tiêu chuẩn.

Điểm dễ nhầm: dynamic filtering của web search chạy bên trong code execution, nhưng API tự cấp phát code execution cho request — bạn không phải tự thêm tool này vào tools.

MCP là gì — host, client, server

MCP (Model Context Protocol) là một chuẩn mở để nối ứng dụng AI với các hệ thống bên ngoài: nguồn dữ liệu, công cụ, và workflow. Cách ví von chính thức trong docs: MCP giống như cổng USB-C cho ứng dụng AI — USB-C chuẩn hóa cách nối thiết bị điện tử, MCP chuẩn hóa cách nối ứng dụng AI với hệ thống ngoài.

Vì sao cần chuẩn hóa? Không có MCP, mỗi ứng dụng AI phải tự viết cách nối cho từng dịch vụ (Jira, Sentry, Figma, database…) — nhân số tích hợp lên. Có MCP, mỗi dịch vụ viết một MCP server, và mọi client hỗ trợ MCP dùng được ngay. Docs gọi đó là "build once and integrate everywhere".

MCP Host

Ứng dụng AI

Thứ điều phối và quản lý một hoặc nhiều client. Ví dụ: Claude Code, Claude Desktop, VS Code.

MCP Client

Cầu nối tới một server

Host tạo một client cho mỗi server. Mỗi client giữ một kết nối riêng, chuyên trách với server của nó.

MCP Server

Chương trình cấp context

Cung cấp tool/dữ liệu. Có thể chạy local hoặc remote — "server" không nói tới nơi chạy.

Ví dụ

VS Code + Sentry

VS Code là host. Nó tạo một MCP client để nối tới Sentry MCP server. Nối thêm filesystem server thì tạo thêm một client nữa.

Hai tầng của MCP

TầngNội dung
Data layerGiao thức trao đổi dựa trên JSON-RPC 2.0: discovery (phiên bản + capabilities), và các primitive tools / resources / prompts / notifications.
Transport layerCơ chế truyền: stdio (tiến trình local nói chuyện qua stdin/stdout, không độ trễ mạng) và Streamable HTTP (cho server remote, hỗ trợ bearer token, API key, custom header — docs khuyến nghị OAuth để lấy token).

Tầng transport che đi chi tiết truyền thông, nên cùng một format JSON-RPC 2.0 dùng được cho cả hai kiểu transport.

Ba primitive — đừng nhầm lẫn

PrimitiveLà gìVí dụ
ToolsHàm có thể gọi để hành động (có phê duyệt của người dùng)truy vấn database, gọi API, thao tác file
ResourcesNguồn dữ liệu để đọc, cấp contextnội dung file, bản ghi database, response API
PromptsTemplate tái sử dụng để cấu trúc tương tácsystem prompt mẫu, few-shot example

Mỗi loại có method discovery (*/list) và retrieval (*/get), riêng tool có thêm tools/call để thực thi. Ví dụ một MCP server về database có thể vừa có tool để query, vừa có resource chứa schema, vừa có prompt chứa few-shot example. Danh sách này là động — client hỏi lúc chạy, không phải đọc file cấu hình cứng.

Local hay remote — chỉ khác transport

Local (thường dùng stdio): host khởi chạy server như một tiến trình con trên máy bạn. Phù hợp với thứ cần chạm tài nguyên máy — filesystem, browser, socket database. Thường phục vụ một client.

Remote (Streamable HTTP): server chạy trên nền tảng của nhà cung cấp, thường phục vụ nhiều client. Ví dụ Sentry MCP server.

Cảnh báo bảo mật — đọc trước khi nối bất cứ server nào

Docs của Claude Code nói rõ: hãy kiểm tra độ tin cậy của server trước khi nối. Server lấy nội dung từ bên ngoài có thể khiến bạn gặp rủi ro prompt injection. Một MCP server là mã chạy trên máy bạn (stdio) hoặc một bên thứ ba nhận dữ liệu của bạn (HTTP) — đối xử với nó như đối xử với một dependency.

Viết MCP server tối giản & nối vào Claude Code

Phần này dùng đúng cú pháp từ quickstart của MCP. Bạn sẽ thấy viết một MCP server không khó hơn viết vài hàm Python.

Chuẩn bị

  • Python 3.10 trở lên, và MCP Python SDK 2.0.0+.
  • uv để tạo project và chạy. Trên Windows: powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex" rồi mở lại terminal.
uv init weather
cd weather
uv venv
.venv\Scripts\activate        # macOS/Linux: source .venv/bin/activate
uv add mcp[cli]
new-item weather.py           # macOS/Linux: touch weather.py

Server tối giản

Ý tưởng cốt lõi: tạo một instance MCPServer, rồi decorate hàm của bạn bằng @mcp.tool(). SDK dùng type hints và docstring để tự sinh tool definition — bạn không phải viết JSON schema tay.

from mcp.server import MCPServer

mcp = MCPServer("tickets")

@mcp.tool()
async def get_ticket(ticket_id: str) -> str:
    """Get a support ticket by its ID.

    Args:
        ticket_id: Ticket ID, e.g. SUP-1042
    """
    return lookup_ticket(ticket_id)

if __name__ == "__main__":
    mcp.run(transport="stdio")

Chạy thử: uv run weather.py — server sẽ lắng nghe message từ MCP host.

Quy tắc số một với server stdio: đừng in ra stdout

Với server dùng transport stdio, tuyệt đối không viết ra stdout — print() trong Python mặc định ghi vào stdout và sẽ làm hỏng các message JSON-RPC, khiến server chết. Dùng module logging chuẩn (ghi vào stderr):

import logging
logger = logging.getLogger(__name__)

# ❌ Bad (STDIO)
print("Processing request")

# ✅ Good (STDIO)
logger.info("Processing request")   # ghi vào stderr

Với server HTTP thì log ra stdout không sao, vì nó không can thiệp vào HTTP response.

Ví dụ đầy đủ trong quickstart còn có một server thời tiết với hai tool get_alerts(state) và get_forecast(latitude, longitude), gọi API của National Weather Service — đáng đọc để thấy cách xử lý lỗi và format kết quả trả về cho model.

Nối vào một host: ví dụ Claude Desktop

Host đọc danh sách server trong key mcpServers của file cấu hình. Trên Windows, file đó ở $env:AppData\Claude\claude_desktop_config.json:

{
  "mcpServers": {
    "weather": {
      "command": "uv",
      "args": [
        "--directory",
        "C:\\ABSOLUTE\\PATH\\TO\\PARENT\\FOLDER\\weather",
        "run",
        "weather.py"
      ]
    }
  }
}

Lưu ý: đường dẫn phải là đường dẫn tuyệt đối; trên Windows dùng \\ hoặc / trong JSON. Có thể cần ghi full path tới uv (tìm bằng where uv).

Nối vào Claude Code

Claude Code có CLI riêng để quản lý MCP server. Ví dụ chính thức — nối server docs của Claude Code (hosted, không cần auth):

# 1. Thêm server (chạy trong terminal, KHÔNG phải trong phiên claude)
claude mcp add --transport http claude-code-docs https://code.claude.com/docs/mcp

# 2. Kiểm tra kết nối
claude mcp list

# 3. Dùng trong phiên
claude
> Use the claude-code-docs server to look up what MCP_TIMEOUT does

# 4. Gỡ khi không dùng nữa
claude mcp remove claude-code-docs

Các phần của lệnh claude mcp add:

  • claude mcp add — đăng ký server với Claude Code.
  • --transport http — server hosted ở một URL, không chạy local. (Với server local, không cần flag này: transport mặc định là stdio.)
  • claude-code-docs — tên bạn tự đặt; dùng để gắn nhãn tool và để tham chiếu trong các lệnh khác.
  • URL — nơi server được host.

Thêm một server local bằng stdio — chú ý dấu -- phân tách option của Claude Code với lệnh chạy server:

claude mcp add playwright -- npx -y @playwright/mcp@latest

Mọi thứ sau -- được truyền nguyên vẹn cho server. Nếu không có --, Claude Code sẽ cố parse các flag của server (như --port) thành option của chính nó.

Scope — server sống ở đâu

ScopeFileAi dùng được
local (mặc định)~/.claude.json, trong entry của project nàyChỉ bạn, chỉ project này

Đổi scope = gỡ entry rồi thêm lại ở scope mới, ví dụ claude mcp add --scope user --transport http claude-code-docs https://code.claude.com/docs/mcp. Trong phiên làm việc, gõ /mcp để xem và quản lý server đã thêm.

Hai con số vận hành cần nhớ
  • Mỗi server nối vào đều chiếm context, vì tên tool và server instructions được nạp vào mọi session. Gỡ server không dùng là cách giữ context sạch.
  • Output của tool MCP bị giới hạn. Claude Code cảnh báo khi output vượt 10.000 token và mặc định cắt ở 25.000 token. Muốn nâng: đặt biến môi trường MAX_MCP_OUTPUT_TOKENS (ví dụ 50000), hoặc server tự khai báo annotation anthropic/maxResultSizeChars.

Với server stdio, Claude Code còn set biến CLAUDE_PROJECT_DIR trong môi trường của server để nó resolve đường dẫn theo project mà không phụ thuộc thư mục làm việc.

Tên tool khi đã nối

Tool từ MCP server xuất hiện với tên dạng mcp__<server>__<tool> — ví dụ mcp__github__list_prs. Nếu server được đóng gói trong một plugin, tên dài hơn: mcp__plugin_<plugin>_<server>__<tool>. Bạn dùng tên đầy đủ này khi viết permission rule, hook matcher, hay khai báo tool cho subagent.

MCP hay tool trực tiếp?

Cả hai cuối cùng đều thành tool trong tools của request — model không phân biệt. Khác biệt nằm ở ai viết, ai bảo trì, và ai dùng lại được.

Một lựa chọn thứ ba đáng biết: MCP connector của Claude API cho phép nối tới các MCP server remote ngay từ Messages API, không cần tự viết MCP client — hữu ích khi bạn muốn dùng server có sẵn mà không muốn dựng hạ tầng client.

Quy tắc chọn nhanh
  1. Một app, vài tool, không ai khác dùng → tool trực tiếp. Ít bộ phận chuyển động hơn.
  2. Nhiều client hoặc nhiều team cùng cần → MCP server. Viết một lần, dùng ở nhiều host.
  3. Cần chạm tài nguyên máy (filesystem, browser, DB socket) → MCP server local qua stdio.
  4. Cần thông tin web có citation, hoặc tính toán trong sandbox → đừng viết gì cả, dùng built-in tool.

Hiểu lầm thường gặp

  1. "Khai báo tool xong là Claude tự chạy tool." — Không, với client tool. Claude chỉ đề nghị: nó trả về block tool_use và dừng với stop_reason: "tool_use". App của bạn phải chạy hàm thật rồi gửi tool_result. Không gửi thì hội thoại đứng yên. Chỉ server tool mới do hạ tầng Anthropic chạy.
  2. "description chỉ là chú thích cho người đọc." — Đây là field ảnh hưởng lớn nhất tới hiệu năng tool. Claude quyết định gọi tool nào dựa trên yêu cầu người dùng và description; một câu mơ hồ kiểu "Gets the stock price for a ticker." khiến model đoán mò. Docs khuyến nghị 3–4 câu mỗi tool, nói rõ cả khi nào không nên dùng.
  3. "Càng nhiều tool càng tốt." — Sai theo hai hướng: định nghĩa tool tốn input token (một setup 5 server có thể ngốn ~55k token), và độ chính xác chọn tool giảm khi vượt 30–50 tool. Cách chữa: bỏ tool thừa, gộp tool cùng nghiệp vụ, hoặc bật tool search.
  4. "Tool trả lỗi là hỏng cả phiên." — Không. Lỗi là một phần của giao thức: gửi tool_result với is_error: true kèm mô tả có ích ("Rate limit exceeded. Retry after 60 seconds.") để Claude tự điều chỉnh. Với lỗi tham số, Claude còn thử lại 2–3 lần trước khi bỏ cuộc.

Thực hành — tự làm, tự kiểm

Làm ra nháp trước rồi mới mở đáp án. Đáp án là gợi ý về cách lập luận — không cần khớp từng chữ.

A1 · Viết definition cho tool refund_order

Bối cảnh: bạn làm app CSKH. Cần một tool để hoàn tiền cho một đơn hàng cụ thể. Viết đầy đủ name, description, input_schema.

Ràng buộc để tự kiểm:

  • Tên tool khớp regex ^[a-zA-Z0-9_-]{1,128}$.
  • Description nói rõ: làm gì, khi nào dùng, khi nào KHÔNG (gợi ý: khách chỉ hỏi chính sách hoàn tiền thì không gọi tool này), tham số nghĩa là gì, giới hạn.
  • Tham số: order_id (bắt buộc), reason (tùy chọn, chỉ nhận vài giá trị), amount (tùy chọn, hoàn một phần).
  • Có additionalProperties: false và (tuỳ chọn) strict: true.

      "amount": {
        "type": "number",
        "description": "Partial refund amount in store currency. Omit to refund the full order."
      }
    },
    "required": ["order_id"],
    "additionalProperties": false
  },
  "strict": true
}

Checklist tự kiểm: tên đúng regex? description ≥ 3 câu và có cả "khi nào không"? tham số có enum thay vì chuỗi tự do? required chỉ gồm những gì thật sự bắt buộc? Có mô tả giới hạn (không đổi phương thức thanh toán, không refund hai lần) để Claude không hứa quá với khách?

A2 · Viết message tiếp theo cho hai tình huống

Bạn gửi request với tools gồm get_weather. Claude trả về:

{
  "stop_reason": "tool_use",
  "content": [
    { "type": "text", "text": "Let me check that for you." },
    { "type": "tool_use",
      "id": "toolu_01A09q90qw90lq917835lq9",
      "name": "get_weather",
      "input": { "location": "Ha Noi, VN" } }
  ]
}

2a. Tool chạy thành công, trả về "31°C, mưa rào". Viết message bạn gửi tiếp theo.

2b. Tool bị timeout. Viết message bạn gửi tiếp theo — và viết sao cho Claude biết nên làm gì.

Xem đáp án gợi ý

2a — luôn giữ assistant message ở giữa:

{
  "role": "user",
  "content": [
    { "type": "tool_result",
      "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
      "content": "31 degrees Celsius, heavy showers" }
  ]
}

2b — lỗi là một kết quả hợp lệ, nhưng phải hữu ích:

{
  "role": "user",
  "content": [
    { "type": "tool_result",
      "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
      "content": "TimeoutError: weather provider did not respond within 10s. Retrying immediately is unlikely to help; suggest the user try again in a few minutes.",
      "is_error": true }
  ]
}

Tự kiểm: block tool_result có đứng đầu mảng content không? tool_use_id có khớp id không? Có chèn text trước tool_result không (sai)? Và ở 2b — thông điệp lỗi có nói nên làm gì tiếp chưa, hay chỉ "failed"?

A3 · Năm quyết định thiết kế

Với mỗi tình huống, chọn phương án và giải thích một câu:

  1. Bạn có 5 tool: create_pr, review_pr, merge_pr, list_prs, get_pr. Nên giữ nguyên hay gộp?
  2. Request của bạn đang có 60 tool và Claude bắt đầu gọi nhầm. Ba cách xử lý, xếp theo thứ tự nên thử?
  3. Bạn cần một tool đọc file log trên máy dev của từng lập trình viên trong team. Dùng tool trực tiếp trong app, hay MCP server? Kiểu transport nào?
  4. Bạn cần "giá cổ phiếu mới nhất kèm nguồn" trong một web app. Tự viết tool gọi API chứng khoán, hay dùng built-in tool nào?
  5. Tool get_weather của bạn cần location, nhưng người dùng chỉ hỏi "What's the weather?". Model có thể làm gì — và bạn phòng thế nào?
Xem đáp án gợi ý
  1. Gộp ba tool hành động thành một (ví dụ github_pr(action: "create" | "review" | "merge", …)), vì chúng cùng một đối tượng nghiệp vụ và dễ gây nhập nhằng. Có thể giữ list_prs/get_pr riêng vì đó là thao tác đọc, khác hẳn về mục đích — nhưng tên nên có namespace dịch vụ (github_…).
  2. (1) Bỏ tool không dùng → (2) gộp tool cùng nghiệp vụ → (3) bật tool search với defer_loading: true cho phần lớn tool. Ngưỡng cần nhớ: chọn tool bắt đầu kém chính xác khi vượt 30–50 tool; tool search giảm >85% token định nghĩa và chỉ nạp 3–5 tool mỗi request.
  3. MCP server local, transport stdio — nó cần chạm filesystem của từng máy, và host khởi chạy nó như tiến trình con. MCP cũng cho dùng lại ở nhiều host (Claude Code, Desktop…).
  4. Dùng web search nếu cần thông tin mới kèm citation (giá $10/1.000 lần search + token); nếu chỉ cần đọc một URL cụ thể thì web fetch. Tự viết tool chỉ hợp lý khi bạn có nguồn dữ liệu riêng hoặc cần logic đặc thù.
  5. Docs nói: Opus có xu hướng nhận ra thiếu tham số và hỏi lại; Sonnet có thể hỏi, nhưng cũng có thể tự suy ra giá trị (ví dụ "New York, NY"). Phòng bằng cách ghi rõ trong description rằng location phải do người dùng cung cấp, và/hoặc bật strict: true.

Kiểm tra hiểu

Sáu câu — làm nhanh để chắc mình nắm cốt lõi.

1. Trong vòng lặp tool use với client tool, sau khi Claude trả về block tool_use, bước tiếp theo là gì?

Gợi ý: ai là bên thực thi — model hay chương trình của bạn?

Chính xác. Với client tool, Claude chỉ đề xuất: response có stop_reason: "tool_use". App của bạn chạy hàm tương ứng rồi gửi message user chứa tool_result với tool_use_id khớp id của lời gọi. Chỉ server tool mới do Anthropic chạy.

2. Với tool_choice mặc định là auto, Claude dựa vào đâu để quyết định gọi một tool?

Gợi ý: docs nói yếu tố quan trọng nhất là phần mô tả tool.

Chính xác. Claude quyết định khi nào gọi tool dựa trên yêu cầu người dùng và mô tả tool — và nó gọi khi yêu cầu khớp với khả năng được mô tả, còn câu trả lời chưa có trong context. Đây là lý do description chi tiết là "yếu tố quan trọng nhất" theo docs.

3. Tool chạy nhưng gặp lỗi. Block tool_result nên trông thế nào?

Gợi ý: lỗi là một phần của giao thức, và docs có khuyến nghị về cách viết thông điệp lỗi.

Chính xác. Lỗi được báo bằng tool_result với cờ is_error: true. Docs khuyến nghị viết thông điệp có ích — ví dụ "Rate limit exceeded. Retry after 60 seconds." — thay vì lỗi chung chung kiểu "failed". Bỏ tool_use_id là sai format và sẽ gây lỗi 400.

4. Vì sao không nên khai báo 60 tool nhỏ trong một request?

Gợi ý: docs nêu hai vấn đề — một về context, một về độ chính xác.

Chính xác. Hai vấn đề tách biệt: context bloat (một setup 5 server có thể ngốn ~55k token chỉ cho định nghĩa) và độ chính xác (khả năng chọn đúng tool giảm khi vượt 30–50 tool). 30–50 là ngưỡng thực nghiệm từ docs, không phải giới hạn cứng của API.

5. Phát biểu nào đúng về MCP host / client / server?

Gợi ý: kiến trúc MCP có host là ứng dụng AI, và mỗi server một client.

Chính xác. Host là ứng dụng AI (Claude Code, VS Code…), điều phối một hoặc nhiều client; host tạo một client cho mỗi server, mỗi client giữ kết nối chuyên trách của nó. Server là chương trình cung cấp context (tool, resource, prompt) — có thể chạy local hoặc remote.

6. Điền giá trị còn thiếu: khi Claude muốn gọi một client tool, response có stop_reason là gì?

"stop_reason": ""
