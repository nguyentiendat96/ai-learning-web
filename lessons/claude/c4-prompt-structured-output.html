Prompt engineering: bắt đầu từ đâu, khi nào đáng làm

Nhiều người hình dung prompt engineering là khéo tay thêm vài câu "thần chú" vào prompt. Tài liệu Anthropic mô tả nó như một quy trình kỹ thuật — và điều thú vị là phần quan trọng nhất lại không phải viết prompt.[1]

Ba thứ phải có trước khi viết prompt

Trang overview của Anthropic nói thẳng: hướng dẫn prompt engineering giả định bạn đã có ba thứ sau. Chưa có thì dành thời gian làm trước đã.

  1. Định nghĩa rõ success criteria — thành công nghĩa là gì, đo bằng gì.
  2. Cách kiểm chứng bằng thực nghiệm — bộ eval để chạy prompt và chấm điểm.
  3. Một prompt nháp để bắt đầu cải thiện.

Và một lưu ý tỉnh táo: không phải eval fail nào cũng nên sửa bằng prompt. Docs nói có trường hợp bạn cải thiện latency và chi phí dễ hơn bằng cách đổi model — prompt engineering không phải cây búa vạn năng.

Success criteria "tốt" trông như thế nào

Docs đưa bốn tính chất: Specific (cụ thể), Measurable (đo được), Achievable (khả thi), Relevant (liên quan tới mục đích sản phẩm). Ví dụ kinh điển từ trang develop-tests:[4]

Tiêu chí cảm xúc (sentiment)
Kém"Model phân loại cảm xúc tốt" — không đo được gì.
Tốt"Đạt F1 ≥ 0,85 trên tập held-out 10.000 tweet đa dạng; cao hơn baseline hiện tại 5%" — cụ thể, đo được, khả thi, liên quan.

Một use case thường cần đánh giá nhiều chiều cùng lúc: task fidelity, consistency, relevance & coherence, tone & style, privacy, mức dùng ngữ cảnh, latency, price. Bạn không cần cả tám — chọn chiều nào quan trọng với sản phẩm của mình.

Vòng lặp prompt engineering

Docs mô tả chu trình: test cases → prompt nháp → kiểm thử & tinh chỉnh lặp → validation cuối → ship. Ba nguyên tắc thiết kế eval đi kèm:

  • Task-specific: eval phải phản ánh phân bố input thật, gồm cả edge case (dữ liệu thiếu, input quá dài, câu hỏi mơ hồ).
  • Automate khi có thể: cấu trúc câu hỏi cho máy chấm — multiple-choice, so khớp chuỗi, chấm bằng code, hoặc LLM chấm.
  • Ưu tiên số lượng hơn chất lượng: nhiều câu với tín hiệu hơi thấp nhưng chấm tự động, tốt hơn ít câu chấm tay.
Điểm thi hay hỏi

Câu hỏi kiểu "bước đầu tiên khi cải thiện một prompt" thường có đáp án là định nghĩa tiêu chí thành công và dựng eval — không phải "thêm ví dụ" hay "thêm chữ MUST". Tương tự: "eval fail thì có nên sửa prompt không?" — không hẳn, có thể đổi model.

Bốn nguyên tắc nền — và cách đặt câu hỏi dài

Đây là bốn kỹ thuật Anthropic xếp vào nhóm "nguyên tắc chung", áp dụng cho mọi model hiện hành.[2]

1 · Rõ ràng và trực tiếp

Claude phản hồi tốt với chỉ dẫn rõ ràng, tường minh. Docs đưa cách hình dung dễ nhớ: coi Claude như một nhân viên cực giỏi nhưng mới vào công ty — không biết chuẩn mực và quy trình của bạn.

"Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too."

— Prompting best practices, "Be clear and direct"

Nếu bạn muốn hành vi "vượt xa mức cơ bản", hãy nói thẳng ra thay vì hy vọng model suy ra từ prompt mơ hồ. Ví dụ trong docs:

Kém hiệu quả

Chung chung

Create an analytics dashboard
Hiệu quả hơn

Cụ thể

Create an analytics dashboard. Include as many
relevant features and interactions as possible.
Go beyond the basics to create a fully-featured
implementation.

Hai lưu ý kèm theo: nói rõ định dạng output mong muốn và các ràng buộc; khi thứ tự hoặc tính đầy đủ của các bước quan trọng, hãy viết thành danh sách đánh số.

2 · Thêm ngữ cảnh — nói cả "vì sao"

Giải thích mục đích đằng sau chỉ dẫn giúp Claude hiểu mục tiêu và cho câu trả lời đúng hướng hơn. Claude đủ thông minh để khái quát từ lời giải thích:

Ràng buộc
KémNEVER use ellipses
TốtYour response will be read aloud by a text-to-speech engine, so never use ellipses since the text-to-speech engine will not know how to pronounce them.

Ở ví dụ thứ hai, Claude không chỉ tránh dấu ba chấm — nó hiểu vì sao, nên biết cách xử lý các trường hợp tương tự (ví dụ ký hiệu khó đọc khác) mà bạn không cần liệt kê.

3 · Cho Claude một vai trò (system prompt)

Đặt vai trò trong system hướng hành vi và giọng điệu cho cả phiên. Docs nói ngay cả một câu cũng tạo khác biệt. Đây là request body từ ví dụ chính thức:

{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "system": "You are a helpful coding assistant specializing in Python.",
  "messages": [
    {"role": "user", "content": "How do I sort a list of dictionaries by key?"}
  ]
}

Lưu ý thực chiến: các model Claude mới phản hồi với system prompt mạnh hơn các thế hệ trước. Nếu prompt cũ của bạn dùng ngôn ngữ gắt kiểu "CRITICAL: You MUST use this tool when..." để chống undertrigger, model mới có thể overtrigger — docs khuyên hạ giọng về mức bình thường ("Use this tool when...").

4 · Cấu trúc prompt bằng XML tags

Khi prompt trộn nhiều loại nội dung — chỉ dẫn, ngữ cảnh, ví dụ, dữ liệu đầu vào — XML tags giúp Claude tách bạch chúng, giảm hiểu sai. Dùng tên tag nhất quán, có nghĩa, và lồng nhau khi nội dung có cấu trúc phân cấp (nhiều document trong <documents>, mỗi cái trong <document index="n">).

<instructions>
  Tóm tắt tài liệu dưới đây thành 3 gạch đầu dòng.
</instructions>

<context>
  Người đọc là quản lý không chuyên kỹ thuật.
</context>

<document>
  {{NOI_DUNG}}
</document>

Docs nêu các tag gợi ý như <instructions>, <context>, <input> — quan trọng là tên nhất quán và mô tả đúng nội dung, không phải tên cụ thể nào.

Bonus: khi ngữ cảnh dài (20k+ token)

  • Dữ liệu dài đặt lên trên, câu hỏi/chỉ dẫn đặt gần cuối prompt. Docs ghi nhận: câu hỏi ở cuối có thể cải thiện chất lượng tới 30% trong test, nhất là với input nhiều tài liệu phức tạp.
  • Bọc từng tài liệu trong <document> với các tag con <document_content> và <source>.
  • Ground bằng trích dẫn: yêu cầu Claude trích các phần liên quan trước (ví dụ bỏ vào <quotes>), rồi mới trả lời (ví dụ trong <info>). Cách này giúp model tập trung vào nội dung đúng và bỏ qua phần còn lại.

Few-shot: dạy bằng ví dụ

Ví dụ là một trong những cách đáng tin cậy nhất để điều hướng định dạng, giọng điệu và cấu trúc output. Kỹ thuật này tên là few-shot (một vài ví dụ) hay multishot prompting.[2]

Ba phẩm chất của một ví dụ tốt

Phẩm chấtNghĩa là gìLỗi hay gặp
Relevant — sát thực tếPhản chiếu đúng use case thật của bạnLấy ví dụ đẹp trên mạng, không giống dữ liệu thật
Diverse — đa dạngBao được edge case; khác nhau đủ để model không "học vẹt" một khuôn ngoài ý muốnCả 3 ví dụ cùng một dạng câu
Structured — có cấu trúcBọc từng ví dụ trong <example>, cả cụm trong <examples>Dán ví dụ lẫn vào chỉ dẫn, model không phân biệt được đâu là luật

Bao nhiêu ví dụ? Docs khuyến nghị 3–5 ví dụ cho kết quả tốt nhất. Đây là điểm cân bằng: đủ để model bắt pattern, chưa đến mức prompt phình to và tốn token vô ích.

Một mẹo hay từ docs: bạn có thể nhờ chính Claude đánh giá bộ ví dụ của mình về độ liên quan và đa dạng, hoặc sinh thêm ví dụ từ bộ ban đầu.

Ví dụ có cấu trúc — bài toán phân loại

Yêu cầu phân loại email CSKH thành 3 nhãn. Để ý ví dụ thứ ba — nó cố tình mơ hồ, dạy model rằng "không rõ thì đừng đoán":

<examples>
  <example>
    <input>Đơn hàng #1234 giao trễ 3 ngày rồi, tôi muốn hủy.</input>
    <output>{"loai": "huy_don", "ly_do": "giao_tre"}</output>
  </example>
  <example>
    <input>Sản phẩm bị lỗi, tôi đổi sang màu khác được không?</input>
    <output>{"loai": "doi_tra", "ly_do": "loi_san_pham"}</output>
  </example>
  <example>
    <input>Ừ thì cũng được, để tôi xem lại đã.</input>
    <output>{"loai": "khac", "ly_do": "khong_ro"}</output>
  </example>
</examples>
Calibration — chọn ví dụ "sát phân bố"

Tư duy đúng: ví dụ của bạn nên là mẫu đại diện cho phân bố input thật, không phải bộ sưu tập các case hoàn hảo. Nếu thực tế 30% email mơ hồ, bộ ví dụ cũng nên có case mơ hồ — nếu không, model sẽ đoán bừa thay vì trả "khong_ro". Và nhớ: ví dụ quá giống nhau dạy model một pattern hẹp hơn bạn tưởng.

Khi làm việc với các model có thinking, một mẹo bổ sung trong docs: đặt <thinking> ngay trong ví dụ để chỉ cho Claude kiểu suy luận — model sẽ khái quát phong cách đó cho các block thinking của chính nó.

Suy nghĩ, tự kiểm — và cú đổi thay của prefill

Với bài toán cần suy luận nhiều bước, cho Claude "chỗ để nghĩ" thường quan trọng hơn thêm vài lời nhắc. Các model Claude hiện hành hỗ trợ thinking (adaptive thinking trên các model mới — Claude tự quyết định khi nào và nghĩ bao nhiêu); mức effort điều chỉnh cường độ suy nghĩ. Phần cấu hình chi tiết thuộc các bài về API/context — ở đây cần nhớ ba mẹo viết prompt.

Chỉ dẫn chung thường tốt hơn "kịch bản từng bước"

"Prefer general instructions over prescriptive steps. A prompt like 'think thoroughly' often produces better reasoning than a hand-written step-by-step plan."

— Prompting best practices, "Leverage thinking"

Lý do docs đưa ra: suy luận của Claude thường vượt xa kịch bản mà con người nghĩ trước. Viết "hãy suy nghĩ kỹ" thường tốt hơn bắt model đi đúng 5 bước bạn tự nghĩ ra.

CoT viết tay — phương án dự phòng

Khi thinking tắt, bạn vẫn có thể khuyến khích suy luận từng bước bằng cách yêu cầu Claude nghĩ qua vấn đề. Docs khuyên tách phần suy luận khỏi phần trả lời bằng tag, ví dụ thúc Claude dùng <thinking> cho lý luận và <answer> cho kết quả — nhờ vậy bạn parse được kết quả sạch.

Yêu cầu Claude tự kiểm

Mẫu trong docs: thêm vào cuối prompt câu kiểu "Before you finish, verify your answer against [test criteria]." — nêu rõ tiêu chí kiểm, không phải chỉ nói "kiểm tra lại". Cách này bắt lỗi khá chắc, đặc biệt với code và toán.

Lưu ý phiên bản: một số model mới nhất tự verify tốt mà không cần nhắc, và các câu "hãy verify" mang từ prompt cũ sang có thể gây over-verification (thừa token, chậm). Nếu đang dùng model mới nhất, thử bỏ lời nhắc này trước khi thêm — chi tiết xem trang prompting của model đó (xem docs mới nhất).

Prefill — kỹ thuật cũ đã đổi luật chơi

Prefill (prefilled response) là cách gửi kèm một phần câu trả lời của assistant để Claude viết tiếp. Nó từng được dùng cho 4 việc: ép format JSON/YAML/phân loại, bỏ preamble ("Here is the requested summary:"), né refusal không cần thiết, và nối tiếp câu trả lời bị ngắt.

Luật mới: bắt đầu từ các model Claude 4.6 (và Claude Mythos Preview), prefill ở lượt assistant cuối cùng không còn được hỗ trợ — request dùng prefill kiểu này trả về lỗi 400. Docs nói khả năng của model đã tiến bộ tới mức phần lớn use case cũ không cần prefill nữa. Việc thêm message assistant ở vị trí khác trong hội thoại thì không bị ảnh hưởng.

Mục đích cũ của prefillCách thay thế theo docs
Ép format JSON / phân loạiDùng structured outputs; phân loại thì tools với enum hoặc structured outputs
Bỏ preambleChỉ dẫn trực tiếp trong system: "Respond directly without preamble..."; hoặc XML tags / structured outputs / tool use; sót thì cắt ở post-processing
Né refusal không cần thiếtPrompt rõ ràng trong user message là đủ
Nối tiếp câu trả lời bị ngắtChuyển sang user message kèm phần cuối của câu trả lời cũ, yêu cầu tiếp tục từ đó; hoặc retry
Bẫy thi cử

"Prefill là cách chuẩn để buộc JSON" là câu trả lời sai với các model mới — vừa trả 400, vừa có thứ đúng hơn là structured outputs. Nhớ cặp đôi: prefill last-turn → 400, thay bằng output_config.format.

Tiêu chí & luật rõ ràng: từ mơ hồ đến đo được

Đây là kỹ năng lõi của domain "specific criteria & rules": biến một yêu cầu mơ hồ thành danh sách tiêu chí mà người khác đọc vào cũng kiểm được. Mục 1 đã nói về success criteria cho cả dự án; mục này nói về tiêu chí ngay trong từng prompt.

Ví dụ trước / sau

Trước — mơ hồ

Xử lý giúp tôi

Đọc email này rồi xử lý giúp tôi.

"Xử lý" là gì? Phân loại? Trả lời? Chuyển ai? Không đoán được — Claude sẽ tự chọn một nghĩa.

Sau — rõ

Có vai trò, luật, hợp đồng output

Bạn là trợ lý CSKH của một công ty
SaaS B2B.

<email>{{EMAIL}}</email>

<task>
Phân loại yêu cầu khách hàng và tóm tắt.
</task>

<rules>
1. Chỉ dùng thông tin có trong <email>.
2. Không xác định được loại -> chọn "khac",
   không đoán.
3. Nhiều yêu cầu -> ưu tiên yêu cầu ở câu đầu.
</rules>

<output_contract>
Trả về đúng 4 dòng:
loai_yeu_cau: [hoan_tien | huy_don |
  loi_ky_thuat | hoi_gia | khac]
do_khan: [cao | trung_binh | thap]
tom_tat: tối đa 25 từ, tiếng Việt
can_nguoi_xu_ly: true hoặc false
</output_contract>

Bản "sau" làm được 5 việc mà bản "trước" không có: (1) vai trò định hướng giọng điệu; (2) dữ liệu tách khỏi chỉ dẫn bằng XML; (3) luật đánh số, kể cả luật chống đoán bừa; (4) hợp đồng output với tập giá trị đóng; (5) độ dài và ngôn ngữ nói rõ. Với pipeline code, bạn còn thay được cả <output_contract> bằng structured outputs — mục 6.

Quy tắc khi viết tiêu chí

  1. Nói việc cần làm, thay vì việc cấm. Docs: thay vì "Do not use markdown", viết "Your response should be composed of smoothly flowing prose paragraphs." Chỉ dẫn khẳng định luôn dễ theo hơn danh sách cấm.
  2. Nói cả "vì sao" khi ràng buộc quan trọng. Nhớ lại ví dụ text-to-speech ở mục 2 — lý do giúp model khái quát đúng.
  3. Mỗi tiêu chí phải kiểm được. Nếu bạn không nghĩ ra cách kiểm, nó chưa phải tiêu chí — nó là mong muốn.
  4. Luật phải phủ cả trường hợp xấu. "Nếu thiếu dữ liệu → trả khong_ro" tốt hơn hy vọng model tự biết dừng.
  5. Đừng gào. Với model mới, "CRITICAL: You MUST..." có thể gây overtrigger; viết ở giọng bình thường.

Structured output: ép JSON đúng schema

Đây là phần nặng nhất của bài. Trước hết, vì sao "hãy trả JSON" không đủ? Docs liệt kê những gì bạn gặp khi không có structured outputs: lỗi parse vì JSON hỏng cú pháp, thiếu field bắt buộc, sai kiểu dữ liệu, vi phạm schema — kéo theo error handling và retry.[3]

Cách làmBản chấtĐảm bảo
"Hãy trả về JSON theo mẫu..."Lời đề nghị trong promptKhông đảm bảo gì — model có thể lệch format
output_config.format (JSON outputs)Constrained decoding: schema được biên dịch thành grammar chặn token saiJSON hợp lệ, đúng schema — "always valid, type safe"
strict: true (strict tool use)Constrained decoding cho tham số toolTên tool và input đúng schema

Structured outputs có hai tính năng bổ trợ nhau, dùng độc lập hoặc cùng lúc:

Feature 1

JSON outputs

output_config.format — kiểm soát Claude trả lời cái gì. Dùng cho trích xuất dữ liệu, báo cáo có cấu trúc, format API response.

Feature 2

Strict tool use

strict: true — đảm bảo Claude gọi hàm của bạn với tham số hợp lệ. Dùng khi schema sai gây hậu quả thật.

Cú pháp thật — JSON outputs

Schema là JSON Schema (có một số giới hạn, xem bên dưới) và được gửi trong output_config.format với type: "json_schema". Đây là body request từ ví dụ chính thức (trích xuất thông tin từ email):

{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "messages": [
    {
      "role": "user",
      "content": "Extract the key information from this email: John Smith (john@example.com) is interested in our Enterprise plan and wants to schedule a demo for next Tuesday at 2pm."
    }
  ],
  "output_config": {
    "format": {
      "type": "json_schema",
      "schema": {
        "type": "object",
        "properties": {
          "name": {"type": "string"},
          "email": {"type": "string"},
          "plan_interest": {"type": "string"},
          "demo_requested": {"type": "boolean"}
        },
        "required": ["name", "email", "plan_interest", "demo_requested"],
        "additionalProperties": false
      }
    }
  }
}

Claude trả về JSON hợp lệ trong text content block của response:

{
  "name": "John Smith",
  "email": "john@example.com",
  "plan_interest": "Enterprise",
  "demo_requested": true
}

Với SDK, bạn không phải tự viết JSON Schema. Ví dụ Python dùng Pydantic — docs gọi client.messages.parse() là phương pháp khuyến nghị:

from pydantic import BaseModel

class ContactInfo(BaseModel):
    name: str
    email: str
    plan_interest: str
    demo_requested: bool

response = client.messages.parse(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Extract the key information from this email: ..."}],
    output_format=ContactInfo,
)

print(response.parsed_output)

SDK tự chuyển class thành schema, gửi qua output_config.format, validate response và trả về object đã parse trong parsed_output. TypeScript có helper tương tự với Zod (zodOutputFormat).

Cú pháp thật — strict tool use

Với tool, thêm "strict": true vào định nghĩa và đảm bảo schema tuân giới hạn (nhớ additionalProperties: false):

{
  "tools": [
    {
      "name": "search_flights",
      "strict": true,
      "input_schema": {
        "type": "object",
        "properties": {
          "destination": {"type": "string"},
          "date": {"type": "string", "format": "date"}
        },
        "required": ["destination", "date"],
        "additionalProperties": false
      }
    }
  ]
}

Hai tính năng dùng cùng lúc được: JSON outputs kiểm format câu trả lời, strict tool use kiểm tham số tool — hữu ích cho agent vừa gọi hàm tin cậy vừa trả kết quả có cấu trúc.

Giới hạn của JSON Schema — phần dễ ra thi

Được hỗ trợKHÔNG hỗ trợ
Kiểu cơ bản: object, array, string, integer, number, boolean, nullSchema đệ quy (recursive)
enum (string/số/bool/null — không có kiểu phức tạp), const$ref ra ngoài (external)
anyOf, allOf (có giới hạn; allOf với $ref không được)Ràng buộc số: minimum, maximum, multipleOf
$ref, $defs, definitions (nội bộ), defaultRàng buộc chuỗi: minLength, maxLength
String formats: date-time, time, date, duration, email, hostname, uri, ipv4, ipv6, uuidRàng buộc array ngoài minItems = 0 hoặc 1
required, additionalProperties (bắt buộc đặt false cho object)additionalProperties khác false

Dùng tính năng không hỗ trợ → lỗi 400 kèm chi tiết. Regex cũng chỉ hỗ trợ tập con: có quantifier, character class, group; không có backreference, lookahead/lookbehind, \b.

Hệ quả thiết kế rất thực tế

Vì schema không có minimum/maximum, không có minLength — nghĩa là các ràng buộc giá trị phải kiểm ở code, không thể giao hết cho schema. Đây chính là cầu nối sang mục 7 (kiểm chứng ngữ nghĩa).

Vận hành: compile, cache, chi phí, thứ tự

  • Compile grammar: lần đầu dùng một schema sẽ tốn thêm độ trễ để biên dịch. Grammar được cache 24 giờ kể từ lần dùng cuối — request sau nhanh hơn nhiều.
  • Cache bị vô hiệu hóa khi: cấu trúc JSON schema đổi, hoặc tập tool trong request đổi (khi dùng kèm tool use). Đổi mỗi name/description thì không làm mất cache.
  • Tốn token hơn một chút: Claude nhận thêm một system prompt mô tả format output; đổi output_config.format cũng làm mất prompt cache của luồng hội thoại đó.
  • Thứ tự property: required trước, optional sau, theo thứ tự trong schema. Nếu thứ tự quan trọng với ứng dụng của bạn, hãy đánh dấu tất cả property là required.
  • Giới hạn độ phức tạp: tối đa 20 strict tool mỗi request, 24 tham số optional, 16 tham số dùng union type (tính gộp trên mọi schema strict của request). Vượt giới hạn ẩn có thể bị "Schema is too complex for compilation." (lỗi 400); có timeout biên dịch 180 giây. Cách hạ độ phức tạp: chỉ đánh dấu strict cho tool thật quan trọng; giảm tham số optional (chuyển thành required khi có thể).

Structured outputs đảm bảo hình thức — schema hợp lệ, đúng kiểu. Nó không đảm bảo sự thật (email có thật không), không đảm bảo phân loại đúng, không đảm bảo nghiệp vụ đúng. Giống hệt bài học "constraints ensure form, not truth" ở Bài 03 — nhưng lần này áp cho output thay vì tool call.

Kiểm chứng & retry: schema chưa đủ

Đây là phần nhiều người bỏ qua khi làm pipeline thật. Ba tầng kiểm, đi từ rẻ đến đắt:

TầngKiểm gìBằng gì
1. Hình thứcJSON parse được, đủ field, đúng kiểu; stop_reason bình thườngStructured outputs + SDK parse; kiểm refusal / max_tokens
2. Ngữ nghĩaGiá trị hợp lệ và nhất quán: enum đúng (so không phân biệt hoa thường), số nằm trong khoảng, các field khớp nhau (tổng = tổng các dòng), ngày không ở tương lai...Code của bạn — vì schema không diễn đạt được minimum/maxLength (mục 6)
3. Chất lượngCâu trả lời có thật sự đúng/đủ tốt theo tiêu chí khôngLLM-as-a-judge có rubric, hoặc người chấm cho case hiếm

Retry với feedback — pattern ghép từ hai thứ docs mô tả

Docs nói structured outputs loại bỏ phần lớn retry do vi phạm schema, nhưng vẫn khuyến nghị "implemented with retries" cho các trường hợp khó, và mô tả self-correction chain như pattern chaining phổ biến nhất. Ghép lại thành quy trình:

  1. Gọi API với output_config.format (hoặc tool strict).
  2. Kiểm tra stop_reason + parse + chạy các rule ngữ nghĩa của bạn.
  3. Nếu lỗi hình thức: gửi lại kèm mô tả lỗi cụ thể và yêu cầu sửa — tối đa N lần (N nhỏ, ví dụ 1–2).
  4. Nếu lỗi ngữ nghĩa: nói rõ field nào sai, vì sao sai (ví dụ "total_amount phải bằng tổng các dòng") — đừng chỉ nói "sai".
  5. Hết lượt retry mà vẫn lỗi: đánh dấu case vào hàng đợi người kiểm thay vì lặp vô hạn.

Chi tiết quan trọng: retry chỉ đáng làm khi input có thể cho ra kết quả đúng. Nếu model không xác định được thông tin, feedback cũng không tạo ra thông tin đó — hàng đợi người kiểm mới là đích đúng.

Multi-pass review cho output quan trọng

"Generate a draft → have Claude review it against criteria → have Claude refine based on the review. Each step is a separate API call so you can log, evaluate, or branch at any point."

— Prompting best practices, "Chain complex prompts"

Vì sao tách thành nhiều lượt gọi API thay vì một prompt dài? Vì bạn nhìn thấy được từng bước: log lại bản nháp, chấm điểm review, rẽ nhánh nếu cần. Với output quan trọng — hợp đồng, báo cáo, dữ liệu tài chính — hãy thiết kế tối thiểu 2 lượt: một lượt sinh, một lượt review theo tiêu chí, rồi refine.

Chấm bằng LLM (LLM-as-a-judge)

Docs xếp thứ tự ưu tiên phương pháp chấm: code-based (nhanh, ổn định, mở rộng tốt nhất) → người chấm (linh hoạt nhưng chậm, đắt — tránh nếu được) → LLM chấm (nhanh, linh hoạt — nhưng phải kiểm độ tin cậy trước khi mở rộng).[4] Ba mẹo cho LLM chấm:

  • Rubric chi tiết, rõ ràng: kèm luật bác bỏ, ví dụ "câu trả lời phải nhắc 'Acme Inc.' trong câu đầu tiên; nếu không, chấm thẳng là 'incorrect'."
  • Kết quả dứt khoát: bắt output 'correct'/'incorrect' hoặc thang 1–5 — đừng để chấm kiểu định tính.
  • Khuyến khích suy luận trước khi chấm: cho grader nghĩ trong <thinking>, rồi mới trả kết quả trong <result> — và bỏ phần suy luận khi lấy điểm.
Grade this answer based on the rubric:
<rubric>{{RUBRIC}}</rubric>
<answer>{{ANSWER}}</answer>
Think through your reasoning in <thinking> tags,
then output 'correct' or 'incorrect' in <result> tags.

Với bộ eval lớn, nhớ nguyên tắc ở mục 1: ưu tiên số lượng hơn chất lượng — nhiều case chấm tự động tốt hơn ít case chấm tay; và thiết kế case theo phân bố thật, gồm cả edge case.

Mẹo áp dụng vào Claude Code (skills)

Skill trong Claude Code cũng là prompt có cấu trúc: SKILL.md gồm frontmatter description (Claude dùng để quyết định khi nào load skill) + phần hướng dẫn markdown chỉ nạp khi skill được dùng.[5] Hai điểm đáng nhớ khi viết skill: (1) description nên chứa từ khóa/trigger phrase và ví dụ yêu cầu mà người dùng thật sẽ gõ — có trường when_to_use để thêm các ví dụ này; (2) muốn biết skill có hoạt động, đừng chỉ xem nó "có trigger" — hãy so sánh có skill vs tắt skill trên vài prompt thật, và đo riêng: có được gọi đúng lúc không, output có đúng ý không. (Chi tiết: docs Claude Code Skills — xem docs mới nhất.)

Xử lý output & Batch API

Xử lý output sau khi gọi

  • Parse bằng schema, đừng bằng regex cảm tính. Với structured outputs, output nằm trong text content block và khớp schema — dùng SDK parse nếu có, hoặc JSON parser + validate theo schema đã gửi.
  • Luôn đọc stop_reason trước khi dùng kết quả: refusal và max_tokens là hai cửa ngõ dẫn tới output không khớp schema (mục 6).
  • Log raw output cho các case fail — không có raw output thì không debug được retry.
  • Transform ngay sau validate: đổi tên field, tính derived value, ghi vào DB... chỉ sau khi output qua cả 3 tầng kiểm.

Batch API — chạy prompt ở quy mô lớn

Message Batches API là cách xử lý số lượng lớn request Messages bất đồng bộ: gửi cả lô đi, chờ xử lý, rồi tải kết quả về.[6] Đây là công cụ chuẩn cho large-scale evaluations — chạy một prompt trên hàng nghìn input để chấm điểm, đúng vòng lặp prompt engineering ở mục 1.

Cái bẫy: kết quả trả về dạng .jsonl nhưng thứ tự không khớp thứ tự request gửi đi. Docs nhấn mạnh: luôn khớp bằng custom_id, không bao giờ bằng vị trí dòng hay số thứ tự. Và một request fail không ảnh hưởng tới các request khác trong batch.

Bốn best practice từ docs: (1) dry-run một request đơn lẻ bằng Messages API thường trước khi đưa vào batch — tránh lỗi validation hàng loạt; (2) dùng custom_id có nghĩa; (3) chia dataset quá lớn thành nhiều batch cho dễ quản; (4) theo dõi trạng thái và có retry logic cho request fail. Batch có thể hủy giữa chừng và dữ liệu batch lưu tối đa 29 ngày — thiết kế pipeline đừng phụ thuộc vào việc kết quả còn mãi.

Hiểu lầm thường gặp

  1. "Thêm chữ MUST / CRITICAL là prompt mạnh hơn." — Các model Claude mới phản hồi với system prompt mạnh hơn thế hệ trước; ngôn ngữ gắt có thể gây overtrigger. Docs khuyên hạ về giọng thường: "Use this tool when..." thay vì "You MUST use this tool". Sức mạnh nằm ở tiêu chí rõ và ví dụ tốt, không nằm ở chữ in hoa.
  2. "Chỉ cần bảo 'hãy trả JSON' là pipeline ổn." — Đó là lời đề nghị, không phải ràng buộc. JSON có thể hỏng cú pháp, thiếu field, sai kiểu — kéo theo retry. Structured outputs (output_config.format) và strict tool use mới là cách ép schema bằng constrained decoding.
  3. "Structured outputs đảm bảo output luôn đúng." — Docs nói "schema compliance in most cases". Ba ngoại lệ: refusal, chạm max_tokens, và enum lệch hoa/thường. Và trên hết: schema không kiểm được ngữ nghĩa — giá trị hợp lệ về kiểu vẫn có thể vô nghĩa hoặc sai nghiệp vụ.
  4. "Prefill vẫn là cách chuẩn để ép format." — Với model Claude 4.6 trở lên, prefill ở lượt assistant cuối trả về lỗi 400. Cách thay thế đúng: structured outputs cho JSON/phân loại, chỉ dẫn trực tiếp cho việc bỏ preamble.

Thực hành — tự làm, tự kiểm

Làm ra nháp trước, rồi mới mở đáp án. Đáp án là gợi ý — điều quan trọng là cách lập luận.

A1 · Viết lại prompt mơ hồ

Prompt gốc: "Viết cho tôi một email trả lời khách hàng đang tức giận vì giao hàng chậm."

Hãy viết lại thành một prompt rõ ràng, dùng ít nhất 4 trong 5 thứ: vai trò (system), ngữ cảnh kèm "vì sao", tiêu chí đo được, hợp đồng output, XML tags. Nêu rõ bạn chọn giọng điệu và độ dài thế nào, và vì sao.

  • Tiêu chí có đo được không? (≤ 120 từ, kết bằng câu hỏi — kiểm được; "giọng chân thành" — không.)
  • Có ít nhất một luật chống hành vi xấu (không hứa bừa) không?
  • Nếu bạn định nói "đừng viết dài dòng" — thử đổi thành chỉ dẫn khẳng định ("tối đa 120 từ") xem có rõ hơn không?

A2 · Thiết kế schema structured output

Tác vụ: trích xuất đơn hàng từ email khách gửi. Các field cần có: ma_don (string), ngay_dat (ngày), tong_tien (số), trang_thai (một trong 4 trạng thái), danh_sach_mon (mảng các object gồm tên, số lượng, đơn giá).

Viết JSON Schema gửi trong output_config.format. Sau đó trả lời: (a) schema có bắt được so_luong ≥ 1 không? (b) có bắt được "tổng tiền = tổng các dòng" không? (c) enum cần lưu ý gì?

Xem đáp án gợi ý

Giá trị đặt vào output_config.format:

{
  "type": "json_schema",
  "schema": {
    "type": "object",
    "properties": {
      "ma_don": {"type": "string"},
      "ngay_dat": {"type": "string", "format": "date"},
      "tong_tien": {"type": "number"},
      "trang_thai": {
        "type": "string",
        "enum": ["cho_xac_nhan", "dang_giao", "da_giao", "huy"]
      },
      "danh_sach_mon": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "ten": {"type": "string"},
            "so_luong": {"type": "integer"},
            "don_gia": {"type": "number"}
          },
          "required": ["ten", "so_luong", "don_gia"],
          "additionalProperties": false
        }
      }
    },
    "required": ["ma_don", "ngay_dat", "tong_tien", "trang_thai", "danh_sach_mon"],
    "additionalProperties": false
  }
}
  • (a) Không. Schema không hỗ trợ minimum — so_luong ≥ 1 phải kiểm ở code.
  • (b) Không. Đây là ràng buộc ngữ nghĩa giữa các field — schema không diễn đạt được; kiểm ở tầng 2.
  • (c) Enum: giá trị có thể lệch hoa/thường, nên so sánh không phân biệt hoa thường và tránh đặt các giá trị chỉ khác nhau hoa/thường.
  • Kiểm thêm: additionalProperties: false có ở mọi object chưa? required đã đủ chưa? Có dùng tính năng không hỗ trợ (minLength, lookahead...) không?

A3 · Chẩn đoán & chọn đường

Với mỗi tình huống, nói: lỗi ở tầng nào (hình thức / ngữ nghĩa / chất lượng), và xử lý thế nào — retry, sửa schema, hay chuyển người kiểm? Riêng (d): chọn Batch hay API thường, vì sao?

  1. Response có đủ field, đúng kiểu, nhưng tong_tien không bằng tổng don_gia × so_luong.
  2. stop_reason: "max_tokens", JSON bị cụt giữa chừng.
  3. Một số case email mơ hồ, model chọn bừa một loại yêu cầu thay vì "khac" — trong khi bộ eval cho thấy pattern này lặp lại.
  4. Bạn cần chấm 8.000 bài luận bằng cùng một rubric, kết quả dùng để so sánh 2 phiên bản prompt; không cần kết quả trong ngày.
Xem đáp án gợi ý
  • 1 — Ngữ nghĩa. Schema không bắt được quan hệ giữa các field. Thêm rule kiểm ở code; retry với feedback cụ thể ("total_amount phải bằng tổng các dòng") 1–2 lần, sau đó chuyển người kiểm.
  • 2 — Hình thức (bị cắt). Không parse được vì output dở dang. Retry với max_tokens cao hơn — đúng hướng dẫn của docs cho trường hợp này.
  • 3 — Chất lượng + thiết kế prompt. Lỗi lặp lại có hệ thống: xem lại few-shot (thiếu ví dụ mơ hồ) và luật "không đoán". Đây là việc sửa prompt/dữ liệu, không phải retry từng case — nhưng vẫn đo lại bằng eval trước/sau (so sánh có sửa vs không sửa).
  • 4 — Batch. Khối lượng lớn, không cần kết quả ngay, chạy eval quy mô lớn — đúng use case của Message Batches API, lại rẻ 50%. Nhớ: dry-run một request trước, dùng custom_id để khớp kết quả, và tính tới hạn 24 giờ / lưu kết quả 29 ngày.

Kiểm tra hiểu

Sáu câu — làm nhanh để chắc mình nắm cốt lõi.

1. Theo tài liệu Anthropic, việc đầu tiên trước khi prompt engineer là gì?

Gợi ý: trang overview liệt kê ba thứ "phải có trước".

Chính xác. Docs yêu cầu ba thứ trước khi prompt engineer: (1) định nghĩa rõ success criteria, (2) cách kiểm chứng bằng thực nghiệm, (3) prompt nháp. Và đừng quên mặt trái: không phải eval fail nào cũng nên sửa bằng prompt — đôi khi đổi model rẻ hơn.

2. Điều nào đúng về few-shot theo docs?

Gợi ý: có một con số cụ thể trong phần "Use examples effectively".

Chính xác. Docs: "Include 3–5 examples for best results", và ví dụ cần relevant (sát use case thật), diverse (phủ edge case, tránh pattern ngoài ý muốn), structured (bọc tag để tách khỏi chỉ dẫn). Ví dụ giống hệt nhau dạy model một khuôn hẹp hơn bạn tưởng.

3. Prefill ở lượt assistant cuối với các model Claude 4.6 trở lên thì thế nào?

Gợi ý: nhớ cặp đôi "prefill last-turn → ?"

Chính xác. Từ Claude 4.6 (và Mythos Preview), prefill ở lượt assistant cuối trả về lỗi 400. Cách thay: structured outputs cho JSON/phân loại, chỉ dẫn trực tiếp để bỏ preamble, prompt rõ ràng cho refusal, và chuyển phần nối tiếp sang user message. Thêm assistant message ở vị trí khác trong hội thoại thì không bị ảnh hưởng.

4. Câu nào đúng về structured outputs?

Gợi ý: mục "Invalid outputs" trong docs structured outputs.

Chính xác. Hai tính năng độc lập — JSON outputs (output_config.format) và strict tool use (strict: true) — có thể dùng riêng hoặc cùng lúc. Constrained decoding đảm bảo hình thức trong phần lớn trường hợp, nhưng refusal, chạm max_tokens, và enum lệch hoa/thường là các ngoại lệ; ngữ nghĩa vẫn phải kiểm ở tầng code/đánh giá.

5. Batch API: làm sao khớp kết quả với request đã gửi?

Gợi ý: docs nhấn mạnh "results may not match input order".

Chính xác. Kết quả batch là file .jsonl và có thể về theo bất kỳ thứ tự nào. Luôn khớp bằng custom_id — vì vậy hãy đặt custom_id có nghĩa ngay từ đầu. Nhớ thêm: batch tối đa 100.000 request / 256 MB, phần lớn xong trong 1 giờ, hết hạn sau 24 giờ, kết quả lưu 29 ngày.

6. Điền vào chỗ trống:

Với JSON outputs, schema được gửi trong trường với type: "json_schema".
