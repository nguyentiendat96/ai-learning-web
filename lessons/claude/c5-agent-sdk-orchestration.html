Ai giữ vòng lặp — API tự viết hay Agent SDK?

Bài 02 đã chốt: an agent is a model in a loop. Bài 03 đã chốt thêm: model chỉ đề nghị gọi tool, còn harness mới là bên thực thi. Vậy harness đó — bạn tự viết, hay để ai đó viết hộ?

Tầng API: bạn tự cầm lái

Gọi thẳng Messages API (qua Client SDK), bạn phải viết toàn bộ vòng lặp. Tài liệu tool-use mô tả đúng vòng lặp đó: Claude trả về stop_reason: "tool_use" kèm một hoặc nhiều tool_use block; code của bạn chạy tool thật rồi gửi kết quả ngược lại trong tool_result — kèm đúng tool_use_id — và lặp tiếp cho đến khi model trả lời mà không gọi tool nữa.

# Vòng lặp tầng API (giản lược theo docs tool-use của Anthropic)
messages = [{"role": "user", "content": "Thời tiết San Francisco thế nào?"}]

# 1) Gọi Messages API với tools=[...]
#    Claude trả về: stop_reason = "tool_use"
#                   content = [ {type:"tool_use", id:"ABC123",
#                                name:"get_weather", input:{...}} ]

# 2) BẠN tự chạy tool thật trong ứng dụng của mình
result = get_weather("San Francisco, CA")     # "15°C, partly cloudy"

# 3) Gửi kết quả về, kèm đúng tool_use_id
messages += [
    {"role": "assistant", "content": assistant_content},
    {"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": "ABC123", "content": result}
    ]},
]

# 4) Lặp cho đến khi stop_reason KHÔNG còn là "tool_use"

Ở tầng này mọi thứ là code của bạn: parse lời gọi, validate tham số, chạy hàm, khớp kết quả, cắt tỉa ngữ cảnh, retry khi lỗi, dừng khi xong. Lợi ích là kiểm soát tuyệt đối; cái giá là bạn phải tự xây lại rất nhiều thứ mà một harness tử tế cần có. (Anthropic có thêm tool runner bản beta trong Client SDK để đỡ phần nào — xem docs mới nhất.)

Một chi tiết tài liệu nói rõ: không phải tool nào cũng chạy trong máy bạn. Client tools (tool bạn định nghĩa, cùng các tool schema do Anthropic định nghĩa như bash, text_editor) do ứng dụng của bạn thực thi. Server tools như web_search, web_fetch, code_execution chạy trên hạ tầng Anthropic — bạn thấy kết quả luôn, không phải tự chạy.

Tầng SDK: vòng lặp đã có người lo

Claude Agent SDK là thư viện (Python và TypeScript) chạy đúng vòng lặp đang vận hành Claude Code. Tài liệu mô tả vòng lặp đó gồm năm bước:

  1. Nhận prompt. Claude nhận prompt của bạn, kèm system prompt, định nghĩa tool và lịch sử hội thoại. SDK phát ra một SystemMessage subtype "init" chứa metadata của session.
  2. Đánh giá và trả lời. Claude quyết định bước kế tiếp: trả text, yêu cầu một hoặc nhiều tool call, hoặc cả hai. Mỗi content block là một AssistantMessage.
  3. Chạy tool. SDK tự chạy từng tool và thu kết quả. Mỗi tập kết quả được đưa ngược về Claude cho quyết định tiếp theo. Bạn có thể dùng hooks để chặn hoặc sửa tool call trước khi nó chạy.
  4. Lặp. Bước 2–3 lặp thành chu kỳ. Mỗi chu kỳ đầy đủ là một turn. Claude tiếp tục cho đến khi tạo ra câu trả lời không còn tool call.
  5. Trả kết quả. SDK phát ra AssistantMessage cuối cùng (chỉ text), rồi ResultMessage chứa kết quả, token usage, chi phí và session ID.
Điểm mấu chốt: một turn là gì

Trong SDK, turn là một vòng khứ hồi bên trong loop: Claude sinh output có tool call → SDK chạy tool → kết quả quay về Claude — và việc này xảy ra không cần trả quyền điều khiển về cho code của bạn. Loop dừng khi output không còn tool call.

Ví dụ từ docs: prompt "Fix the failing tests in auth.ts" diễn ra trong 4 turn — ba turn gọi tool (chạy test, đọc file, sửa + chạy lại) và một turn cuối chỉ có text. Toàn bộ hành trình đó nằm gọn trong một lần gọi query().

Dòng message — bạn nhìn thấy gì

SDK phát ra một stream message. Năm loại cốt lõi (theo docs):

MessageNghĩa
SystemMessageSự kiện vòng đời session: "init" (metadata), "compact_boundary" (sau khi nén ngữ cảnh), "informational", "worker_shutting_down".
AssistantMessagePhát ra cho từng content block trong câu trả lời của Claude — text hoặc một tool call.
UserMessagePhát ra sau mỗi lần chạy tool, mang kết quả gửi ngược về Claude (và cả input bạn stream vào giữa loop).
StreamEventChỉ có khi bật partial messages — sự kiện streaming thô (text delta, chunk input của tool).
ResultMessageKết thúc loop: text cuối, token usage, chi phí, session ID. Kiểm tra subtype để biết thành công hay chạm trần.

ResultMessage.subtype cho biết chuyện gì đã xảy ra: success (xong bình thường), error_max_turns (chạm trần số turn), error_max_budget_usd (chạm trần ngân sách), error_during_execution (lỗi giữa chừng), error_max_structured_output_retries (không ra được JSON hợp lệ sau số lần retry cấu hình). Trường result (text cuối) chỉ có ở subtype success — luôn kiểm subtype trước khi đọc.

Van an toàn: đừng để agent chạy mãi

Không đặt giới hạn thì loop chạy đến khi Claude tự thấy xong — ổn với task hẹp, nhưng có thể chạy rất lâu với prompt mở kiểu "cải thiện codebase này". Hai van chính là max_turns/maxTurns (đếm chỉ các turn có tool) và max_budget_usd/maxBudgetUsd (trần chi phí). Ví dụ trong docs: max_turns=2 ở kịch bản sửa test sẽ dừng trước bước sửa file. Ngân sách còn bao trùm cả sub-agent — tiêu của sub-agent tính vào tổng, và khi chạm trần thì không spawn thêm sub-agent được nữa.

Claude Agent SDK: là gì, khi nào dùng

Định nghĩa gọn từ docs: Agent SDK cho bạn đúng bộ tool, vòng lặp agent và cách quản lý ngữ cảnh đang vận hành Claude Code, lập trình được bằng Python và TypeScript. Cả hai SDK đóng gói kèm một binary Claude Code gốc, nên phần lớn trường hợp bạn không cần cài Claude Code riêng.

Hooks & subagents

Hooks và sub-agent

Hook chạy code của bạn tại các điểm trong vòng đời agent; sub-agent là agent con có ngữ cảnh riêng, tool riêng, model riêng.

Thêm: skills, commands và memory tự nạp từ .claude/ của project và ~/.claude/ giống hệt Claude Code — nghĩa là hạ tầng bạn đã xây cho CLI dùng lại được trong SDK.

Agent đầu tiên — code thật từ quickstart

Đây là ví dụ nguyên văn tinh thần từ quickstart (Python): một agent tự tìm và sửa bug trong utils.py.

import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, AssistantMessage, ResultMessage


async def main():
    async for message in query(
        prompt="Review utils.py for bugs that would cause crashes. Fix any issues you find.",
        options=ClaudeAgentOptions(
            allowed_tools=["Read", "Edit", "Glob"],   # tự phê duyệt các tool này
            permission_mode="acceptEdits",            # tự phê duyệt thao tác sửa file
        ),
    ):
        if isinstance(message, AssistantMessage):
            for block in message.content:
                if hasattr(block, "text"):
                    print(block.text)                 # Claude đang nghĩ/viết gì
                elif hasattr(block, "name"):
                    print(f"Tool: {block.name}")      # tool đang được gọi
        elif isinstance(message, ResultMessage):
            print(f"Done: {message.subtype}")         # kết quả cuối


asyncio.run(main())

Nhìn kỹ: bạn không hề viết vòng lặp. Bạn khai báo quyền, đưa prompt, rồi đọc stream. SDK lo phần còn lại — kể cả việc gọi Edit, chạy lại test và lặp cho đến khi xong.

Hai điều dễ quên về xác thực

Một: SDK đọc API key từ biến môi trường của process chạy agent (ANTHROPIC_API_KEY); nó không tự đọc file .env — muốn thì bạn tự nạp trước. Hai: trừ khi được Anthropic phê duyệt trước, bên thứ ba không được dùng login claude.ai hay hạn mức của claude.ai cho sản phẩm của mình — hãy dùng xác thực bằng API key như quickstart.

Orchestration: hub-and-spoke và sub-agents

Bài 06 đã dạy: đa agent chỉ thắng khi các nhánh thật sự độc lập, chuyên môn hoá có ích, và có manager đủ mạnh để tổng hợp. Claude biến mô hình đó thành một cấu trúc cụ thể: hub-and-spoke — một agent trung tâm (lead/coordinator) giao việc cho các sub-agent chuyên biệt, mỗi sub-agent chạy trong ngữ cảnh riêng và chỉ trả về kết quả cuối.

                    ┌───────────────────────────┐
                    │   LEAD (agent trung tâm)  │  giữ mục tiêu, chia việc,
                    │   ví dụ: "review PR #42"  │  tổng hợp kết quả
                    └─────────┬────────┬────────┘
                     Agent tool (ủy quyền)│
              ┌───────────────┘        └───────────────┐
              ▼                        ▼               ▼
     ┌─────────────────┐    ┌─────────────────┐   ┌─────────────────┐
     │ sub-agent: bảo  │    │ sub-agent: chạy │   │ sub-agent: docs │
     │ mật (chỉ đọc)   │    │ test (Bash)     │   │ (Write)         │
     │ Read,Grep,Glob  │    │ Bash,Read,Grep  │   │ Read,Write      │
     └────────┬────────┘    └────────┬────────┘   └────────┬────────┘
              └────────── chỉ kết quả cuối trở về hub ─────┘
                          (tool call, file đọc, log… ở lại ngữ cảnh con)

Vì sao mô hình này đáng dùng — tài liệu SDK nêu bốn lợi ích, và tôi đối chiếu với bài 06:

Lợi íchNghĩa là gìVí dụ
Context isolationMỗi sub-agent có hội thoại riêng; tool call và kết quả trung gian ở lại trong đó, chỉ thông điệp cuối trở về agent cha.Sub-agent đọc hàng chục file để tìm lỗi — ngữ cảnh chính chỉ nhận một bản tóm tắt.
ParallelizationNhiều sub-agent chạy đồng thời; việc xong theo thời gian của cái chậm nhất thay vì tổng thời gian.Ba sub-agent review style / security / test-coverage chạy cùng lúc.
Specialized instructionsMỗi sub-agent có system prompt chuyên môn riêng, không làm nhiễu prompt của agent chính.Sub-agent "database-migration" chỉ chứa kiến thức về SQL, rollback, toàn vẹn dữ liệu.
Tool restrictionsGiới hạn tool của sub-agent — vừa an toàn vừa đỡ tốn ngữ cảnh vì mỗi định nghĩa tool đều chiếm chỗ.Sub-agent "doc-reviewer" chỉ có Read + Grep: phân tích được nhưng không thể sửa nhầm.

Còn chi phí thì vẫn như bài 06 dạy: coordination không miễn phí, handoff là bản tóm tắt nên dễ rơi mất chi tiết, và mỗi sub-agent là thêm token. Tài liệu bổ sung vài con số vận hành cần biết: sub-agent chạy nền theo mặc định; mặc định tối đa 20 sub-agent chạy đồng thời trong một session (đổi được qua biến môi trường CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS); và sub-agent có thể tự spawn sub-agent nữa, có giới hạn độ sâu (con số cụ thể thay đổi theo phiên bản — xem docs mới nhất).

Task tool — giờ tên là Agent tool

Trong Claude Code, việc uỷ quyền diễn ra qua Agent tool. Tài liệu ghi rõ: từ phiên bản 2.1.63, Task tool được đổi tên thành Agent; các tham chiếu Task(...) cũ trong settings và định nghĩa agent vẫn hoạt động như alias. Nếu bạn gặp tài liệu cũ nói "Task tool" — đó chính là nó. Một số điểm khác cần nhớ:

  • Claude Code có sẵn các sub-agent built-in: Explore (chỉ đọc, tìm kiếm codebase), Plan (nghiên cứu để lập kế hoạch, chỉ đọc), general-purpose (làm được cả việc khám phá lẫn sửa đổi).
  • Claude có thể đặt tên cho sub-agent qua tham số name khi gọi Agent tool — tên giúp gọi lại, nhắn hoặc resume sub-agent đó sau khi nó xong.
  • Muốn cấm hẳn việc uỷ quyền: deny Agent tool trong permissions.deny, hoặc bỏ Agent khỏi danh sách tools của sub-agent đang xét (để nó không đẻ thêm sub-agent).

Định nghĩa một sub-agent — hai cách

Cách 1: khai báo trong code SDK bằng AgentDefinition (docs khuyến nghị cho ứng dụng SDK).

from claude_agent_sdk import ClaudeAgentOptions, AgentDefinition

options = ClaudeAgentOptions(
    # Tool của PHIÊN được tự phê duyệt; "Agent" ở đây là để cho phép ủy quyền
    allowed_tools=["Read", "Grep", "Glob", "Agent"],
    agents={
        "code-reviewer": AgentDefinition(
            # description: Claude dựa vào đây để biết KHI NÀO giao việc
            description="Expert code review specialist. Use for quality, security, and maintainability reviews.",
            # prompt: system prompt riêng của sub-agent
            prompt="You are a code review specialist. Identify security vulnerabilities, "
                   "check performance, verify coding standards, suggest specific improvements.",
            # tools: giới hạn quyền THẬT SỰ của sub-agent — ở đây là chỉ đọc
            tools=["Read", "Grep", "Glob"],
            model="sonnet",
        ),
    },
)

Đừng lẫn ba cái tên

Đây là chỗ đề thi rất dễ gài. Ba khái niệm khác nhau:

  • allowed_tools / allowedTools — option trên query(): danh sách tool được tự động phê duyệt cho phiên. Tool không nằm trong danh sách vẫn tồn tại; lời gọi cần phê duyệt sẽ rơi xuống permission mode rồi tới callback canUseTool.
  • disallowed_tools / disallowedTools — danh sách chặn, áp ở mọi chế độ, kể cả bypassPermissions (với rule có phạm vi như Bash(rm *)). Riêng deny theo tên trần như "Bash" thì tool bị xoá khỏi ngữ cảnh của Claude trước cả khi model kịp thấy.
  • tools / disallowedTools trong AgentDefinition hoặc frontmatter sub-agent — giới hạn thật sự bộ tool của sub-agent. Đây mới là thứ tạo ra ranh giới "chỉ đọc".

Mẹo nhớ: allowedTools là "cửa mở sẵn cho ai qua", tools của sub-agent là "phát cho nhân viên đúng chùm chìa khoá họ được dùng".

Phiên bản "managed" của hub-and-spoke

Nếu chọn Managed Agents (beta), orchestration được khai báo ở tầng cấu hình agent: trường multiagent kiểu coordinator liệt kê danh sách agent được phép uỷ quyền. Điểm đáng nhớ từ docs: các agent chia sẻ sandbox, filesystem và credentials, nhưng mỗi agent chạy trong session thread riêng — luồng sự kiện tách biệt ngữ cảnh, có lịch sử hội thoại riêng. Thread bền: coordinator có thể gửi follow-up cho agent đã gọi từ trước và agent đó vẫn nhớ các turn cũ. Docs cũng gọi tên ba pattern hợp với multi-agent: parallelization (fan-out việc độc lập rồi tổng hợp), specialization (agent chuyên miền), và escalation (nhờ agent/model mạnh hơn cho một số subtask khó) — escalation bạn sẽ gặp lại ở mục 8.

Ràng buộc: code hay prompt?

Đây là một trong những câu hỏi thi quan trọng nhất của chủ đề orchestration: muốn agent bị ràng buộc thì viết vào prompt hay viết vào code? Nguyên tắc gọn: prompt nói ý định; code bảo đảm hành vi. Model có thể bỏ qua hoặc quên một câu trong prompt; nó không thể vượt qua một deny rule hay một hook chặn — vì những thứ đó chạy ngoài model.

Thứ tự đánh giá quyền — bản đồ để chọn chỗ đặt ràng buộc

Khi Claude xin gọi một tool, SDK kiểm tra theo đúng sáu bước sau (theo docs permissions):

  1. Hooks. Chạy trước tiên. Hook có thể chặn thẳng lời gọi. Một hook trả allow không bỏ qua các bước deny/ask phía sau — chúng vẫn được đánh giá.
  2. Deny rules. Khớp là chặn, kể cả trong bypassPermissions. Deny theo tên trần (như Bash) xoá tool khỏi ngữ cảnh; deny có phạm vi (như Bash(rm *)) được kiểm ở bước này.
  3. Ask rules. Khớp là rơi xuống callback canUseTool để hỏi, kể cả trong bypassPermissions.
  4. Permission mode. Chế độ hiện hành quyết định: acceptEdits tự duyệt thao tác sửa file, plan không tự duyệt ghi file, bypassPermissions duyệt gần hết (trừ các critical path), dontAsk từ chối thay vì hỏi…
  5. Allow rules. Khớp là duyệt luôn. Có những lời gọi được duyệt sẵn không cần rule, ví dụ đọc file trong working directory.
  6. Callback canUseTool. Không bước nào giải quyết thì mới tới đây — code bạn tự quyết. Ở mode dontAsk, bước này bị bỏ qua và lời gọi bị từ chối.
Ba sự thật quyết định thiết kế
  • Deny và hook thắng tất cả. Hook deny áp dụng kể cả trong bypassPermissions. Muốn kiểm tra chạy trên mọi tool call — dùng PreToolUse hook, đừng trông vào canUseTool.
  • Tool được auto-approve không bao giờ tới canUseTool. Nếu bạn đặt logic kiểm tra ở callback này nhưng tool đã được allow rule duyệt trước, logic của bạn bị bỏ qua trong im lặng.
  • Prompt không phải hàng rào. "Tuyệt đối không sửa file .env" viết trong system prompt là lời dặn, không phải khoá. Khoá thật là rule/hook.

Đối chiếu bài 06 — "global constraints"

Bài 06 dạy: ràng buộc toàn cục (ngân sách, thời gian, chính sách) phải do manager giữ, không đẩy xuống worker. Ở tầng Claude, điều đó nghĩa là: đặt ngân sách ở maxBudgetUsd của phiên (bao trùm cả sub-agent), đặt chính sách ở hook/rule cấp phiên — chứ đừng chỉ dặn từng sub-agent bằng prompt.

Hooks & triggers: tự động hoá ở điểm móc

Hook là hàm callback chạy khi có sự kiện trong vòng đời agent: tool sắp được gọi, tool vừa trả kết quả, session bắt đầu, agent dừng… Chúng chạy trong process ứng dụng của bạn, không nằm trong ngữ cảnh của model — nên không tốn context, và có thể rút ngắn vòng lặp: một PreToolUse từ chối khiến tool không chạy, Claude chỉ nhận thông báo bị từ chối.

Các hook thường dùng (theo docs SDK):

HookKích hoạt khiDùng để
PreToolUseTrước khi tool chạy (chặn/sửa được)Validate input, chặn lệnh nguy hiểm
PostToolUseSau khi tool trả kết quảAudit output, kích hoạt tác dụng phụ
UserPromptSubmitKhi prompt được gửi điBơm thêm ngữ cảnh vào prompt
StopKhi agent kết thúcKiểm tra kết quả, lưu trạng thái session
SubagentStart / SubagentStopSub-agent khởi động / hoàn tấtTheo dõi, gom kết quả các task song song
PreCompactTrước khi nén ngữ cảnhLưu trữ transcript đầy đủ trước khi tóm tắt

Danh sách đầy đủ có thêm PostToolUseFailure, PermissionRequest, SessionStart, SessionEnd, Notification, TaskCompleted… (một số chỉ có ở TypeScript SDK — xem docs mới nhất). Ngoài callback trong code, SDK còn nạp được hook dạng shell command từ file settings khi bật settingSources.

Ví dụ: chặn ghi vào .env bằng code, không bằng lời dặn

Ví dụ nguyên mẫu từ docs hooks — tôi rút gọn phần khung, giữ nguyên logic:

async def protect_env_files(input_data, tool_use_id, context):
    file_path = input_data["tool_input"].get("file_path", "")
    if file_path.split("/")[-1] == ".env":
        return {
            "hookSpecificOutput": {
                "hookEventName": input_data["hook_event_name"],
                "permissionDecision": "deny",
                "permissionDecisionReason": "Cannot modify .env files",
            }
        }
    return {}   # trả object rỗng = cho qua


options = ClaudeAgentOptions(
    # matcher lọc hook: chỉ chạy với Write|Edit
    hooks={"PreToolUse": [HookMatcher(matcher="Write|Edit", hooks=[protect_env_files])]}
)

Khi chạy, Claude thử tạo .env, hook từ chối, và câu trả lời cuối của Claude giải thích rằng nó không thể tạo file .env. Điểm đáng chú ý: ranh giới nằm ở code — kể cả model bị "dụ" bởi prompt injection cũng không qua được hook.

Còn "triggers" thì sao?

Nếu hook là "làm gì đó khi agent đang chạy", thì trigger là "khởi động agent khi có sự kiện". Claude Code có các cơ chế như routines — chạy theo lịch, kích hoạt qua API call, hoặc phản ứng với sự kiện GitHub, từ hạ tầng cloud; scheduled tasks trên desktop chạy theo lịch định kỳ; và GitHub Actions / GitLab CI để chạy Claude trong pipeline. Ba thứ này thuộc nhóm tính năng đang tiến hoá nhanh — dùng chúng để gọi agent, rồi để hook canh chừng agent bên trong. (xem docs mới nhất: routines, scheduled-tasks, github-actions.)

Phân vai cho gọn
  • Trigger — khi nào bắt đầu một phiên (lịch, sự kiện, webhook).
  • Permission rule / hook — điều gì được phép xảy ra trong phiên (cứng, ngoài model).
  • Prompt / CLAUDE.md — nên hành xử thế nào khi mọi thứ hợp lệ (mềm, trong model).

Fixed hay dynamic decomposition?

Bài 06 đã phân biệt ba mức cam kết: workflow cố định → plan-then-execute → replan. Ở tầng Claude, câu chuyện tương tự nhưng có thêm một lựa chọn mới: để chính Claude viết harness cho task thay vì bạn viết trước.

Fixed (static) — bạn viết quy trình trước

Bạn tự chia việc và mã hoá quy trình bằng Agent SDK (hoặc claude -p): tuần tự gọi agent A, fan-out cho B/C/D, tổng hợp bằng E. Ưu điểm: rẻ, dễ đoán, dễ test, tái dùng. Nhược điểm nằm ở chính ưu điểm: vì phải đúng cho mọi trường hợp, pipeline thường phải chung chung. Blog Anthropic mô tả đúng điểm này: static workflow "phải chạy được cho mọi edge case", nên nó generic.

Dynamic — Claude tự viết harness khi chạy

Với dynamic workflows (tính năng khá mới của Claude Code — xem docs mới nhất), Claude viết một file JavaScript orchestrate các sub-agent ngay lúc chạy, may đo cho đúng task trước mắt:

workflow.js  (Claude viết ra trong lúc chạy)
├─ agent(prompt, opts)   → sinh một subagent (chọn được model, isolation)
├─ parallel([...])       → fan-out nhiều agent rồi chờ tất cả
└─ pipeline(items, ...)  → chảy từng item qua các bước

(ví dụ prompt: "dùng workflow kiểm chứng từng claim kỹ thuật
 trong bản nháp này với codebase — tôi không muốn ship thứ gì sai")

Blog nêu ba chế độ thất bại mà cách này nhắm khắc phục — đọc kỹ vì đây là chất liệu thi tốt:

Chế độ thất bạiNghĩa
Agentic lazinessDừng trước khi xong task nhiều phần rồi tuyên bố hoàn thành (ví dụ làm 35/50 mục của một buổi security review).
Self-preferential biasThiên vị kết quả của chính mình, đặc biệt khi được yêu cầu tự kiểm hay tự chấm theo rubric.
Goal driftMất dần độ trung thành với mục tiêu gốc qua nhiều turn, nhất là sau compaction — mỗi lần tóm tắt là mất mát, các ràng buộc kiểu "đừng làm X" dễ bị rơi.

Cách chữa nằm ở cấu trúc: tách nhiều sub-agent với ngữ cảnh riêng và mục tiêu hẹp, để việc kiểm tra không nằm trong cùng đầu với việc làm. Sáu pattern Claude hay ghép (theo blog):

PatternÝ tưởng
Classify-and-actAgent phân loại task rồi định tuyến tới agent/hành vi phù hợp.
Fan-out-and-synthesizeChia thành nhiều mảnh, chạy mỗi mảnh một agent, rồi tổng hợp (bước tổng hợp là barrier — chờ tất cả).
Adversarial verificationMỗi agent sinh kết quả có một agent khác phản biện/kiểm chứng độc lập.
Generate-and-filterSinh nhiều ý tưởng, lọc theo rubric/kiểm chứng, bỏ trùng, giữ cái tốt nhất.
TournamentNhiều agent cùng giải một task theo cách khác nhau; agent chấm đấu cặp chọn ra người thắng.

Tradeoff — và câu tự vấn

Dynamic workflows "thường dùng nhiều token hơn và hợp với task phức tạp, giá trị cao". Blog tự đặt câu hỏi tỉnh táo: task này có thật sự cần thêm compute không? — và tự trả lời: hầu hết task code thường ngày không cần một hội đồng 5 reviewer.

Nối với bài 06: fixed = chốt trước khi làm; dynamic = vừa làm vừa chia lại. Quy tắc ngón tay cũ vẫn đúng — chốt sớm thì nhanh, rẻ, dễ đoán; linh hoạt thì thích ứng tốt nhưng đắt và phức tạp hơn. Chọn theo giá trị của phần phản hồi thu về.

Session: continue, resume theo tên, fork

Bài 04 và bài 05 đã nói về quản lý ngữ cảnh và memory. Ở tầng SDK, cơ chế ghi nhớ có tên gọi riêng: session — và nó cũng là một task statement của blueprint: named session resume.

Định nghĩa từ docs: session là lịch sử hội thoại SDK tích luỹ trong khi agent làm việc — prompt của bạn, mọi tool call, mọi kết quả, mọi câu trả lời. SDK tự ghi ra đĩa. Quay lại session nghĩa là agent có trọn ngữ cảnh cũ: file đã đọc, phân tích đã làm, quyết định đã ra. Có một câu cần nhớ nguyên văn: Sessions persist the conversation, not the filesystem — session không phải ảnh chụp ổ đĩa; muốn hoàn tác thay đổi file phải dùng cơ chế khác (file checkpointing).

Ba động từ: continue, resume, fork

Bạn cầnDùng gì
Task một phát, không theo sauMột lần gọi query() là đủ — không cần gì thêm.
Chat nhiều lượt trong cùng một processPython: ClaudeSDKClient (tự theo dõi session). TypeScript: continue: true trên mỗi lần gọi.
Tiếp tục sau khi process khởi động lạicontinue_conversation=True (Python) / continue: true (TS) — bám session gần nhất trong thư mục hiện tại, không cần ID.
Quay lại một session cụ thể (không phải session mới nhất)resume + session ID. Bắt buộc khi có nhiều session (ví dụ mỗi user một session).
Thử hướng khác mà không phá bản gốcFork: tạo session mới, bắt đầu bằng bản sao lịch sử của session gốc; bản gốc còn nguyên.

Code tối thiểu (Python) — lấy ID rồi quay lại:

# Lần chạy 1: hứng session ID từ ResultMessage
async for message in query(prompt="Phân tích module auth và đề xuất cải tiến", options=...):
    if isinstance(message, ResultMessage):
        session_id = message.session_id      # lưu lại (DB, file…) để resume sau

# Lần chạy sau: quay lại đúng session đó
async for message in query(
    prompt="Giờ refactor nó sang JWT",
    options=ClaudeAgentOptions(resume=session_id),
):
    ...

Với TypeScript, cách "nhớ session" đơn giản nhất là continue: true — nó tự tìm session gần nhất trên đĩa, không cần bạn cầm ID. Muốn mang session sang máy khác (container, serverless), truyền thêm adapter session_store/sessionStore để SDK nhân bản transcript sang backend của bạn cho host khác resume được.

Resume theo tên — phía Claude Code CLI

Ở CLI, session còn được đặt tên. Trong phiên, gõ /rename auth-refactor; sau này quay lại đúng phiên đó bằng:

claude --continue              # mở cuộc trò chuyện GẦN NHẤT trong thư mục hiện tại
claude --resume                # mở trình chọn session
claude --resume auth-refactor  # resume thẳng session theo TÊN
claude --resume <session-id>   # resume theo ID (dùng cho session tạo bởi SDK / claude -p)

Vài chi tiết đáng nhớ:

  • Đặt tên được cả bằng /rename trong phiên, Ctrl+R trong trình chọn session, hoặc từ app/Remote Control. Khi tên bị trùng với một session đang sống, Claude Code giữ tên cho session cũ và thêm hậu tố cho session mới (ví dụ auth-refactor-grace).
  • Session tạo bởi claude -p hoặc Agent SDK bị loại khỏi trình chọn session và khỏi --continue, nhưng vẫn resume được nếu bạn truyền thẳng session ID: claude --resume <session-id>.
  • Resume khôi phục: lịch sử hội thoại (kể cả tool call/result), model đang dùng, agent (nếu chạy bằng --agent, giữ nguyên tool restrictions và model), permission mode (khi resume ở terminal), goal đang hoạt động, scheduled task chưa hết hạn. Không tự khôi phục một số flag khởi chạy như --mcp-config, --settings, --plugin-dir, --fallback-model, các thư mục --add-dir — gặp lại thì phải truyền lại. (xem docs mới nhất.)
Trạng thái dài hạn nằm ở đâu?

Session giữ hội thoại, nhưng như mục 8 sẽ thấy, hội thoại có thể bị nén và mất chi tiết. Vì vậy quy tắc bền vững (style, quy ước, "đừng làm X") phải sống ở CLAUDE.md — tài liệu nói rõ: CLAUDE.md được nạp lại ở mọi request, còn chi tiết trong prompt ban đầu có thể không được giữ sau compaction.

Progressive summarization & escalation — nhập môn

Hai chủ đề này thuộc C6, nhưng bạn cần biết chúng tồn tại để hiểu vì sao các phần trên được thiết kế như vậy. Mục này chỉ ở mức nhận diện.

Progressive summarization = compaction

Ngữ cảnh không tự reset giữa các turn trong một session — system prompt, định nghĩa tool, hội thoại, input/output của tool… tất cả tích tụ. Khi cửa sổ ngữ cảnh gần đầy, SDK tự động nén (compact): tóm tắt lịch sử cũ để giải phóng chỗ, giữ lại các trao đổi gần nhất và quyết định then chốt. Khi việc đó xảy ra, stream phát ra một message type: "system", subtype "compact_boundary".

Bốn điều thực dụng quanh compaction:

  • Nó lossy. Tóm tắt thay message cũ, nên chỉ dẫn cụ thể ở đầu hội thoại có thể không còn. Quy tắc bền vững phải nằm ở CLAUDE.md (được bơm lại mỗi request).
  • Dạy nó giữ gì. Compactor đọc CLAUDE.md như mọi ngữ cảnh khác — thêm một mục kiểu "When summarizing, always preserve: mục tiêu hiện tại, file đã đọc/sửa, kết quả test, quyết định đã ra…" là tóm tắt biết giữ đúng thứ.
  • Hook để lưu vết. PreCompact chạy trước khi nén — chỗ lý tưởng để archive transcript đầy đủ.
  • Nén thủ công. Gửi /compact như một prompt string để kích hoạt theo ý muốn.

Vì sao điều này gắn với orchestration? Vì blog dynamic workflows xếp goal drift là hệ quả trực tiếp của chuỗi nén: "mỗi bước tóm tắt là mất mát". Tách việc ra nhiều sub-agent ngữ cảnh riêng chính là một cách giảm số lần phải nén một ngữ cảnh khổng lồ.

Escalation = biết khi nào cần "người giỏi hơn"

Trong tài liệu Managed Agents, escalation là một trong ba pattern multi-agent được gọi tên: consult a more capable agent or model for a subset of complex subtasks — với một phần việc con khó, đừng cố nhồi cho agent yếu; hãy hỏi agent/model mạnh hơn. Còn trong pattern triage của dynamic workflows, escalation là nhánh dành cho con người: agent đọc nội dung không tin cậy thì chỉ phân loại và tóm tắt; nếu không tự xử được thì escalate to a human.

Một dạng escalation "đời thường" bạn đã gặp ngay trong bài này: khi agent chạm trần error_max_turns, docs gợi ý resume session với giới hạn cao hơn — chuyển từ chế độ chạy tự do sang chế độ có người xem lại và nới van. C6 sẽ đào sâu: khi nào nén, khi nào tách ngữ cảnh mới, khi nào chuyển model/người.

Hiểu lầm thường gặp

Bốn hiểu lầm hay gặp nhất khi mới chuyển từ "tự viết loop" sang hệ sinh thái Claude:

  1. "Agent SDK chính là Anthropic API / Client SDK đổi tên." — Không. Client SDK cho bạn truy cập Messages API; bạn tự viết tool loop. Agent SDK là một thư viện khác: nó chạy binary Claude Code và mang sẵn vòng lặp agent, built-in tool, permissions, sessions, hooks. Chọn sai hàng trong bảng bốn lựa chọn ở mục 2 là lỗi thiết kế, không chỉ là lỗi từ ngữ.

  2. "Cứ viết 'tuyệt đối không làm X' vào prompt là an toàn." — Không. Prompt là hướng dẫn mềm; model có thể quên hoặc bị prompt injection dụ. Ràng buộc cứng nằm ở code: deny rule, hook PreToolUse, giới hạn tools của sub-agent. Và nhớ: tool được auto-approve không bao giờ tới canUseTool — đặt kiểm tra ở đó có thể bị bỏ qua trong im lặng.

  3. "Nhiều sub-agent thì luôn tốt hơn một agent." — Không. Sub-agent tách ngữ cảnh, chạy song song và chuyên môn hoá tốt — nhưng handoff chỉ là bản tóm tắt (bài 06: "handoff là bản tóm tắt" là cái bẫy), coordination tốn kém, và mỗi sub-agent là thêm token. Docs cũng nhắc dùng sub-agent như một cách giữ ngữ cảnh sạch, không phải như một nghi thức bắt buộc cho mọi task.

  4. "Resume session là khôi phục lại mọi thứ." — Không. Session lưu hội thoại, không lưu filesystem; compaction đã làm mất một phần chi tiết; và một số flag khởi chạy (MCP config, settings, plugin dir, add-dir…) không được tự khôi phục. Resume giỏi giữ mạch suy nghĩ — không phải một nút "undo" vạn năng.

Thực hành — tự làm, tự kiểm

Ba bài dưới đây làm ra nháp trước, rồi mới mở đáp án. Đáp án là gợi ý — quan trọng là cách lập luận của bạn.

Bài 1 — Chọn tầng cho đúng

Đề bài: Với mỗi tình huống, chọn công cụ phù hợp nhất — Messages API (Client SDK, tự viết loop), Agent SDK, hay Managed Agents — và nói vì sao. Nêu một rủi ro nếu chọn sai.

  1. Script nội bộ chạy trong CI: mỗi khi có PR, tự đọc diff, sửa lỗi chính tả tài liệu, chạy lại lint, rồi đăng comment. Chạy trong repo, cần quyền ghi file.
  2. Một endpoint nhỏ: người dùng gửi câu hỏi, bạn muốn model trả về JSON đúng schema cố định, không cần tool, không cần nhớ gì.
  3. Sản phẩm agent chạy 24/7: session khách hàng nằm trong sandbox do Anthropic quản lý, công ty không muốn tự vận hành hạ tầng harness.
Xem đáp án gợi ý
  • 1 — Agent SDK (hoặc chạy CLI headless claude -p với --output-format json): bài toán cần đúng thứ SDK mang sẵn — built-in tool đọc/sửa file, chạy lệnh, permission cho thao tác ghi, hook để audit. Tự viết loop bằng Messages API nghĩa là bạn phải tự xây lại mọi thứ đó. Rủi ro nếu chọn sai tầng: ước tính công sức sai và tự tạo lỗ hổng ở phần tool/permission.
  • 2 — Messages API (Client SDK): một lượt, không tool, không session — vòng lặp agent là thừa. Nếu cần JSON đúng schema, dùng structured output của API. Rủi ro nếu chọn sai: kéo cả harness nặng vào cho một việc một phát, tăng độ trễ, chi phí và bề mặt lỗi.
  • 3 — Managed Agents: đúng định nghĩa "Anthropic host agent, cấu hình qua Claude API" — harness chạy sẵn, session trong sandbox managed (hoặc self-hosted sandbox nếu cần). Lưu ý đây là beta (xem docs mới nhất). Rủi ro nếu chọn sai: tự vận hành hạ tầng session/sandbox là việc lớn không tạo giá trị trực tiếp.

Bài 2 — Thiết kế hub-and-spoke cho một buổi review

Đề bài: Bạn cần review một PR lớn gồm 3 phần: (a) thay đổi xác thực, (b) migration database, (c) tài liệu API. Hãy:

  1. Vẽ sơ đồ hub-and-spoke: lead + 3 sub-agent.
  2. Viết cho mỗi sub-agent một dòng description và danh sách tools giới hạn hợp lý.
  3. Phần nào chạy song song được, phần nào phải chờ? Bước tổng hợp do ai làm?
  4. Dự đoán một chi tiết có thể mất khi handoff, và cách giữ nó.
Xem đáp án gợi ý 
                    ┌──────────────────────────────┐
                    │ LEAD: "review PR #42, tổng   │
                    │ hợp thành báo cáo cuối"      │
                    └──────┬─────────┬─────────┬───┘
                 ┌─────────┘         │         └─────────┐
                 ▼                   ▼                   ▼
        ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
        │ security-review │ │ migration-review│ │ docs-review     │
        │ Read,Grep,Glob  │ │ Read,Grep,Bash  │ │ Read,Grep       │
        │ (chỉ đọc)       │ │ (chạy EXPLAIN…) │ │ (chỉ đọc)       │
        └─────────────────┘ └─────────────────┘ └─────────────────┘
                    3 kết quả độc lập → lead tổng hợp
  • Descriptions: security — "Reviews authentication and authorization changes for security issues. Read-only."; migration — "Reviews database migrations for correctness, rollback safety, and data integrity. Read-only, may run read-only DB commands."; docs — "Checks API documentation against the code changes. Read-only."
  • Tools: cả ba không có Write/Edit. Chỉ migration-review có Bash (và chỉ nên là lệnh đọc). Đây là ranh giới cứng — đừng chỉ dặn trong prompt.
  • Song song: ba review độc lập chạy đồng thời; bước tổng hợp là barrier — lead chờ cả ba rồi mới viết báo cáo (giống fan-out-and-synthesize).
  • Handoff mất gì: evidence thô — số dòng, đoạn log, trích dẫn file — vì sub-agent chỉ trả thông điệp cuối. Cách giữ: yêu cầu kết quả có trích dẫn file:line cụ thể trong bản tóm tắt, hoặc cho sub-agent ghi bằng chứng ra file trong repo để lead đọc khi cần.

Bài 3 — Enforcement hay prompt?

Đề bài: Mỗi yêu cầu sau nên thực hiện bằng code hay prompt? Nêu cơ chế cụ thể (rule, hook, option…) nếu là code:

  1. Không bao giờ cho agent sửa file .env.
  2. Agent luôn trả lời bằng tiếng Việt.
  3. Mỗi phiên tối đa 2 USD.
  4. Sub-agent "doc-checker" không được chạy Bash, chỉ đọc và grep.
  5. Agent nên chạy test trước khi khẳng định đã sửa xong.
Xem đáp án gợi ý
  • 1 — Code. Deny rule cho Edit/Write trên đường dẫn đó + hook PreToolUse kiểm tra file_path và trả permissionDecision: "deny". Hook chạy trước mọi bước và áp cả trong bypassPermissions.
  • 2 — Prompt. Đây là hướng dẫn mềm về phong cách — system prompt hoặc CLAUDE.md. Không có cơ chế code nào "bắt" được nội dung text trả lời một cách hợp lý (và cũng không cần).
  • 3 — Code. max_budget_usd/maxBudgetUsd; chạm trần thì SDK trả ResultMessage subtype error_max_budget_usd. Ngân sách bao cả sub-agent.
  • 4 — Code. Khai tools: ["Read", "Grep"] (frontmatter) hoặc AgentDefinition(tools=["Read","Grep"]). Không phát tool thì sub-agent không thể gọi — mạnh hơn mọi câu dặn dò.
  • 5 — Prompt (kèm code tuỳ chọn). "Test trước khi kết luận" là ưu tiên hành vi → system prompt/CLAUDE.md. Muốn siết hơn thì thêm hook Stop để kiểm tra trạng thái test trước khi cho dừng, nhưng hãy coi đó là biện pháp tăng cường, không phải mặc định cho mọi dự án.

Kiểm tra hiểu

Sáu câu — làm nhanh để chắc mình nắm cốt lõi.

1. Agent SDK khác Client SDK (Messages API) ở điểm cốt lõi nào?

Gợi ý: hỏi "ai viết vòng lặp model → tool → model?"

Chính xác. Client SDK cho bạn Messages API và bạn tự viết tool loop (nhận stop_reason: "tool_use", chạy tool, gửi tool_result, lặp). Agent SDK mang sẵn vòng lặp đó — cùng bộ tool, cách quản lý ngữ cảnh và permissions của Claude Code.

2. Trong vòng lặp của Agent SDK, một turn là gì?

Gợi ý: docs nói turn là một round trip bên trong loop và xảy ra không cần trả quyền về code của bạn.

Chính xác. Turn là chu kỳ model → tool → model. Loop tiếp tục các turn cho đến khi output không còn tool call. Và nhớ: max_turns/maxTurns chỉ đếm các turn có dùng tool.

3. Muốn sub-agent không thể sửa file (chỉ đọc), cách nào là ràng buộc cứng đúng nhất?

Gợi ý: model chỉ có thể gọi những tool mà nó nhìn thấy.

Chính xác. Không phát tool ghi file thì sub-agent không thể gọi — đó là ranh giới thực thi được. Prompt chỉ là hướng dẫn mềm; model mạnh hay temperature thấp không thay đổi bộ tool được cấp.

4. Điều nào sau đây KHÔNG đúng về hooks trong Agent SDK?

Gợi ý: hook "rút ngắn vòng lặp" nghĩa là gì?

Chính xác. Hook không phải gợi ý — nó chạy trước mọi bước đánh giá quyền và có thể chặn thẳng; hook deny còn áp dụng cả trong bypassPermissions. Vì chạy trong process của bạn nên hook không tốn ngữ cảnh của model, và PreCompact đúng là chỗ để archive transcript.

5. Bạn muốn quay lại đúng phiên đã đặt tên auth-refactor trong Claude Code CLI. Lệnh nào đúng?

Gợi ý: --continue không nhận tên; nó chỉ mở phiên gần nhất.

Chính xác. claude --resume <name> resume thẳng phiên theo tên (đặt bằng /rename); claude --continue chỉ mở phiên gần nhất trong thư mục hiện tại. Session tạo bởi SDK hoặc claude -p không nằm trong trình chọn nhưng vẫn resume được bằng claude --resume <session-id>.

6. Điền từ còn thiếu vào câu cốt lõi của docs về session:

"Sessions persist the , not the filesystem."
