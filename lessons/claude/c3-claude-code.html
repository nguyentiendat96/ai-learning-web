Claude Code là gì — và nó chạy ở đâu

Định nghĩa gọn nhất từ docs: Claude Code là một agentic coding tool — nó đọc codebase của bạn, sửa file, chạy lệnh, và tích hợp với các công cụ phát triển xung quanh bạn. Nó không chỉ trả lời câu hỏi như chatbot; nó tự làm, tự kiểm, tự lặp cho đến khi xong việc.

Cùng một Claude Code, có bốn bề mặt chính (docs Overview):

Terminal

CLI — bản đầy đủ tính năng

Chạy claude ngay trong terminal, tại thư mục project. Cài bằng script native, Homebrew (macOS), hoặc WinGet (Windows). Đây là bản gốc — mọi tính năng đều có ở đây.

IDE

VS Code & JetBrains

Extension cho VS Code (và Cursor), plugin cho JetBrains. Có inline diff, @-mention, duyệt plan, lịch sử hội thoại ngay trong editor. Plugin JetBrains cần cài CLI riêng trước.

Desktop

Ứng dụng desktop

App riêng (macOS/Windows/Linux beta): xem diff trực quan, chạy nhiều session song song, lên lịch task định kỳ, khởi động cloud session. Đã bao gồm Claude Code, không cần cài CLI.

Web

claude.ai/code

Chạy trên browser, không cần cài gì. Hợp cho task dài: giao việc rồi quay lại xem kết quả, làm việc trên repo không có sẵn trên máy, chạy nhiều task song song.

Vài điều Claude Code làm được, theo docs:

  • Tự động hóa việc tồn đọng: viết test cho code chưa có test, sửa lỗi lint khắp project, gỡ merge conflict, cập nhật dependency.
  • Xây tính năng & sửa bug: mô tả bằng ngôn ngữ tự nhiên; Claude lập kế hoạch, viết code nhiều file, rồi kiểm chứng.
  • Commit & PR: làm việc trực tiếp với git — stage, viết commit message, tạo branch, mở PR.
  • Nối công cụ qua MCP: đọc tài liệu trên Google Drive, cập nhật ticket Jira, lấy dữ liệu Slack…
  • Tùy biến bằng instructions, skills, hooks: chính là nội dung các mục sau của bài này.
  • Chạy song song & tự động hóa: nhiều agent cùng lúc; pipe log vào, chạy trong CI, ghép với công cụ khác.
Một câu để nhớ

Claude Code = agent (model trong vòng lặp — bạn đã biết) + harness + một bộ đồ nghề built-in (đọc file, sửa file, chạy lệnh, web…). Bài này lo phần “cấu hình harness”: dạy harness biết luật của bạn, biết gọi đúng quy trình, và biết hỏi trước khi làm việc nguy hiểm.

Cấu hình phân tầng: file nào đè file nào

Claude Code đọc cấu hình từ nhiều nơi. Khi cùng một key xuất hiện ở nhiều nơi, nơi có độ ưu tiên cao hơn thắng. Đây là thứ tự từ cao xuống thấp, theo docs Settings:

#TầngFile / nguồnPhạm vi
1Managed settings (enterprise)managed-settings.json, MDM policy, hoặc server-managed settings từ claude.ai consoleTổ chức triển khai. Gần như không gì của bạn đè được (chỉ vài ngoại lệ bảo mật đặc biệt).
2Command lineFlag khi chạy claude, hoặc claude --settings <file-json>Chỉ session hiện tại.
3Project local.claude/settings.local.jsonBạn, trong đúng dự án này. Claude Code tự giữ file này ngoài git khi nó tạo file.
4Shared project.claude/settings.jsonCả nhóm — commit file này để teammate nhận cùng cấu hình.
5User~/.claude/settings.jsonBạn, cho mọi dự án trên máy.

Ví dụ đời thường: team set "model" trong .claude/settings.json là claude-sonnet-5; bạn muốn dùng Opus nên set "model": "claude-opus-5-5" trong .claude/settings.local.json. Vì local nằm trên shared project, chỉ session của bạn đổi model — teammate không bị ảnh hưởng (đúng ví dụ trong docs Settings).

Hai cái bẫy của cơ chế phân tầng

  1. Không phải “file này thay cả file kia”. Claude Code trộn theo từng key: key nào có ở tầng cao hơn thì lấy tầng đó, key nào không có thì rơi xuống tầng dưới.
  2. List thì hợp nhất, không đè. permissions.allow set ở user, project, local… sẽ được cộng dồn — mỗi file thêm mục của mình mà không xóa mục của file khác.

Trên Windows, ~/.claude nghĩa là %USERPROFILE%\.claude. Muốn biết máy mình đang bị ảnh hưởng bởi nguồn nào, chạy /status — dòng Setting sources cho biết nguồn managed nào đang áp dụng; menu /config để đổi các thiết lập thường dùng.

Câu thần chú cho đề thi

Managed > command line > project local > shared project > user. Managed chỉ nói về quyền của tổ chức; còn giữa “của bạn” và “của nhóm”, cái riêng luôn thắng cái chung.

CLAUDE.md — bộ nhớ do bạn viết

Mỗi session Claude Code bắt đầu với một context window mới tinh. CLAUDE.md là file markdown chứa chỉ dẫn bền vững: Claude đọc nó ở đầu mọi session. Docs nói thẳng vai trò của nó: hãy xem CLAUDE.md là nơi ghi lại những thứ mà nếu không có, bạn sẽ phải giải thích lại mỗi session.

Đặt ở đâu

Phạm viĐường dẫnDùng cho

Linux/WSL: /etc/claude-code/CLAUDE.md
macOS: /Library/Application Support/ClaudeCode/CLAUDE.md		Chuẩn code, chính sách bảo mật, yêu cầu tuân thủ của tổ chức.

Nó được nạp như thế nào

  • Claude Code nạp CLAUDE.md và CLAUDE.local.md từ thư mục làm việc và mọi thư mục cha ở trên. Chạy ở foo/bar/ thì nạp cả foo/CLAUDE.md lẫn foo/bar/CLAUDE.md.
  • Các file được nối vào context chứ không đè nhau: từ gốc filesystem xuống thư mục làm việc, nên file gần bạn nhất được đọc sau cùng. Trong cùng một thư mục, CLAUDE.local.md nằm sau CLAUDE.md.
  • CLAUDE.md trong các thư mục con không nạp lúc khởi động — chỉ nạp khi Claude đọc file trong thư mục đó.

Viết gì trong đó

Docs đưa một tiêu chí rất dễ nhớ: viết chỉ dẫn đủ cụ thể để kiểm chứng được. So sánh:

❌ Mô tả chung chung✅ Cụ thể, kiểm chứng được
“Format code cho tử tế”“Dùng thụt lề 2 space”
“Nhớ test thay đổi của bạn”“Chạy npm test trước khi commit”
“Giữ file có tổ chức”“API handlers nằm trong src/api/handlers/”

Ba nguyên tắc kích thước và cấu trúc:

  • Ngắn: nhắm dưới 200 dòng mỗi file. File dài ăn context và làm Claude tuân kém hơn.
  • Có cấu trúc: nhóm theo heading + bullet; Claude theo chỉ dẫn có tổ chức dễ hơn đoạn văn dày đặc.
  • Nhất quán: hai chỉ dẫn mâu thuẫn thì Claude có thể chọn đại một cái. Thỉnh thoảng chạy /doctor prompt-audit để Claude tự soi file chỉ dẫn cũ/mâu thuẫn.

Ví dụ một CLAUDE.md mẫu

Đây là file cho một dự án Node/TypeScript tưởng tượng — chú ý nó chỉ chứa thứ Claude không thể tự suy ra từ code:

# Project: acme-api

## Commands
- Install: `pnpm install`
- Dev server: `pnpm dev`
- Tests: `pnpm vitest run <file>` (chạy một file trước — full suite rất chậm)
- Typecheck: `pnpm tsc --noEmit`

## Conventions
- TypeScript strict mode; không dùng `any`.
- API handlers nằm trong `src/api/handlers/`, mỗi resource một file.
- Lỗi trả về dạng `{ code, message }`, không bao giờ trả stack trace thô.

## Workflow
- Chạy typecheck + test file vừa sửa trước khi báo xong.
- Không commit trực tiếp lên `main`; đặt tên branch `feat/…`, `fix/…`.

Vài công cụ liên quan

  • /init — để Claude phân tích codebase và sinh file CLAUDE.md khởi đầu (build commands, test, quy ước nó tìm thấy). Nếu đã có CLAUDE.md, /init gợi ý cải thiện chứ không ghi đè.
  • /context — kiểm tra file nào đã nạp, mục Memory files.
  • /memory — mở và sửa CLAUDE.md / CLAUDE.local.md / auto memory ngay trong session.
  • Import file khác bằng cú pháp @path/to/file — file được import cũng nạp lúc khởi động, tối đa 4 tầng lồng nhau.

Còn AGENTS.md?

Nếu repo của bạn đã có AGENTS.md cho các coding agent khác, Claude Code đọc trực tiếp được. Mặc định (giá trị claude-md-or-agents-md): nếu không có CLAUDE.md/CLAUDE.local.md trong thư mục làm việc hoặc phía trên, Claude dùng AGENTS.md; nếu có CLAUDE.md thì chỉ đọc CLAUDE.md. Bạn có thể đặt chế độ đọc cả hai (claude-md-and-agents-md). Mẹo an toàn cho đa nền tảng: để một dòng @AGENTS.md trong CLAUDE.md — Claude luôn đọc được, kể cả trên Windows nơi symlink hay gặp trục trặc.

Điểm quan trọng nhất của mục này

Docs nói rất rõ: CLAUDE.md được Claude coi là context, không phải cấu hình được cưỡng chế. Nó định hướng hành vi, nhưng không phải hàng rào an ninh. Muốn chặn cứng một hành động bất kể Claude quyết định gì, phải dùng hook (mục 7) hoặc permission rule (mục 8).

Auto memory — Claude tự ghi chú

CLAUDE.md là thứ bạn viết. Auto memory là thứ Claude viết: nó tự ghi lại các bài học, sở thích của bạn, và những chỉnh sửa bạn lặp đi lặp lại — để session sau không phải dạy lại.

CLAUDE.mdAuto memory
Ai viếtBạnClaude
Nội dungChỉ dẫn, quy tắcBài học, pattern, sở thích
Phạm viTheo project, user, hoặc tổ chứcTheo repository, dùng chung giữa các worktree
Nạp vào sessionMỗi session, toàn bộ fileMỗi session, 200 dòng đầu hoặc 25KB

Lưu ở đâu và gồm những gì

Mỗi project có một thư mục riêng: ~/.claude/projects/<project>/memory/. Đường dẫn <project> suy ra từ git repository, nên mọi worktree và thư mục con của cùng một repo dùng chung một thư mục memory. Trong thư mục đó:

~/.claude/projects/<project>/memory/
├── MEMORY.md           # Index — mỗi memory một dòng, nạp vào mọi session
├── user_role.md        # Một memory
├── feedback_testing.md # Một memory
└── ...                 # Claude tự tạo thêm file chủ đề

Auto memory là machine-local — không đồng bộ giữa các máy hay lên cloud; file cũng không mất theo thời hạn dọn transcript. Bạn có thể mở xem, sửa, xóa thoải mái vì nó chỉ là markdown.

Điều khiển

  • Mặc định bật. Vào /memory để bật/tắt — nó ghi key autoMemoryEnabled vào settings.
  • Tắt cho một project: đặt autoMemoryEnabled: false trong settings của project đó. Hoặc tắt hẳn bằng biến môi trường CLAUDE_CODE_DISABLE_AUTO_MEMORY=1.
  • Đổi vị trí lưu: key autoMemoryDirectory (đường dẫn tuyệt đối hoặc bắt đầu bằng ~/).
Phân biệt để không mất điểm

Khi bạn nói “remember that the API tests require a local Redis instance” — Claude lưu vào auto memory. Khi bạn muốn nó vào file quy tắc của nhóm, phải nói rõ: “add this to CLAUDE.md”.

Commands vs Skills — cùng dấu /, khác ở đâu

Đây là chỗ đề thi rất hay hỏi, và cũng là chỗ docs có tin “vỡ lòng”: custom commands đã được gộp vào skills. Một file .claude/commands/deploy.md và một skill .claude/skills/deploy/SKILL.md đều tạo ra /deploy và hoạt động giống nhau. Các file .claude/commands/ cũ vẫn chạy tiếp.

Vậy skill thêm gì so với command file?

  • Một thư mục cho file phụ trợ — tài liệu tham chiếu dài, script, template chỉ nạp khi cần.
  • Frontmatter điều khiển ai được gọi skill — bạn hay Claude, hoặc cả hai.
  • Khả năng Claude tự nạp khi thấy liên quan — dựa vào description, không cần bạn gõ /.

Cần phân biệt thêm một tầng: built-in command (như /help, /compact) chạy logic cố định; còn bundled skill (như /code-review, /debug, /doctor) là prompt có sẵn để Claude tự orchestrate bằng tools của nó. Skills của Claude Code theo chuẩn mở Agent Skills, và Claude Code mở rộng thêm: điều khiển invocation, chạy trong subagent, tiêm context động.

SKILL.md — frontmatter thật

Một skill gồm hai phần: YAML frontmatter giữa hai dấu ---, và phần markdown là chỉ dẫn. Tên thư mục (hoặc field name) thành tên lệnh; description là thứ Claude dùng để quyết định có tự nạp skill không. Đây là ví dụ nguyên bản từ docs — skill tóm tắt thay đổi chưa commit, kèm kỹ thuật dynamic context injection (!`lệnh` được chạy và thay bằng output trước khi Claude đọc skill):

---
description: Summarizes uncommitted changes and flags anything risky. Use when the user asks what changed, wants a commit message, or asks to review their diff.
---

## Current changes

!`git diff HEAD`

## Instructions

Summarize the changes above in two or three bullet points, then list any risks you notice
such as missing error handling, hardcoded values, or tests that need updating.
If the diff is empty, say there are no uncommitted changes.

Các field quan trọng nhất (đầy đủ hơn trong docs Skills):

FieldNghĩa

Ví dụ một skill “task content” chỉ bạn được gọi (ý tưởng từ docs):

---
name: deploy
description: Deploy the application to staging. Use when the user asks to ship a build.
disable-model-invocation: true
allowed-tools: Bash(pnpm run *) Bash(git status *)
---

Deploy the application:
1. Run the test suite
2. Build the application
3. Push to the deployment target

Một ưu điểm lớn về context: khác với CLAUDE.md, thân skill chỉ nạp khi được dùng — nên tài liệu tham chiếu dài gần như miễn phí cho đến lúc cần.

Viết bằng ví dụ, đừng viết bằng mô tả

Đây là nguyên tắc xuyên suốt của docs cho mọi thứ bạn viết cho Claude: CLAUDE.md, skill, prompt. Khái niệm nó muốn nói rất đơn giản: một ví dụ cụ thể đáng giá hơn ba tính từ trừu tượng, vì ví dụ chỉ cho Claude biết “đúng trông như thế nào”.

Cùng một yêu cầu, hai cách viết

Mô tả trừu tượngViết bằng ví dụ / tiêu chí
“Implement a function that validates email addresses.” “Write a validateEmail function. Example test cases: user@example.com is true, invalid is false, user@.com is false. Run the tests after implementing.” (ví dụ từ docs Best practices)
“Làm dashboard đẹp hơn.” “[dán screenshot] implement this design. Take a screenshot of the result and compare it to the original. List differences and fix them.”
“Sửa lỗi build.” “Build fails with this error: [dán lỗi]. Fix it and verify the build succeeds. Address the root cause, don't suppress the error.”

Vì sao nó hoạt động? Vì Claude dừng khi công việc “trông xong”. Nếu không có tiêu chí kiểm chứng, bạn chính là vòng kiểm tra — mọi sai sót phải đợi bạn phát hiện. Đưa ví dụ hoặc lệnh kiểm tra (test, build, lint, screenshot so sánh), vòng lặp agent tự khép kín: Claude làm → chạy kiểm tra → đọc kết quả → sửa tiếp.

Áp vào cách viết skill

  • Trong description: đặt use case chính lên đầu và kèm ví dụ yêu cầu ở when_to_use (“dùng khi user hỏi ‘what changed’, xin commit message, hoặc nhờ review diff”).
  • Nếu Claude gọi skill quá thường xuyên: docs khuyên làm description cụ thể hơn — thêm ví dụ đúng, bớt từ chung.
  • Trong thân skill: viết chỉ dẫn ở dạng hành động kiểm chứng được (“Run the tests after every edit”) thay vì mô tả mơ hồ (“test cẩn thận”).
Câu tự kiểm

Với mỗi câu bạn viết trong CLAUDE.md hoặc skill, hỏi: “Nếu không có câu này, Claude có mắc lỗi cụ thể nào không?” Nếu không trả lời được, cắt nó đi — file gọn thì Claude tuân tốt hơn. Đây cũng chính là tiêu chí docs dùng: mỗi dòng phải đáng giá context của nó.

Hooks — tự động hóa theo sự kiện

Hook là các lệnh do bạn định nghĩa (shell command, HTTP endpoint, MCP tool, prompt, hoặc subagent) mà Claude Code tự chạy tại những thời điểm nhất định trong vòng đời của nó. Docs gọi đây là lớp kiểm soát deterministic: việc gì đã cấu hình hook thì chắc chắn xảy ra — không phụ thuộc model “có nhớ hay không”.

Hook chạy theo ba nhịp (docs Hooks):

  • Mỗi session: SessionStart, SessionEnd.
  • Mỗi lượt: UserPromptSubmit (trước khi Claude xử lý prompt), Stop (khi Claude kết thúc lượt trả lời).
  • Mỗi lời gọi tool: PreToolUse (trước khi tool chạy — chặn được) và PostToolUse (sau khi tool chạy thành công).

Một bảng rút gọn các event quan trọng và khả năng chặn (theo bảng exit-code trong docs Hooks reference):

EventKhi nào chạyExit code 2 có chặn được?

UserPromptSubmitTrước khi Claude xử lý promptCó — chặn prompt, không tới Claude
PreToolUseTrước khi tool chạyCó — chặn lời gọi tool
PostToolUseSau khi tool chạy thành côngKhông — tool đã chạy rồi; stderr được hiện cho Claude

Cấu hình hooks trông thế nào

Hook được khai trong settings file (hoặc trong frontmatter của skill/agent). Một object hooks, mỗi event là một key, trong đó là mảng các nhóm { matcher, hooks: [...] }. matcher lọc lời gọi tool (ví dụ "Edit|Write"); để trống nghĩa là mọi trường hợp. Đây là ví dụ auto-format sau mỗi lần sửa file — nguyên bản từ docs:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}

Đọc từng phần: event PostToolUse chạy sau khi tool sửa file thành công; matcher: "Edit|Write" chỉ áp cho hai tool ghi file; command nhận JSON sự kiện trên stdin, moi .tool_input.file_path bằng jq, rồi gọi Prettier lên file đó. Chạy thành công thì Claude Code im lặng — muốn chắc hook đã chạy, xem file được format lại hoặc bật debug log.

Một lưu ý thực tế từ docs: hook trên chỉ bắt được file do tool Edit/Write sửa. Nếu Claude ghi file bằng lệnh shell, hook không thấy. Muốn phủ mọi thay đổi, dùng hook FileChanged (theo dõi file trên đĩa) hoặc một hook Stop quét cây làm việc mỗi lượt.

Ví dụ thật thứ hai: lint trước khi commit

Bài toán: chặn Claude commit khi lint còn lỗi. Đây là PreToolUse — nó chạy trước khi tool Bash thực thi, nên chặn được. Dùng if để hook chỉ nổ với lệnh git commit:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git commit *)",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/lint-before-commit.sh"
          }
        ]
      }
    ]
  }
}

Và script .claude/hooks/lint-before-commit.sh:

#!/bin/bash
# Đọc JSON sự kiện từ stdin, lấy lệnh mà Claude định chạy.
input=$(cat)
cmd=$(echo "$input" | jq -r '.tool_input.command')

case "$cmd" in
  git\ commit*)
    npm run lint || { echo "Lint failed - fix the errors before committing." 1>&2; exit 2; }
    ;;
esac

exit 0

Ba điều cần khắc cốt:

  • exit 0 và không in gì = “không có ý kiến gì” — tool tiếp tục chạy theo luồng permission bình thường. Hook im lặng không có nghĩa là phê duyệt.
  • exit 2 = “dừng, đừng làm” — với PreToolUse nó chặn lời gọi tool; nội dung stderr được đưa cho Claude làm phản hồi để sửa. Lưu ý: exit 1 không chặn — nên script phải chủ động exit 2 khi lint fail.
  • Muốn điều khiển tinh hơn (allow/ask/deny, thêm context…) thì exit 0 và in JSON ra stdout — ví dụ hookSpecificOutput.permissionDecision: "deny".

Dùng /hooks để xem toàn bộ hook đang cấu hình (menu này chỉ đọc — muốn sửa thì sửa file settings hoặc nhờ Claude sửa).

Vì sao hook quan trọng đến vậy

Mọi thứ ở các mục trước (CLAUDE.md, skill) đều là “lời khuyên” cho model. Hook là cơ chế cưỡng chế của harness: format luôn chạy, lint luôn chạy, lệnh nguy hiểm luôn bị chặn — dù model có “quên”. Đây cũng là câu trả lời chuẩn cho câu hỏi thi: “muốn đảm bảo X luôn xảy ra thì dùng gì?” → hook.

Permissions & Plan Mode

Claude Code có hệ thống quyền nhiều tầng: hành động rủi ro thì hỏi, hành động an toàn thì chạy thẳng. Nền tảng (docs Permissions): đọc file trong thư mục làm việc không cần hỏi; lệnh Bash có hỏi (trừ nhóm lệnh read-only có sẵn); sửa file có hỏi; web fetch/search có hỏi. Khi bạn chọn “Yes, and don’t ask again” cho một lệnh Bash, Claude Code lưu thành rule allow trong .claude/settings.local.json của repo.

Ba loại rule: allow / ask / deny

  • Allow — dùng tool không cần hỏi. Ask — luôn hỏi. Deny — cấm hẳn.
  • Cú pháp: Tool hoặc Tool(specifier) — ví dụ Bash(npm run build), Read(./.env), WebFetch(domain:example.com).
  • Thứ tự đánh giá: deny → ask → allow. Match đầu tiên thắng, và độ cụ thể không đổi thứ tự này. Nghĩa là một deny rộng như Bash(aws *) chặn mọi lệnh aws, kể cả lệnh khớp allow hẹp hơn — allow không thể “khoét lỗ” trong deny.
  • Deny bằng tên tool trần (ví dụ Bash) còn mạnh hơn: nó rút tool khỏi context của Claude — Claude không còn thấy tool đó nữa.

Ví dụ trong settings (nguyên bản từ docs):

{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)"
    ]
  }
}

Cấu hình này cho Claude chạy script npm và git commit không cần hỏi, nhưng cấm mọi lệnh bắt đầu bằng git push. Nhớ quy tắc list hợp nhất ở mục 2: rule allow/deny từ nhiều file settings được cộng lại khi đánh giá.

Permission modes — ai hỏi, ai không

ModeKhông cần hỏiHợp cho
default (Manual)Chỉ đọcViệc nhạy cảm, code lạ — bạn duyệt mọi hành động
acceptEditsĐọc + sửa file + lệnh filesystem thông thường (mkdir, touch, mv, cp)Lặp nhanh trên code bạn đang review
planĐọc + lệnh read-only; không sửa file nguồnKhám phá codebase trước khi đổi

Ghi chú phiên bản: từ v2.1.283, auto là mode mặc định khi khởi động session terminal/VS Code trên mọi gói; bạn vẫn đổi mode bất cứ lúc nào (xem docs mới nhất). Mode mặc định đặt được bằng key permissions.defaultMode trong settings file. Muốn xem/sửa rule đang có, gõ /permissions — dialog liệt kê rule và file settings chứa nó.

Plan Mode — nghĩ trước, sửa sau

Plan mode tách khám phá khỏi thực thi. Trong plan mode, Claude đọc file và chạy lệnh read-only để hiểu vấn đề, rồi trình một kế hoạch — không sửa file nguồn cho tới khi bạn duyệt. Cách vào:

  1. Bật: nhấn Shift+Tab tới khi thanh trạng thái hiện ⏸ plan mode on, gõ /plan trước một prompt, hoặc khởi động bằng claude --permission-mode plan.
  2. Khám phá: để Claude đọc code, trả lời câu hỏi — chưa có thay đổi nào trên đĩa.
  3. Lập kế hoạch: yêu cầu một plan chi tiết (file nào đổi, luồng ra sao). Nhấn Ctrl+G để mở plan trong editor và sửa trực tiếp nếu muốn.
  4. Duyệt: Claude hỏi bạn chọn — Yes, and use auto mode (duyệt + chạy auto), Yes, manually approve edits (duyệt + duyệt từng sửa đổi), hoặc No, keep planning (giữ plan mode, nói Claude sửa kế hoạch).
  5. Thực thi: duyệt plan là thoát plan mode; Claude bắt đầu code và tự kiểm chứng theo plan.
Khi nào dùng — và khi nào đừng

Dùng khi bạn chưa chắc về hướng làm, khi thay đổi nhiều file, hoặc khi làm với code bạn không quen. Bỏ qua khi phạm vi đã rõ và sửa đổi nhỏ (sửa typo, thêm một dòng log, đổi tên biến) — plan mode thêm overhead không cần thiết. Câu tự kiểm của docs: “Nếu bạn mô tả được diff trong một câu, bỏ qua plan.”

Một chi tiết nối sang mục sau: khi ở plan mode và cần nghiên cứu codebase, Claude giao việc tìm hiểu cho Plan subagent — output khám phá nằm trong context riêng, còn hội thoại chính vẫn read-only.

Sub-agents — worker có ngữ cảnh riêng

Subagent là một trợ lý chuyên biệt chạy trong context window riêng, có system prompt riêng, bộ tool riêng, và quyền riêng; khi xong nó chỉ trả bản tóm tắt về cho hội thoại chính. Docs ví von rất chuẩn: dùng subagent khi một việc phụ sẽ “làm ngập” hội thoại chính bằng kết quả tìm kiếm, log, hay nội dung file mà bạn sẽ không tham chiếu lại.

Lợi ích chính:

  • Giữ context: việc khám phá/cài đặt diễn ra ngoài hội thoại chính.
  • Cưỡng chế ràng buộc: giới hạn tool mà subagent được dùng (ví dụ chỉ đọc).
  • Chuyên môn hóa: system prompt tập trung cho một loại việc.
  • Tiết kiệm: định tuyến việc phù hợp sang model nhanh/rẻ hơn (ví dụ Haiku).

Claude Code có sẵn vài subagent built-in: Explore (read-only, tìm kiếm/phân tích codebase), Plan (nghiên cứu cho plan mode), General-purpose (việc nhiều bước cần cả khám phá lẫn sửa). Claude chọn subagent dựa trên description của nó — nên description phải nói rõ khi nào dùng.

Tạo subagent

Subagent là file markdown có YAML frontmatter, đặt trong .claude/agents/ (project) hoặc ~/.claude/agents/ (cá nhân, dùng mọi project). Ví dụ nguyên bản từ docs:

---
name: code-improver
description: Scans files and suggests improvements for readability, performance, and best practices. Use after writing or modifying code.
tools: Read, Grep, Glob
model: sonnet
---

You are a code improvement specialist. For each issue you find, explain
the problem, show the current code, and provide an improved version.

Gọi thử: “Use the code-improver agent to suggest improvements in this project”. Trong transcript, việc giao việc hiện thành một dòng tool call mang tên subagent kèm mô tả ngắn.

Vài lưu ý vận hành (docs Sub-agents):

  • Description tốn context: mô tả của các subagent (trừ built-in) cộng lại vượt 15.000 token thì Claude Code cảnh báo lúc khởi động — hãy viết ngắn, đẩy chi tiết vào system prompt (chỉ nạp khi subagent chạy).
  • Subagent chạy trong cùng session; muốn nhiều session song song thì đó là chuyện của background agents / agent view (tầng khác).
  • Subagent có thể được cấu hình preload skill; ngược lại, skill có thể chạy trong ngữ cảnh subagent bằng context: fork.

CI & chế độ non-interactive

Cùng một Claude Code, chạy không cần người ngồi trước màn hình: thêm flag -p (viết đầy đủ --print) là mọi lệnh claude trở thành non-interactive. Claude Code trả kết quả ra stdout, exit code 0 khi thành công và khác 0 khi thất bại — nên script của bạn rẽ nhánh được theo exit status.

Các lệnh mẫu từ docs:

# Hỏi một câu về codebase rồi in câu trả lời
claude -p "What does the auth module do?"

# Chạy task có pre-approve tool (không bị hỏi permission giữa chừng)
claude -p "Find and fix the bug in auth.py" --allowedTools "Read,Edit,Bash"

# Pipe dữ liệu vào, ghi kết quả ra file
cat build-error.txt | claude -p 'concisely explain the root cause of this build error' > output.txt

# Output JSON có cấu trúc (kèm session ID, usage, chi phí)
claude -p "Summarize this project" --output-format json

Vài flag đáng nhớ cho CI:

FlagDùng để
--allowedToolsPre-approve tool — ví dụ "Read,Edit,Bash" hoặc rule hẹp như "Bash(npm test)"
--output-formattext (mặc định) · json · stream-json (JSON theo dòng, stream thời gian thực)
--json-schemaÉp output khớp một JSON Schema; kết quả nằm ở field structured_output (kèm --output-format json)
--bareBỏ qua auto-discovery hooks, skills, MCP, CLAUDE.md, auto memory — chạy nhanh và giống nhau trên mọi máy. Docs khuyến nghị cho CI/script; cần ANTHROPIC_API_KEY (không dùng login subscription).
--permission-modeVí dụ CI khóa chặt: claude -p "run the test suite" --permission-mode dontAsk --allowedTools "Bash(npm test)" "Read"
Cẩn thận khi chạy -p

Một session -p không hỏi gì: không có dialog tin cậy workspace, không có prompt phê duyệt MCP server. Không có --bare, nó vẫn chạy hook trong .claude/settings.json của project và kết nối server trong .mcp.json — kể cả ở thư mục bạn chưa từng “trust”. Vì vậy trong CI hãy dùng --bare hoặc allowlist chặt bằng --allowedTools + dontAsk.

GitHub Actions — Claude trong PR/issue

Claude Code GitHub Action chạy Claude Code ngay trong workflow của repo: ai đó viết @claude … trong comment issue/PR, Claude phân tích code, thực hiện thay đổi và push commit; hoặc bạn truyền prompt để nó chạy tự động theo bất kỳ event nào (kể cả cron). Cài nhanh bằng /install-github-app trong Claude Code, hoặc cài thủ công: cài Claude GitHub App → thêm secret (ANTHROPIC_API_KEY, hoặc CLAUDE_CODE_OAUTH_TOKEN cho subscription) → copy workflow vào .github/workflows/.

Workflow tối thiểu cho chế độ tương tác @claude (nguyên bản từ docs):

name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

Vài điểm docs nhấn mạnh:

  • id-token: write là bắt buộc cho cơ chế xác thực GitHub App mặc định của action; actions: read cho Claude đọc kết quả CI trên PR; if giúp không khởi động runner cho comment không nhắc @claude.
  • Tham số claude_args truyền được mọi CLI argument của Claude Code, ví dụ --max-turns 5 --model claude-sonnet-5 hoặc --allowedTools ….
  • Chạy skill trong CI: skill trong repo (cần actions/checkout trước) thì truyền /tên-skill làm prompt; skill trong plugin thì khai plugin_marketplaces + plugins rồi truyền /plugin:tên-skill.
  • Best practices từ docs: chuẩn dự án viết vào CLAUDE.md (workflow trong CI cũng đọc); không bao giờ commit key — luôn để trong GitHub Secrets; quản lý chi phí bằng prompt cụ thể và --max-turns.

Hiểu lầm thường gặp

Bốn chỗ người mới hay hiểu sai — mỗi cái đều là một câu hỏi thi tiềm năng:

  1. “Viết vào CLAUDE.md là Claude bắt buộc phải tuân.” — Không. Docs nói CLAUDE.md là context, không phải cấu hình cưỡng chế. Hai chỉ dẫn mâu thuẫn thì Claude có thể chọn đại một cái. Muốn chặn cứng: PreToolUse hook hoặc rule deny.
  2. “Settings để ở file nào cũng như nhau.” — Không. Có đúng một thứ tự: managed > command line > project local > shared project > user. Ngoài ra rule dạng list như permissions.allow thì hợp nhất giữa các file, chứ không đè nhau — nên đừng ngạc nhiên khi rule từ file khác vẫn có hiệu lực.
  3. “Slash command và Agent Skill là hai hệ thống riêng.” — Không. Custom commands đã được gộp vào skills: .claude/commands/deploy.md và .claude/skills/deploy/SKILL.md cùng tạo /deploy. Skill chỉ thêm khả năng: thư mục file phụ trợ, frontmatter điều khiển ai gọi, và Claude tự nạp khi liên quan. (Built-in command và bundled skill thì vẫn khác nhau — một cái chạy logic cố định, một cái là prompt cho Claude orchestrator.)
  4. “Auto memory chính là CLAUDE.md do Claude viết.” — Không hẳn: cùng là bộ nhớ bền vững nhưng khác vai. CLAUDE.md là chỉ dẫn do bạn viết, đọc toàn bộ mỗi session. Auto memory là bài học Claude tự ghi, theo từng repository, máy cục bộ, và chỉ nạp 200 dòng đầu hoặc 25KB mỗi session. Muốn chỉ dẫn vào file của nhóm thì phải nói rõ “add this to CLAUDE.md”.

Thực hành — tự làm, tự kiểm

Làm ra nháp trước, rồi mở đáp án. Đáp án là gợi ý — điều quan trọng là bạn giải thích được vì sao.

A1 · Viết một CLAUDE.md cho dự án giả định

Bối cảnh: dự án booking-api (Node + TypeScript). Sự thật cần truyền đạt:

  • Dùng pnpm, không dùng npm. Test bằng pnpm vitest run <file> — chạy một file trước vì full suite chậm. Typecheck bằng pnpm tsc --noEmit.
  • Handlers nằm trong src/api/handlers/. Lỗi trả về dạng { code, message }, không trả stack trace thô.
  • Không commit trực tiếp lên main. Branch: feat/…, fix/….
  • Claude phải chạy typecheck + test file vừa sửa trước khi báo xong.

Viết file dưới 200 dòng, rồi tự kiểm bằng checklist trong đáp án.

Xem đáp án gợi ý 
# Project: booking-api

## Commands
- Install: `pnpm install`
- Tests: `pnpm vitest run <file>` (một file trước; full suite rất chậm)
- Typecheck: `pnpm tsc --noEmit`

## Conventions
- API handlers nằm trong `src/api/handlers/`.
- Lỗi trả `{ code, message }`; không trả stack trace thô.

## Workflow
- Chạy typecheck + test file vừa sửa trước khi báo xong.
- Không commit trực tiếp lên `main`; branch `feat/…`, `fix/…`.

Checklist tự kiểm:

  • Mỗi dòng có phải thứ Claude không thể tự suy ra từ code? (Nếu suy ra được — cắt.)
  • Chỉ dẫn có cụ thể, kiểm chứng được? (“Chạy pnpm tsc --noEmit” chứ không phải “đảm bảo code đúng”.)
  • Có mâu thuẫn với chỉ dẫn nào khác không? Có trùng lặp không?
  • Dưới 200 dòng? (File này ~12 dòng — tốt.)

A2 · Chọn đúng công cụ: CLAUDE.md, skill, hook hay subagent?

Với mỗi tình huống, chọn một cơ chế và giải thích một câu:

  1. “Luôn dùng 2-space indentation, không dùng tab.”
  2. “Quy trình release 7 bước, chỉ chạy khi tôi gọi /release — tuyệt đối không để Claude tự chạy.”
  3. “Sau mỗi lần Claude sửa file, tự chạy Prettier.”
  4. “Cần đọc 30 file trong repo để trả lời một câu hỏi kiến trúc; không muốn kết quả tràn vào hội thoại chính.”
  5. “Chặn mọi lệnh git push.”
Xem đáp án gợi ý
  • 1 — CLAUDE.md. Sự thật luôn đúng, mọi session, ngắn gọn.
  • 2 — Skill + disable-model-invocation: true. Quy trình nhiều bước, có tác dụng phụ, chỉ bạn kích hoạt. (Đặt frontmatter này để Claude không tự gọi.)
  • 3 — Hook (PostToolUse, matcher Edit|Write). Phải xảy ra mỗi lần, không phụ thuộc model.
  • 4 — Subagent. Cách ly context: nó đọc 30 file nhưng chỉ trả summary.
  • 5 — Permission rule deny (Bash(git push *)), hoặc PreToolUse hook nếu cần logic phức tạp. Đây là cơ chế cưỡng chế, không phải lời khuyên.

A3 · Viết một skill + một hook config thật

Phần 1 — Skill. Viết .claude/skills/review-diff/SKILL.md: một skill tóm tắt diff chưa commit và cảnh báo rủi ro. Yêu cầu: có description nêu rõ khi nào dùng (kèm trigger phrase), pre-approve đúng tool cần thiết, và tiêm diff hiện tại vào nội dung skill.

Phần 2 — Hook. Viết config auto-format sau mỗi lần Claude sửa file bằng Edit/Write, dùng Prettier. Nêu một hạn chế của hook này và cách khắc phục.

Xem đáp án gợi ý

Phần 1 — SKILL.md:

---
description: Summarizes uncommitted changes and flags anything risky. Use when the user asks what changed, wants a commit message, or asks to review their diff.
allowed-tools: Bash(git diff *)
---

## Current changes

!`git diff HEAD`

## Instructions

Summarize the changes above in two or three bullet points, then list any risks
such as missing error handling, hardcoded values, or tests that need updating.
If the diff is empty, say there are no uncommitted changes.

Tự kiểm: description có nêu khi nào dùng và trigger phrase? allowed-tools có đủ hẹp (Bash(git diff *), không phải Bash) không? Có cần disable-model-invocation không? (Ở đây không — skill này vô hại và hữu ích khi Claude tự nạp.)

Phần 2 — hook:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}

Hạn chế: chỉ bắt file do tool Edit/Write sửa; nếu Claude ghi file qua lệnh shell thì hook không thấy. Khắc phục: dùng hook FileChanged (theo dõi file trên đĩa, bất kể ai ghi) hoặc hook Stop quét cây làm việc mỗi lượt.

Kiểm tra hiểu

Sáu câu — làm nhanh để chắc mình nắm phần cấu hình. Chú ý phân bố đáp án đấy.

1. Trong các tầng cấu hình, tầng nào có độ ưu tiên cao nhất?

Gợi ý: tầng nào mà bạn không đè được?

Chính xác. Thứ tự đầy đủ: managed > command line > project local > shared project > user. Managed settings do tổ chức triển khai (file/MDM/server-managed) và gần như không gì của bạn đè được — chỉ có vài ngoại lệ bảo mật đặc biệt.

2. Bạn muốn chỉ dẫn dùng chung cho cả nhóm, được commit vào repo. Đặt CLAUDE.md ở đâu?

Gợi ý: file nào Claude Code tự giữ ngoài git, và file nào là ghi chú cá nhân?

Chính xác. Project instructions nằm ở ./CLAUDE.md hoặc ./.claude/CLAUDE.md — commit để cả nhóm nhận. ~/.claude/CLAUDE.md là sở thích cá nhân; CLAUDE.local.md là ghi chú riêng (nên gitignore); còn đường dẫn memory/ là auto memory do Claude tự ghi.

3. Có cả .claude/commands/deploy.md và .claude/skills/deploy/SKILL.md. Điều gì đúng?

Gợi ý: docs nói custom commands “đã được hợp nhất” vào đâu?

Chính xác. Custom commands đã được gộp vào skills: file command và skill tạo cùng tên lệnh, chạy cùng cách. Skills thêm thư mục file phụ trợ, frontmatter điều khiển invocation, và khả năng Claude tự nạp khi thấy liên quan.

4. Muốn tự động chạy formatter sau khi Claude sửa file thành công, dùng hook event nào?

Gợi ý: “sau khi tool chạy thành công”.

Chính xác. PostToolUse chạy sau khi tool thành công — ví dụ matcher "Edit|Write" cộng lệnh Prettier. PreToolUse chạy trước và có thể chặn; UserPromptSubmit chạy trước khi Claude xử lý prompt; SessionEnd chạy lúc kết thúc session.

5. Tình huống nào hợp với Plan Mode nhất?

Gợi ý: docs nói nếu mô tả được diff trong một câu thì bỏ qua plan.

Chính xác. Plan mode hữu ích khi bạn chưa chắc về hướng làm, thay đổi chạm nhiều file, hoặc code không quen. Ba việc còn lại đều nhỏ và rõ phạm vi — plan chỉ thêm overhead.

6. Điền flag còn thiếu để chạy Claude Code non-interactive trong script/CI:

claude "Summarize this project"

Luyện thêm với nguồn chính thức

Bốn repo GitHub chính thức của Anthropic — nơi tra cứu khi docs chưa đủ, và để học bằng ví dụ thật:

  • anthropics/claude-code — repo chính thức của Claude Code; theo dõi issues và release notes khi cần thông tin mới nhất ngoài trang documentation.
  • anthropics/claude-code-action — GitHub Action chính thức để dùng Claude Code trong CI (nối tiếp phần GitHub Actions ở mục 10); mở thư mục examples/ để lấy workflow claude.yml dùng ngay.
  • anthropics/skills — kho Agent Skills chính thức; đọc các skill mẫu (frontmatter + thân skill) rồi bắt chước cấu trúc để viết skill của mình.
  • anthropics/claude-plugins-official — thư mục plugins chính thức; xem cách đóng gói skills, hooks, subagents thành plugin để tái sử dụng và chia sẻ cho nhóm.
