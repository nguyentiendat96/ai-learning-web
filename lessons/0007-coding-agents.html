Vì sao coding agent là domain quan trọng nhất

Trong danh sách domain của khóa học — coding agents (buổi 3b), computer use agents (buổi 4a), deep research agents (buổi 5b) — code được dạy đầu tiên. Không phải ngẫu nhiên. Đây là nơi agent tiến bộ nhanh nhất, sản phẩm chín nhất, và cũng là nơi bài học rút ra được áp cho các domain khác.

Slide 2 chia coding agent thành ba mức trưởng thành. Đây là cách phân loại bạn sẽ gặp lại suốt bài:

 MỨC 1 · viết code           MỨC 2 · sửa repository       MỨC 3 · làm development
 ─────────────────           ──────────────────────       ────────────────────────
 prompt ──► code             issue + repo                 yêu cầu ──► code
 (một lần completion)        ──► tìm ──► sửa ──► test     ──► review ──► deploy
                             ◄──── lặp ─────┘             ──► theo dõi ──► bảo trì
  • Mức 1 — viết code (single completion). Bạn đưa một prompt, model trả về một đoạn code, hết. Giống tính năng gợi ý code trong editor. Không có vòng lặp.
  • Mức 2 — sửa repository. Model nhận một issue và cả repository, phải tìm file liên quan, sửa nhiều file, rồi chạy test để kiểm. Đây là nơi vòng lặp agent bắt đầu.
  • Mức 3 — làm development. Không chỉ sửa bug: nhận yêu cầu, viết code, review, quyết định release, deploy, theo dõi, bảo trì — cả vòng đời phần mềm (slide 61).

Vì sao code là domain "nóng" nhất

Bốn lý do. Tôi xếp theo mức độ quan trọng:

  1. Code là nơi agent tự kiểm được. Chạy test xong là biết đúng hay sai — tín hiệu rõ ràng, không cần con người phán. Nghĩ mà xem: kiểm tra một bài luận "hay chưa" rất khó, còn kiểm tra một hàm "đúng chưa" thì chạy vài dòng test là xong. Nhờ vậy agent có thể tự sửa mình trong vòng lặp. Đây là lý do sâu xa nhất khiến code là domain tiến nhanh nhất.

    Ví dụ đời thường: làm bài tập có đáp án ở cuối sách thì bạn tiến bộ nhanh hơn nhiều so với làm bài chỉ có người chấm cuối kỳ. Code chính là loại bài tập "có đáp án" đó — đáp án tên là test.

  2. Code là cách agent chạm vào mọi thứ khác. Muốn agent đặt vé máy bay, phân tích bảng dữ liệu, dựng một trang web — cuối cùng vẫn phải có code chạy phía sau. Code không chỉ là một domain; nó là đôi tay của phần lớn agent khác.

  3. Thời gian của lập trình viên không nằm ở việc gõ code. Slide 62 dẫn một khảo sát 5.928 ngày làm việc tự khai của kỹ sư Microsoft (Meyer et al., 2019): chỉ 15% thời gian là đọc/viết code và test; 85% còn lại là họp, email, debug, chạy test, review, viết tài liệu, giúp đồng nghiệp, học, nghỉ. Nếu agent chỉ giúp gõ code nhanh hơn thì nó chỉ chạm 15% — cơ hội lớn nằm ở phần còn lại. Đó là lý do slide 63 liệt kê cả một "họ" task: sửa bug, viết thư viện, sinh test, sửa CI, bảo trì dài hạn.[1]

  4. Code là nơi có nhiều thước đo tốt. Test pass, build xanh, benchmark công khai — đo được thì cải thiện được. Các domain khác (viết nội dung, thiết kế) khó đo hơn nhiều.

Pre-training — học từ code và văn bản

Slide 7 (dẫn từ dự án OLMo, Groeneveld et al., 2024) nêu ba nguyên tắc:

  • Trộn nguồn. Web, văn bản kỹ thuật, toán, source code, tài liệu. Vì sao cần trộn? Vì model code vẫn phải đọc hiểu mô tả yêu cầu, đọc tài liệu thư viện, đọc thông báo lỗi — toàn là văn bản.
  • Giữ cấu trúc. Thụt lề, ranh giới file, API, quan hệ giữa văn bản và code. Ví dụ: docstring nằm ngay trên hàm — model phải học được mối quan hệ "mô tả ở trên ↔ code ở dưới". Nếu bạn xé file thành các câu rời rạc, thông tin đó biến mất.
  • Đánh giá trong lúc luyện. Hai loại thước đo: held-out loss theo từng domain (model đoán token giỏi đến đâu trên dữ liệu chưa thấy) và bài tập coding chức năng (model có giải được bài không). Hai thứ khác nhau: đoán token giỏi không tự động có nghĩa là giải được bài. Giống như chép chính tả đúng chưa chắc viết được đoạn văn.

Slide 8 (dẫn từ StarCoder) nói về làm sạch dữ liệu — phần ít được nhắc nhưng cực kỳ quan trọng:

  • Lọc theo ngôn ngữ và nguồn: bỏ code do máy sinh hàng loạt, file lỗi encoding, nội dung lặp vô giá trị.
  • Khử trùng lặp (deduplicate): fork, thư viện "vendored" (bản sao thư viện nhúng trong dự án), file gần giống nhau, lời giải bị copy.
  • Kiểm soát nguồn gốc: ghi lại license, ngày, lựa chọn opt-out, lọc dữ liệu nhạy cảm.
  • Chống rò rỉ (leakage): chia tập train/test theo repository hoặc theo họ bài toán; khử nhiễm (decontaminate) các bài thi.

Vì sao phải khử trùng lặp và chống rò rỉ? Hai lý do rất đời thường. Thứ nhất, nếu cùng một đoạn code xuất hiện một nghìn lần, model sẽ học thuộc nó thay vì học cách viết code như thế. Thứ hai, nếu đề thi đã nằm sẵn trong tập luyện thì điểm thi là điểm giả — giống như cho học sinh làm đề trước rồi khen "em giỏi".

Slide 10 cho một con số cụ thể: StarCoderBase — 15,5 tỷ tham số, luyện trên 1 nghìn tỷ token (1T tokens), hơn 80 ngôn ngữ, dữ liệu gồm source code, issue, commit, notebook. Xu hướng quan sát được: hầu hết ngôn ngữ đều tốt lên khi tăng số token luyện. (Nhắc lại: "tham số" là các trọng số model học được; "token" là mảnh text — mục sau nói kỹ.)

Token hóa code — vì sao khoảng trắng là token

Đây là phần thú vị nhất của bài, và cũng là phần dễ bỏ qua nhất.

Model không nhìn thấy chữ cái như bạn. Nó nhìn thấy token — mảnh text đã được cắt sẵn. Một token có thể là cả từ, một phần của từ, hoặc vài ký tự. Với code, slide 9 (dẫn StarCoder §5.3 và StarCoder2) mô tả cách tokenizer làm việc qua bốn điểm:

  • Tokenizer học bằng byte-level BPE trên cả code lẫn văn xuôi. (BPE là thuật toán gộp dần những cặp ký tự hay đi cùng nhau thành một token — cứ gộp cặp xuất hiện nhiều nhất, lặp lại.)
  • Identifier có thể trải qua nhiều token. Một tên hàm dài như calculate_monthly_interest có thể bị cắt thành vài mảnh. Đây là một lý do kỹ thuật khiến model đôi khi "gõ nhầm" giữa tên biến: nó đang ghép các mảnh.
  • Khoảng trắng mang cú pháp và nội dung. Trong Python, thụt lề là cú pháp. Trong chuỗi ký tự, dấu cách là nội dung. Không được xóa.
  • Gộp chuỗi khoảng trắng hay gặp thành token. Thay vì trả một token cho mỗi dấu cách, tokenizer gộp cả cụm — ví dụ token "xuống dòng + ba dấu cách".

Slide 9 đưa một ví dụ rất cụ thể. Đây là dòng code nguồn và cách nó bị cắt token (ký hiệu · = dấu cách, ↵ = xuống dòng, | = ranh giới token):

Nguồn (2 dòng code):  if·ready:↵····return·value↵
Token (7 mảnh):        if | ·ready | : | ↵··· | ·return | ·value | ↵

· = dấu cách     ↵ = xuống dòng     | = ranh giới token

Nhìn kỹ chỗ thụt lề: bốn dấu cách không bị cắt thành bốn token. Token thứ tư là ↵··· — xuống dòng kèm ba dấu cách. Dấu cách thứ tư dính luôn vào chữ tiếp theo thành ·return. Đếm thử theo cách "mỗi dấu cách một token" thì đoạn này tốn 13 mảnh; cách gộp chỉ tốn 7. Gần một nửa.[2]

Vì sao điều này quan trọng
  • Ngữ cảnh chứa được nhiều code hơn. Ít token hơn cho cùng một file nghĩa là nhét được nhiều file hơn vào context window — nối thẳng vào bài 04.
  • Model "thấy" được thụt lề. Vì thụt lề là token, model phân biệt được khối code này nằm trong khối kia — điều kiện để hiểu Python, YAML.
  • Sửa code phải tái tạo đúng từng khoảng trắng. Trong Python, một dấu cách sai có thể đổi nghĩa chương trình. Đây là một lý do kỹ thuật khiến "sửa" khó hơn "viết mới" — mục 5 sẽ nói tiếp.

Mid-training — trộn code, text, toán

Pre-training xong, model vẫn cần một chặng nữa: mid-training. Slide 11 nói: tiếp tục luyện với tỉ lệ code cao hơn, nhưng giữ lại text và toán. Ví dụ được dẫn: Code Llama — từ Llama 2, luyện thêm 500 tỷ token cho các bản 7B, 13B và 34B.

Vì sao không "dồn hết" cho code? Slide 12 (bảng trích từ Qwen2.5-Coder, Hui et al., 2024) trả lời bằng số:

Tỉ lệ code / text / toánĐiểm code (Common code)Toán (MATH)Kiến thức chung (MMLU)
100 / 0 / 049.810.323.8

Đọc bảng này rất thú vị: khi bớt code một chút để thêm text và toán, điểm code gần như đứng yên (49.8 → 48.3, giảm 1.5) trong khi điểm toán tăng gấp ba (10.3 → 33.2) và kiến thức chung tăng gần gấp ba (23.8 → 62.9). Đổi rất hời.

Vì sao? Vì một coding agent vẫn phải nói chuyện với con người: đọc issue viết vội, hiểu tài liệu, giải thích vì sao nó sửa như vậy. Một model chỉ giỏi cú pháp mà quên đọc hiểu sẽ sửa sai yêu cầu. Giống học sinh chuyên Toán vẫn phải học Văn — không phải để viết văn hay, mà để đọc đề.

Ngữ cảnh dài — nhìn sang file bên cạnh

Slide 13 đưa một tình huống rất thật. Ba file liên quan nhau:

  • types.py — định nghĩa Result.value có thể là None;
  • worker.py — truyền Result đi tiếp;
  • caller.py — cần hoàn thành nốt phần kiểm tra null.

Muốn sửa caller.py cho đúng, model phải biết chuyện gì xảy ra ở types.py. Nhìn mỗi caller.py thì không thể biết. Vì vậy mid-training cho model học trên chuỗi file liên quan — cùng đường dẫn, cùng phụ thuộc — và trên chuỗi dài hơn. Qwen2.5-Coder luyện từ 8K lên 32K token; kỹ thuật YaRN kéo tiếp lên 128K. Và phải kiểm tra lại ba thứ: hoàn thành code xuyên file, infilling, và khả năng giữ ngữ cảnh ngắn — kéo dài ngữ cảnh không được làm hỏng prompt ngắn.

Infilling — học cách đọc cả hai phía

Model ngôn ngữ cổ điển chỉ đọc một chiều: cho phần đứng trước, đoán token tiếp theo. Nhưng trong editor thật, bạn thường cần điền vào giữa. Slide 14 ví dụ:

def is_positive(x: int) -> ____:
    return x > 0

Chỗ trống là kiểu trả về. Nếu chỉ đọc phần trước, model phải đoán mò. Nhưng phần code phía sau — return x > 0 — chính là bằng chứng cho đáp án bool. Đọc được cả hai phía thì dễ hơn hẳn.

Slide 15 (dẫn InCoder, Fried et al.) giải thích cách luyện. Khi huấn luyện, người ta lấy một file, cắt ra ba phần prefix / span / suffix, rồi xếp lại thành:

Luyện:     prefix [M0] suffix [M0] span [END]
Dùng:      prefix [M0] suffix [M0]  ──►  sinh ra span

[M0] là một "sentinel token" — ký hiệu đánh dấu chỗ trống. Nếu có nhiều lỗ, mỗi lỗ có sentinel riêng để model biết mảnh nào thuộc vị trí nào. Nhờ luyện kiểu này, model làm được nhiều việc "không cần dạy riêng": hoàn thành code, suy ra kiểu dữ liệu, viết comment, đổi tên biến.

Hiệu quả của việc nhìn suffix, số liệu từ slide 16 (bài kiểm tra infilling dựng từ HumanEval, đo % hàm hoàn thành qua được test):

Cách làmCó dùng suffix không?Một dòngNhiều dòng

Khoảng cách 48.2% → 69.0% cho thấy: đọc được code phía sau là lợi thế lớn, nhất là với các đoạn nhiều dòng. Và slide 17 trả lời câu hỏi "học infilling có làm hỏng khả năng viết code theo kiểu thường không?" — với cùng ngân sách 52 tỷ token, mục tiêu có mặt nạ nhân quả đạt pass@1 cao hơn chút trên cả HumanEval (8.0 so với 6.0) và MBPP (10.9 so với 8.9). Học điền vào giữa không hại gì; thậm chí tốt hơn.[3]

Vì sao điều này quan trọng với agent? Vì sửa code chính là một bài infilling: bạn thay một đoạn nằm giữa file, phải tôn trọng cả phần trên lẫn phần dưới. Slide 18 còn liệt kê các tín hiệu khác mà model học được từ code: commit diff (code trước + thông điệp commit → code sau), diagnostics (code lỗi + thông báo lỗi → bản sửa), tests (chương trình + kết quả test → phần thưởng), và execution traces (chương trình → các dòng đã chạy + trạng thái). Code là loại dữ liệu đặc biệt: nó kèm theo cả lịch sử sửa chữa của chính nó.

Tóm mục 2 trong một câu

Model code được luyện ba chặng — pre-training trên code + text đã làm sạch, mid-training trộn tỉ lệ hợp lý và kéo dài ngữ cảnh, rồi RL bằng phần thưởng chạy được code — và ngay từ khâu cắt token, "khoảng trắng" đã được đối xử như nội dung quan trọng.

Đánh giá code sinh ra

Câu hỏi trung tâm của mục này: làm sao biết một đoạn code do model viết là "tốt"? Trả lời được câu này thì mới luyện được, so sánh được, và cải thiện được. Slide 19–27 dẫn bạn đi từ cách ngây thơ nhất đến cách mạnh nhất.

Cách ngây thơ: so chữ với bài mẫu

Cách đầu tiên ai cũng nghĩ tới: exact match — code sinh ra có giống hệt bài giải mẫu không? Và BLEU-4 — đo tỉ lệ trùng các cụm n-gram token, kèm hình phạt nếu bài quá ngắn (mượn từ ngành dịch máy).

Slide 20 cho một ví dụ làm sáng tỏ vấn đề. Đề bài: viết hàm kiểm tra số nguyên x có dương không. Bài giải mẫu: return x > 0.

Bài làm của modelHành vi thậtKết luận
return x >= 0 — khác một ký tựSai tại x = 0Khác chữ, và quả thật sai
return not (x <= 0) — viết rất khácĐúng với mọi số nguyênKhác chữ, nhưng đúng

Bài học: giống chữ không có nghĩa là đúng, khác chữ không có nghĩa là sai. So khớp văn bản giống như chấm điểm một bài toán bằng cách so chữ viết với đáp án — bạn học sinh giải bằng cách khác mà vẫn đúng sẽ bị điểm thấp oan, còn bạn chép y hệt đáp án nhưng chép nhầm dấu cũng được điểm cao.

Hiểu cấu trúc và ngữ nghĩa

Hai hướng cải tiến, đi từ nông đến sâu:

  • CodeBLEU (slide 21, Ren et al., 2020) — không chỉ so token, mà so cả cấu trúc: cây cú pháp, luồng dữ liệu. Hai đoạn code viết khác nhau nhưng cùng "hình dạng" sẽ được điểm cao hơn.
  • CodeBERTScore (slide 22, Zhou et al., EMNLP 2023) — mã hóa prompt và từng đoạn code thành vector, so các vector token theo ngữ cảnh, ghép cặp tốt nhất rồi tính precision / recall / F-score. Nói đơn giản: thay vì so chữ, nó so ý nghĩa gần đúng.

Cả hai vẫn chỉ là ước lượng. Muốn biết code đúng hay không, cách duy nhất chắc chắn là chạy nó.

Cách mạnh nhất: chạy thử

Slide 23 mô tả quy trình — gọi là đánh giá bằng thực thi (functional evaluation). Lấy ứng viên is_positive(x): return x >= 0, cho chạy trong một môi trường cô lập (isolated runtime, có giới hạn thời gian và bộ nhớ) với ba test case:

Kết luận: "zero is not positive" — số 0 không phải số dương. Chỉ một test case bắt được lỗi mà mắt người đọc lướt qua. Đây là sức mạnh của việc chạy code: nó kiểm hành vi, không kiểm hình thức.

Nhưng đừng thần thánh hóa. Slide 24 liệt kê cả hai mặt:

Hình dung: một bài kiểm lái xe gồm ba tuyến cố định. Qua được ba tuyến đó thì được cấp bằng — nhưng không chứng minh bạn lái giỏi ở mọi con đường. Và nếu người ra đề sai thì kết quả sai theo. Test hữu hạn chỉ trả lời được đúng những câu nó hỏi.

Benchmark chuẩn: HumanEval, CodeContests, pass@k

  • HumanEval (slide 25): 164 hàm Python. Đề là docstring, model viết phần thân; chấm bằng unit test ẩn. Nhỏ nhưng là thước đo kinh điển.
  • CodeContests (slide 25): các bài thi lập trình thi đấu, gồm bài kiểu Codeforces. Đề là cả một phát biểu bài toán, model phải viết cả chương trình; chấm bằng biên dịch + chạy test.
  • pass@k (slide 26): xác suất để ít nhất một trong k lần sinh vượt qua toàn bộ test. Ví dụ dễ hiểu: pass@10 = 50% nghĩa là cho model thử 10 lần, một nửa số bài sẽ được giải ít nhất một lần. Vì model sinh ngẫu nhiên, "thử nhiều lần" là một chiến lược thật, có đo đạc hẳn hoi.

Yêu cầu phi chức năng

Slide 27 nhắc một điều người mới hay quên: code đúng chưa đủ. Yêu cầu "làm cho code này chạy nhanh hơn" cũng là một bài toán, và cách chấm khác hẳn:

  • Hiệu năng: chạy test + đo thời gian chạy → điểm là speedup (nhanh hơn bao nhiêu lần).
  • Độ trễ / tài nguyên: so với các bản sửa mẫu của con người → điểm DiffBLEU.
  • Bảo trì / bảo mật: kiểm tra tĩnh (static checks) + độ khớp với bản sửa mẫu → CodeQL × DiffBLEU.

Slide này dẫn bộ NoFunEval (Singhal et al., 2024) gồm 397 bài sửa code thuộc loại này. Vì sao quan trọng? Vì món ăn ngon nhưng nấu ba tiếng và bừa hết mọi cái nồi thì nhà hàng vẫn không dùng được. Trong công việc thật, tốc độ, an toàn, dễ bảo trì thường quan trọng ngang với "chạy ra đúng kết quả".

Học từ kết quả test (RL)

Slide 28 mô tả vòng lặp luyện bằng phần thưởng thực thi (dẫn DeepCoder, Luo et al., 2025):

  1. Lấy bài toán, model sinh nhiều lời giải — mỗi lời giải gồm phần suy luận và phần code cuối.
  2. Chạy code cuối trong môi trường thực thi.
  3. Pass / fail → phần thưởng.
  4. Cập nhật model: làm những lời giải được thưởng trở nên dễ sinh hơn.
  5. Sinh lại với model mới, lặp tiếp.

Slide 29 cho một ví dụ để thấy "phần thưởng thực thi" dạy được gì. Bài toán: tính tổng 1 + … + n, với n có thể tới 1012.

  • Cách ngây thơ — cộng từng số (sum(range(n + 1))) — đúng nhưng quá chậm với n lớn. Không được thưởng.
  • Cách tốt — ghép cặp hai đầu, rút ra công thức n * (n + 1) // 2, kiểm tra với 0 và 1 — đúng và nhanh. Được thưởng.
  • Cách "nhớ nhầm công thức" — n * (n - 1) // 2 — sai ngay từ n = 1. Không được thưởng.

Điểm cần nhớ: model học được suy luận hướng tới lời giải, không chỉ học cú pháp. Và chỉ một lỗi chép công thức nhỏ cũng đủ làm sai — nên bước chạy thử không bao giờ được bỏ.

Mục 3 nói về sinh một hàm. Công việc thật thì khác: bạn có một repository, một issue mô tả triệu chứng, và không ai chỉ cho bạn file nào đang sai. Slide 32 gọi đây là bước chuyển từ single-step coding sang agentic coding:

Ví dụ xương sống: lỗi "retries = 0"

Slide 34–36 kể một câu chuyện nhỏ nhưng chứa gần như toàn bộ bài học của mục này. Repository có ba file: cli.py, config.py, test_config.py. Triệu chứng: người dùng đặt số lần thử lại là 0 (nghĩa là "không thử lại"), nhưng hệ thống lại thử lại 3 lần.

Bước 1 — Localize. Agent không đoán. Nó chạy rg 'retries' buggy_config.py (rg là lệnh tìm kiếm text, bạn có thể hình dung như Ctrl+F nhưng chạy trong terminal) và tìm thấy dòng nghi phạm:

return config.get("retries") or 3

Rồi nó tái hiện lỗi trước khi sửa:

$ RETRY_MODULE=buggy_config python3 -m unittest test_config.RetryTests.test_zero
AssertionError: 3 != 0
FAILED (failures=1)

Thấy chưa? Test khẳng định "phải bằng 0" mà thực tế ra 3. Giờ thì chắc chắn lỗi nằm ở đâu, và cần sửa điều kiện chứ không phải sửa test.

Vì sao dòng đó sai? — "falsy" trong Python

Trong Python, một số giá trị được coi là "falsy" (tạm dịch: quy về sai) khi dùng trong điều kiện: 0, "" (chuỗi rỗng), [] (danh sách rỗng), None, False. Câu x or y trả về y nếu x falsy. Nên config.get("retries") or 3 biến mọi giá trị falsy thành 3 — kể cả số 0 hợp lệ.

Ví dụ đời thường: bạn đặt bàn và nói "0 người lớn, 2 trẻ em", nhân viên nghe "0 người lớn" thành "chưa nói gì" nên tự điền mặc định 3 người lớn. Lỗi không nằm ở con số 0 — nó nằm ở chỗ không phân biệt "không có giá trị" với "giá trị bằng 0".

Bước 2 — Edit. Slide 35 cho thấy thay đổi:

# Trước — mọi giá trị falsy đều chọn mặc định
return config.get("retries") or 3

# Sau — số 0 tường minh được giữ nguyên
value = config.get("retries")
return 3 if value is None else value

Chú ý cách sửa: tách "thiếu giá trị" (None) ra khỏi "giá trị bằng 0". Đây là kiểu sửa điển hình của người có kinh nghiệm — và cũng là kiểu infilling đã nói ở mục 2: sửa một đoạn nằm giữa file, phải giữ nguyên phần xung quanh.

Bước 3 — Verify. Slide 36 chạy toàn bộ test, không chỉ test vừa sửa:

$ python3 -m unittest -v test_config
missing   →  3   PASS
None      →  3   PASS
zero      →  0   PASS
positive  →  2   PASS
Ran 4 tests: OK

Bốn trường hợp, không phải một. Ba trường hợp sau là để chắc rằng bản sửa không làm hỏng hành vi cũ. Trong nghề này người ta gọi đó là regression — thứ mà mục 6 sẽ gặp lại với tên gọi chính thức.

Kiểm nhanh: điền vào chỗ trống — trong bản sửa, điều kiện để dùng giá trị mặc định là value is ____.

Vì sao verify là siêu năng lực

Điều đáng chú ý: agent không cần đúng ngay lần đầu. Nó chỉ cần phát hiện được mình sai — và trong code, việc đó rẻ: chạy test là biết. Đây chính là lý do ở mục 1 tôi nói code là domain "nóng" nhất.

Hãy so với một công việc không có thước đo: viết một bản đề xuất. Agent viết xong, hay hay dở không ai biết ngay, sửa mãi không biết dừng. Còn ở đây: chạy test, đỏ thì sửa, xanh thì xong. Vòng lặp có điểm dừng khách quan.

Một lựa chọn khác: workflow cố định (Agentless)

Slide 37 giới thiệu một hướng ngược lại với vòng lặp tự do: Agentless (Xia et al.). Thay vì để model tự quyết mỗi bước, Agentless dùng một quy trình cố định: định vị → sửa → kiểm chứng theo các bước được thiết kế sẵn. Ít quyết định hơn, khó "lạc đường" hơn, dễ đoán và rẻ hơn.

Điều này nối tiếp bài 06 (ba mức cam kết: workflow → plan-then-execute → replan): không phải cứ tự do hơn là tốt hơn. Và nó dẫn thẳng tới chủ đề lớn của mục 6 — harness.

Sửa file khó hơn viết mới

Nghe có vẻ ngược đời. Viết cả hàm mới dài 30 dòng, sửa một dòng trong hàm cũ — chẳng phải cái sau dễ hơn sao? Không. Và hiểu vì sao là chìa khóa để hiểu cả mục này.

Vì sao sửa khó hơn viết

Slide 5 nói gọn một câu: editing — condition on both sides (sửa — phải điều kiện hóa trên cả hai phía). Cụ thể hơn, có năm khó khăn chồng lên nhau:

  1. Phải tìm đúng chỗ trước đã. Viết mới thì bạn biết viết vào đâu. Sửa thì phải localize trong một repository có thể hàng nghìn file — như mò kim trong đống rơm, trừ khi bạn biết theo dấu dữ liệu.
  2. Phải khớp chính xác văn bản xung quanh. Công cụ sửa file thường hoạt động kiểu "tìm đoạn cũ, thay đoạn mới". Nếu đoạn cũ không khớp từng ký tự — kể cả khoảng trắng — lệnh thất bại.
  3. Phải không phá code khác. Sửa xong, mọi hành vi cũ phải còn nguyên. Đây là ràng buộc mà "viết mới" không có.
  4. Đích có thể mơ hồ. Cùng một dòng return x xuất hiện ba lần trong file — thay dòng nào? Công cụ cần đủ ngữ cảnh để phân biệt.
  5. Phải tái tạo đúng khoảng trắng và phong cách. Nhớ lại mục 2: thụt lề là token mang cú pháp. Một dấu cách sai trong Python có thể đổi nghĩa chương trình.

Ví dụ đời thường: viết một câu mới vào bản nháp thì dễ. Sửa một câu trong bản hợp đồng đã in thì bạn phải khớp từng chữ xung quanh, không được làm sai nghĩa điều khoản khác, và không được để lại vết mực lem. Cùng một "câu văn", hai mức độ khó hoàn toàn khác.

Bộ tool: chỉ một cái shell là đủ?

(Exit status là mã số lệnh trả về — 0 là thành công, khác 0 là lỗi. Timeout là giới hạn thời gian chạy để một lệnh treo không làm chết cả phiên.)

Vì sao một giao diện duy nhất lại đủ? Vì shell vốn đã là "bộ chuyển đổi vạn năng" của máy tính — muốn làm gì cũng có lệnh. Và model đã thấy vô số lệnh shell trong dữ liệu luyện. Đây là bài học lớn: harness đơn giản vẫn có thể rất mạnh.

Bốn cách nói "sửa chỗ này" (edit formats)

Slide 40–42 liệt kê bốn cách model có thể diễn đạt một thay đổi. Đọc kỹ bảng này, vì đây là phần "cơ bắp" của coding agent:

1. Dùng lệnh shell (sed / awk / script Python). Ví dụ đổi giá trị trong file cấu hình:

sed 's/^RETRIES = 3$/RETRIES = 5/' settings.py > settings.new
mv settings.new settings.py

Ưu: linh hoạt, làm được cả loạt thay đổi trên nhiều file. Nhược: phải viết đúng biểu thức, dễ sai nếu văn bản không như tưởng.

2. Gửi cả file mới (whole file). Model viết lại toàn bộ nội dung file. Đơn giản để áp dụng — không cần khớp gì cả. Nhược điểm: lặp lại cả phần không đổi (tốn token) và có rủi ro viết lại nhầm phần không liên quan. Các tool dùng cách này: Pi write, OpenCode write, OpenHands create.

3. Tìm và thay (search / replace). Model gửi "đoạn cũ" và "đoạn mới". Gọn, tiết kiệm — nhưng cần đoạn cũ khớp duy nhất:

<<<<<<< SEARCH
RETRIES = 3
=======
RETRIES = 5
>>>>>>> REPLACE

Các tool dùng cách này: OpenHands, Pi, OpenCode edit. Rủi ro: nếu "đoạn cũ" xuất hiện ở nhiều chỗ, tool không biết thay chỗ nào — hoặc tệ hơn, thay nhầm chỗ.

4. Unified diff / patch. Đây là định dạng chuẩn của nghề lập trình. Bản đầy đủ ghi cả số dòng và ngữ cảnh:

--- a/settings.py
+++ b/settings.py
@@ -1,2 +1,2 @@
-RETRIES = 3
+RETRIES = 5
 TIMEOUT = 30

Dòng @@ -1,2 +1,2 @@ nói vị trí và độ dài đoạn: bản cũ bắt đầu từ dòng 1 gồm 2 dòng, bản mới cũng vậy. Dấu - là dòng bị bỏ, dấu + là dòng thêm vào, dòng không dấu là ngữ cảnh giữ nguyên. Aider dùng biến thể bỏ số dòng hunk cho gọn. Còn Codex dùng định dạng "file-operation patch" — nói thao tác theo tên file, có ngữ cảnh, không cần đếm dòng:

*** Begin Patch
*** Update File: settings.py
@@
-RETRIES = 3
+RETRIES = 5
 TIMEOUT = 30
*** End Patch

Tìm đúng chỗ để sửa

SWE-bench, harness, và cách luyện agent

Đã có model, có vòng lặp, có edit format. Câu hỏi còn lại: làm sao biết một coding agent giỏi thật, và làm sao luyện nó giỏi lên? Đây là nội dung slide 46–54, phần "cơm áo" của cả buổi giảng.

SWE-bench là gì và vì sao nó khó

SWE-bench (Jimenez et al.) lấy các issue thật từ những repository Python phổ biến, đưa cho agent cả issue lẫn repository ở đúng thời điểm trước khi issue được sửa, và yêu cầu agent tạo ra một patch. Cách chấm gồm hai phần (slide 47):

  • Fail → pass: các test lẽ ra phải fail trước bản sửa — giờ phải pass. Đây là "yêu cầu sửa" đã được đáp ứng.
  • Pass → pass: các test vốn đã pass — phải tiếp tục pass. Đây là "hành vi cũ được giữ nguyên".

Vì sao SWE-bench khó? Năm lý do, xếp theo độ khó tăng dần:

  1. Phải định vị trong repository lớn. Không ai chỉ file nào. Ở bài toán localization (slide 64, CodeScout 2026), agent phải đoán đúng file, đúng module, đúng hàm — và điểm là F1 ở cả ba mức. Điểm quan trọng: bản patch đúng không được đưa vào làm manh mối; agent phải tự tìm.
  2. Không được phá hành vi cũ. Sửa đúng chỗ nhưng làm hỏng chỗ khác là fail. Đây là ràng buộc pass → pass.
  3. Test bị ẩn. Agent không thấy test chấm điểm, nên không thể "học tủ". Nó phải giải bài toán thật, không phải đoán đáp án.
  4. Issue viết bằng ngôn ngữ tự nhiên, thường mơ hồ. "Ứng dụng thỉnh thoảng treo khi lưu" — người viết issue không biết nguyên nhân, nếu biết họ đã sửa rồi.
  5. Môi trường phải chạy được. Cài dependency, đúng phiên bản, chạy được test — với repository thật, việc này không nhỏ. Slide 48 vì vậy nhấn: phải kiểm tra môi trường trước khi thu thập dữ liệu luyện.

Ví dụ đời thường để hình dung độ khó: bạn được giao "cái máy in thỉnh thoảng kẹt giấy, sửa đi", trong một tòa nhà 5.000 phòng, và sau khi sửa phải chắc chắn 100 thiết bị khác vẫn chạy. Đó gần đúng là SWE-bench.

Tạo ra task luyện được: SWE-Gym và SWE-smith

Muốn luyện agent, cần rất nhiều task chạy được. Issue thật thì có hạn, nên người ta chế thêm. Slide 48 (SWE-Gym) định nghĩa một task chạy được gồm ba phần:

  • Trạng thái đầu: file + dependency + lệnh chạy test.
  • Issue: hành vi mong muốn + cách tái hiện.
  • Kiểm tra: bug phải fail trước; bản sửa phải khôi phục hành vi đúng.

Còn slide 51–52 (SWE-smith, Yang et al., 2025) mô tả cách tiêm bug nhân tạo để nhân số lượng task lên: chuẩn bị một bản chạy tốt → sửa code, không sửa test → giữ lại những ca mà test mới bắt đầu fail. Ví dụ cụ thể từ slide 52:

Trạng tháiCodeKết quả test
Bản gốc (baseline)return 3 if value is None else value4 pass

Khôi phụcquay lại dòng gốc4 pass

Vì sao "sửa code, không sửa test" là nguyên tắc sắt? Vì test là nguồn sự thật của task. Nếu bạn bẻ test cho khớp với code sai, bạn đang dạy agent "làm hài lòng đề bài hỏng" — một thói quen tai hại khi gặp đề thật. Giống như huấn luyện viên sửa đồng hồ bấm giây cho khớp thành tích, thay vì sửa học trò chạy nhanh hơn.

Slide 53 nhắc thêm: các ngôn ngữ khác nhau có cách chạy khác nhau — Python dùng pyproject.toml + pytest, TypeScript dùng package.json + npm test, Rust dùng Cargo.toml + cargo test. Nguyên tắc: đọc cấu hình dự án trước khi chọn lệnh build/test. Đừng đoán — nhìn bếp trước khi nấu.

Học từ nhiều bước — và bài toán "lỗi muộn"

Slide 49 (R2E-Gym, Jain et al., 2025) nói về luyện RL cho chuỗi hành động dài. Có một chi tiết phân biệt tinh tế:

  • Hành động của agent là mục tiêu luyện — tìm file, quyết định sửa gì, chạy test hay kết thúc.
  • Kết quả tool chỉ là ngữ cảnh — danh sách file tìm được, patch đã áp, output test. Không phải thứ để "học thuộc".
  • Phần thưởng đến ở cuối: sửa được hay không. Và đây là vấn đề: một thất bại ở cuối không chỉ ra được quyết định nào ở giữa đã sai.

Ví dụ: một đội bóng thua 0–1. Không ai biết ngay là do đường chuyền sai ở phút 20, do thay người ở phút 70, hay do chiến thuật từ đầu. Trong học tăng cường người ta gọi đó là bài toán credit assignment (phân bổ công – lỗi). Agent cũng vậy: patch cuối cùng fail, nhưng lỗi có thể nằm ở bước tìm file (chọn sai file), ở bước sửa (sửa sai dòng), hay ở bước kiểm (bỏ qua test). Cả một chuỗi đúng, chỉ một bước sai — mà tín hiệu thưởng chỉ có một con số ở cuối.

Slide 50 bổ sung hướng xử lý: thay vì chỉ sinh một lời giải, cho model sinh nhiều phương án rồi dùng một learned verifier (bộ chấm học được) để chọn phương án tốt nhất — đổi compute lúc suy luận lấy độ chính xác. (Nhớ lại pass@k ở mục 3: sinh nhiều rồi chọn là chiến lược có cơ sở.)

Harness + model — hai nửa của một năng lực

Đây là phần kết tinh của cả bài. Slide 54 định nghĩa:

Harness = prompts + tools + agent loop + context management

— slide 54. Chính là bốn thứ bạn đã học ở bài 02 (vòng lặp), bài 03 (tools), bài 04 (ngữ cảnh).

Và slide 54 kể một xu hướng luyện model mới: multi-harness training — cùng một model (cùng trọng số) được chạy trong nhiều harness khác nhau (ví dụ OpenHands, OpenCode, Codex), mỗi harness có prompt, tool, vòng lặp, cách quản lý ngữ cảnh riêng; kết quả patch được chấm bằng test; rồi các "trajectory" (đường đi của agent) và phần thưởng được dùng để cập nhật model. Nemotron 3 Ultra dùng tiêu chuẩn ít nhất 2 harness cho mỗi phân bố task; Polar thì để các harness "bản địa" gọi chung một proxy API của model.

Vì sao phải luyện nhiều harness? Vì một model chỉ biết làm việc trong một kiểu khung là model mong manh. Giống một nhân viên chỉ làm được khi có đúng chiếc bàn quen thuộc: đổi văn phòng là loay hoay. Luyện qua nhiều harness buộc model học phần bản chất của công việc — tìm, sửa, kiểm — chứ không học thuộc cách gọi tool của riêng một khung.

Hướng mới: model đoán trước kết quả chạy code

Slide 73–79 mở một hướng nghiên cứu thú vị. Một agent hiện tại có hai vai: policy π(a | h) — chọn hành động dựa trên lịch sử; và một world model p(o | h, a) — đoán kết quả của hành động đó. Hiện tại agent phải chạy thật để biết kết quả. Nếu model đoán được, nó có thể chọn hành động tốt hơn mà không cần chạy hết mọi thứ.

Nhưng đoán sai thì nguy hiểm. Slide 75 cho một ví dụ rất hay:

items = [1]
alias = items
alias.append(2)
result = len(items)

Thực thi thật: items = [1, 2], alias = [1, 2], result = 2 — vì alias và items trỏ vào cùng một danh sách (tham chiếu chung), không phải hai bản sao. Một model đoán sai kiểu "alias là bản sao" sẽ tưởng result = 1 — và đó chính là lỗi dự đoán mà slide muốn cảnh báo.

Slide 76 cho thấy hậu quả: có hai bản sửa A (đúng) và B (sai). Model đoán "A sẽ fail, B sẽ pass" → nó chọn B và vứt A. Chỉ cần world model sai một lần là quyết định sai. Slide 79 để mở bốn câu hỏi: đoán giỏi hơn có ra quyết định tốt hơn không? Chi phí (thời gian, token, số lần chạy thật) có giảm không? Bối cảnh mới thì sao? Và khi nào nên chạy thật thay vì đoán? Tóm mục 6 trong một câu

SWE-bench chấm agent bằng hai câu hỏi — "sửa được chưa?" (fail → pass) và "có phá gì không?" (pass → pass); muốn luyện thì cần task chạy được (SWE-Gym, SWE-smith); và kết quả cuối cùng phụ thuộc cả model lẫn harness — nên cả hai được thiết kế và luyện cùng nhau.

Hiểu lầm thường gặp

Bốn hiểu lầm hay gặp nhất khi mới làm quen với coding agent:

  1. "Model giỏi là đủ — harness chỉ là phụ kiện." — Không. Cùng một model GPT-4 Turbo, chỉ đổi định dạng sửa file, tỉ lệ thành công nhảy từ 20% lên 61% (slide 43). mini-SWE-agent với harness chỉ có shell vẫn mạnh (slide 39). Và chính các nhóm luyện model cũng luyện qua nhiều harness (slide 54). Harness và model là hai nửa của một năng lực.

  2. "So khớp code với bài mẫu là đánh giá được." — Không. return x >= 0 khác bài mẫu đúng một ký tự nhưng sai ở x = 0; return not (x <= 0) viết khác hẳn nhưng lại đúng (slide 20). Giống chữ ≠ đúng, khác chữ ≠ sai. Muốn biết đúng hay không thì phải chạy — mà chạy thì cũng chỉ biết đúng với những test đã có (slide 24).

  3. "Test pass nghĩa là xong việc." — Chưa. Slide 61 nói thẳng: "a test pass is one step, not the release decision" — test pass là một bước, không phải quyết định phát hành. Còn pass → pass (không phá hành vi cũ), còn yêu cầu phi chức năng (nhanh hơn, an toàn hơn, dễ bảo trì — slide 27), còn review, deploy, theo dõi, đường lùi. Một chiếc xe qua được kiểm định khí thải chưa chắc đã đủ an toàn để chở người.

  4. "Sửa một dòng thì dễ hơn viết cả hàm." — Không hẳn. Sửa phải tìm đúng chỗ, khớp chính xác văn bản xung quanh, không phá code khác, và tái tạo đúng khoảng trắng. Cộng thêm: cách diễn đạt bản sửa cũng quan trọng bậc nhất (20% so với 61%). Sửa một câu trong hợp đồng đã ký khó hơn viết câu mới trong bản nháp — vì bạn còn phải tôn trọng toàn bộ phần còn lại.

Thực hành — tự làm, tự kiểm

Ba bài dưới đây làm ra nháp trước, rồi mới mở đáp án. Đáp án chỉ là gợi ý — điều quan trọng là cách lập luận của bạn.

Bài 1 — Bóc một bug "falsy" theo vòng localize → edit → verify

Đề bài: Bạn được giao một issue: "Khách hàng chọn 'không phân trang' (page size = 0) nhưng hệ thống vẫn trả về 20 dòng mỗi trang." Trong repository có file paging.py:

def page_size(cfg):
    return cfg.get("page_size") or 20

Hãy viết ra:

  1. Localize: bạn làm gì để chắc chắn lỗi nằm ở dòng này (chứ không phải chỗ khác)?
  2. Edit: viết hai dòng code thay thế.
  3. Verify: liệt kê bốn trường hợp cần chạy, và kết quả mong đợi của từng trường hợp.
  4. Giải thích: một câu — vì sao or là sai ở đây?
Xem đáp án gợi ý
  • Localize: tìm theo tên khóa: rg 'page_size' . để thấy mọi chỗ dùng nó; rồi tái hiện lỗi bằng cách chạy test truyền page_size = 0 và xem nó trả về 20. Khi test đỏ đúng như triệu chứng, bạn đã định vị được chỗ cần sửa. (Nếu chưa có test cho ca này, viết test trước — nhớ nguyên tắc "sửa code, không sửa test" đã nói ở mục 6 chỉ áp cho tiêm bug; còn khi tái hiện lỗi thật thì thêm test mới là việc đúng.)
  • Edit: 
    value = cfg.get("page_size")
return 20 if value is None else value
  • Verify: (a) không có khóa page_size → 20; (b) page_size = 0 → 0 (ca vừa sửa); (c) page_size = 20 → 20; (d) page_size = 5 → 5. Và chạy cả bộ test để chắc không làm hỏng gì khác (regression).
  • Giải thích: or coi mọi giá trị falsy — trong đó có số 0 hợp lệ — là "không có giá trị", nên số 0 bị thay bằng mặc định; cần phân biệt "thiếu" (None) với "bằng 0".

Nếu bạn tự nghĩ ra thêm ca "page_size = -1" thì càng tốt — câu hỏi tiếp theo sẽ là: giá trị âm nên bị từ chối hay hiểu là "không giới hạn"? Đó là quyết định hành vi, không phải cú pháp.

Bài 2 — Chọn cách sửa file (edit format)

Đề bài: Với mỗi tình huống, chọn một cách diễn đạt bản sửa phù hợp — gửi cả file (whole file), tìm/thay (search-replace), unified diff, hay script shell (sed/Python) — và nói ra rủi ro chính của cách bạn chọn.

  1. Đổi một dòng TIMEOUT = 30 thành TIMEOUT = 60 trong file dài 400 dòng; dòng này chỉ xuất hiện một lần.
  2. Viết lại toàn bộ một file cấu hình 15 dòng (đổi hầu hết nội dung).
  3. Đổi tên hàm getUser thành fetchUser ở 40 file khác nhau.
  4. Đổi return x thành return x + 1 trong một file mà dòng return x xuất hiện ba lần giống hệt nhau.
Xem đáp án gợi ý
  • (1) Search-replace hoặc unified diff. Thay đổi nhỏ, mục tiêu duy nhất → hai cách đều gọn và an toàn. Rủi ro: nếu chuỗi tìm kiếm không khớp từng ký tự (khoảng trắng, dấu nháy) thì lệnh thất bại — nhưng thất bại thì vô hại, còn hơn thay nhầm.
  • (2) Whole file. File ngắn, đổi nhiều → viết lại cả file là đơn giản nhất. Rủi ro: lặp lại phần không đổi (tốn token) và có thể vô tình bỏ sót một dòng cũ quan trọng; với file ngắn thì rủi ro này nhỏ.
  • (3) Script shell (sed / Python) chạy trên nhiều file. Search-replace đơn lẻ không phủ 40 file; whole-file 40 lần thì phí và dễ sai. Rủi ro: script có thể thay cả những chỗ không nên thay (ví dụ tên hàm trùng trong chuỗi ký tự hoặc comment) — nên chạy thử khô (dry-run) hoặc kiểm tra bằng rg sau khi chạy.
  • (4) Cần thêm ngữ cảnh để phân biệt. Đoạn cũ không duy nhất → search-replace trần rất nguy hiểm: nó có thể thay cả ba chỗ, hoặc thay sai chỗ. Cách đúng: kèm thêm các dòng xung quanh để đoạn tìm trở nên duy nhất, hoặc dùng diff có ngữ cảnh (và nếu công cụ hỗ trợ, có số dòng). Nếu sau khi thêm ngữ cảnh vẫn còn hai chỗ giống nhau, phải đọc code để hiểu chỗ nào đúng về mặt ngữ nghĩa — đây là lúc agent cần "hiểu", không chỉ cần "khớp".

Điểm chung: chọn format là bài toán đánh đổi giữa gọn và chắc. Và nhớ con số 20% → 61%: lựa chọn này không nhỏ.

Bài 3 — Tự thiết kế một task luyện kiểu SWE-smith

Đề bài: Chọn một hàm nhỏ bất kỳ (tự nghĩ cũng được, ví dụ hàm tính phí giao hàng). Hãy thiết kế một task luyện gồm bốn phần, đúng theo tinh thần slide 48 và 51–52:

  1. Baseline chạy tốt: code + 4 test đều pass (viết ra 4 ca kiểm).
  2. Tiêm bug: sửa code, không sửa test — sao cho đúng một test fail.
  3. Bằng chứng ba trạng thái: trước / sau khi tiêm / sau khi khôi phục.
  4. Kiểm tra môi trường: một câu — làm sao chắc task này chạy được trước khi đem đi luyện?
Xem đáp án gợi ý

Ví dụ với hàm tính phí giao hàng (miễn phí khi đơn từ 100 trở lên):

def shipping_fee(total, is_member):
    if total >= 100:
        return 0
    return 0 if is_member else 5
  • Baseline — 4 test pass: (a) total = 99, không phải member → 5; (b) total = 100 → 0 (đúng biên); (c) total = 150 → 0; (d) total = 50, là member → 0.
  • Tiêm bug: đổi total >= 100 thành total > 100. Test (b) — đúng ca biên — bắt đầu fail: nhận 5 thay vì 0. Ba test còn lại vẫn pass.
  • Ba trạng thái: trước: 4 pass · sau tiêm: 3 pass + 1 fail · khôi phục: 4 pass. Đúng ba dòng bằng chứng như slide 52.
  • Kiểm tra môi trường: chạy baseline một lần trên máy sạch (đúng phiên bản, đủ dependency) và xác nhận "4 pass" trước khi tiêm bug — nếu baseline đã không chạy được thì mọi kết quả sau đó vô nghĩa (slide 48: validate the environment before collecting trajectories).

Tự kiểm thêm: bug của bạn có phải loại "sửa code, không sửa test" không? Nếu bạn thấy mình đang chỉnh test cho khớp code sai — làm lại từ đầu. Và nếu bug khó tới mức chính bạn không sửa được sau 10 phút, hãy tiêm bug dễ hơn: task luyện cần độ khó vừa phải, không cần hóc búa.

Kiểm tra hiểu

Sáu câu, bấm chọn — đúng thì hiện giải thích, sai thì hiện gợi ý để thử lại.

1. Đâu là lý do sâu xa nhất khiến code trở thành domain mà agent tiến bộ nhanh nhất?

Gợi ý: nghĩ tới chuyện agent biết mình sai mà không cần con người phán.

Chính xác. Code là "bài tập có đáp án ở cuối sách": test chạy ra kết quả, build xanh hay đỏ — tín hiệu rõ ràng, rẻ, không cần con người. Nhờ đó vòng lặp localize → edit → verify có điểm dừng khách quan, và agent tự sửa mình được. Đây cũng là lý do RL từ kết quả test hoạt động tốt trong domain code (slide 28).

2. Vì sao tokenizer của model code gộp chuỗi khoảng trắng thành một token (kiểu ↵···), thay vì trả một token cho mỗi dấu cách?

Gợi ý: đếm lại ví dụ ở mục 2 — 13 mảnh so với 7 mảnh.

Chính xác. Slide 9: gộp các cụm khoảng trắng hay gặp thành token để không tiêu một token cho mỗi dấu cách. Ví dụ if·ready:↵····return·value↵ tốn 7 token thay vì 13. Lợi ích kép: cùng ngữ cảnh chứa được nhiều code hơn, và thụt lề vẫn là token mang cú pháp — model vẫn "thấy" được cấu trúc khối.

3. Thí nghiệm của Aider trên 89 bài refactoring cho kết quả: cùng GPT-4 Turbo, SEARCH/REPLACE đạt 20% còn simplified unified diff đạt 61%. Bài học chính là gì?

Gợi ý: điều duy nhất thay đổi trong thí nghiệm là gì?

Chính xác. Biến duy nhất bị đổi là định dạng diễn đạt bản sửa — cùng model, cùng bài. Kết quả 20% → 61% cho thấy harness (prompt + tools + loop + context) là một nửa của năng lực, không phải phụ kiện. Các phương án b và d sai vì quá tuyệt đối: mỗi format có điểm mạnh yếu (mục 5); phương án c sai vì model vẫn quan trọng — bài học là cả hai cùng quan trọng.

4. mini-SWE-agent chỉ cho model một giao diện duy nhất là shell (chạy lệnh, không tool riêng cho từng việc) mà vẫn đạt kết quả tốt. Bài học rút ra là gì?

Gợi ý: slide 39 và slide 54 nói gì về "harness = prompts + tools + agent loop + context management"?

Chính xác. Một giao diện shell đã đủ để đọc (rg, cat, find), sửa (sed, Python, patch) và kiểm (pytest, build). Sự tồn tại của mini-SWE-agent, Agentless và thí nghiệm Aider cùng dẫn tới một kết luận: kết quả của agent là tích của model và harness — không thể chỉ nhìn một phía.

5. Trong cách chấm của SWE-bench, phần pass → pass kiểm tra điều gì?

Gợi ý: fail → pass là "sửa được cái cần sửa"; vậy pass → pass là gì?

Chính xác. Slide 47: fail → pass là "yêu cầu sửa đã được đáp ứng", pass → pass là "hành vi cũ được giữ nguyên" (regression check). Một bản sửa chỉ đúng khi vượt qua cả hai — sửa được bug mới mà phá hành vi cũ thì vẫn fail. Đây cũng là lý do ví dụ retries ở mục 4 phải chạy cả bốn test, không chỉ test của ca zero.

6. Slide 49 nói: "một thất bại ở cuối không chỉ ra được quyết định nào ở giữa đã sai". Ý này quan trọng thế nào khi luyện coding agent bằng RL?

Gợi ý: tín hiệu thưởng chỉ có một con số ở cuối chuỗi, còn chuỗi thì dài.

Chính xác. Cả chuỗi có thể đúng, chỉ một bước sai — nhưng phần thưởng chỉ nói "fail". Model phải tự suy ra lỗi nằm ở bước tìm file, bước sửa, hay bước kiểm. Đây là bài toán credit assignment (giống đội bóng thua 0–1 mà không biết lỗi ở đường chuyền nào). Vì vậy slide 49 tách rõ: hành động của agent là mục tiêu luyện, còn output tool chỉ là ngữ cảnh.
